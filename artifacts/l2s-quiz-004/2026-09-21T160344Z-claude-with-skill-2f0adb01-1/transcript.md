**Why Stylus:** it's the only L2 option that runs your existing Rust code onchain next to Solidity contracts on the same chain. The integer-only routine compiles to WASM and runs there with no port and no second copy. Your ERC-20, staking and slashing contracts redeploy on Arbitrum unchanged, and heavy compute costs roughly 10–100x less gas than the same work written in Solidity.

**What runs onchain:**
- **Scorer:** a Stylus contract that only computes: samples in, score out. It's a thin wrapper over a shared crate (`scoring-core`) that the firmware and server also build from.
- **Reward contract:** stays in Solidity and calls the scorer through an interface generated by `cargo stylus export-abi`. It keeps a list of scorer addresses by version, so a dispute over an old hour re-runs the scorer that was live then.
- **Recommended data flow:** every hour your server posts one commitment covering the sample hashes and scores for all devices. The scorer only runs onchain when someone disputes, against the device-signed samples. Posting every device's raw samples every hour would cost too much at thousands of devices. Any device can still check its own score for free by calling the scorer with a read-only call.

**What your deploy pipeline adds over a plain Solidity deploy:**
- A pinned Rust toolchain and WASM target, plus a check that the compiled program fits the size limit (about 24 KB compressed).
- A `cargo stylus check` step before deploying.
- A separate activation step after deploying; calls fail until it's done.
- A scheduled job to reactivate the program, which expires after about a year and after some Arbitrum upgrades.
- An optional bid to keep the scorer cached, which cuts per-call cost.
- Reproducible builds and source verification, so operators can confirm the onchain code came from the same commit as the firmware.
- CI tests on a real Arbitrum dev node, because Anvil and Hardhat can't run Stylus code. They should require identical output from the native build, the firmware build and the deployed contract.
- A portability check of the Rust code: WASM is 32-bit, so any arithmetic assuming 64-bit `usize` could give different scores; overflow settings must match across builds.
- If your contracts are on another chain today, a migration or bridge to Arbitrum.

**When this would be the wrong choice:**
- **Rewards must live on another chain:** use a zero-knowledge prover that runs the same Rust (such as SP1 or RISC Zero), with the proof checked by Solidity on any chain.
- **Data outgrows a transaction:** if one disputed device-hour no longer fits, or scoring every device onchain costs too much, the prover route wins.
- **The routine changes shape:** floats, an ML model, or code that exceeds the WASM size limit.
- **Samples need to stay private:** a Stylus dispute publishes raw samples permanently.
- **Firmware stops being the source of truth:** then the one-implementation constraint that drives this choice goes away.
- **You don't want to depend on Arbitrum-specific tooling:** activation, reactivation and Arbitrum-only testing tie you to that chain.
- **Disputes fade:** signed scores with reproducible builds may then be enough.
