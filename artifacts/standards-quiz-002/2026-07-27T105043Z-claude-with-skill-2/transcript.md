The EVM sees code at the address and loads the implementation's bytecode to execute, but **storage reads and writes hit the user's own account**, and `address(this)` / `msg.sender` inside that code are the **user's address**. This is delegatecall-shaped, at the account level.\n\nThe `0xef` prefix is deliberate: EIP-3541 has banned deployed contract code from starting with `0xef` since London, so no real contract can be mistaken for a delegation designator.\n\n**Cost:** `PER_AUTH_BASE_COST` = 12,500 gas per authorization for an account that already exists (25,000 charged upfront, refunded down to 12,500 when the authority is a pre-existing account — every one of these users qualifies).\n\n### How approve + swap becomes one atomic transaction\n\nThe implementation exposes a batch-execute entrypoint (the minimal standardized form is ERC-7821 `execute(bytes32 mode, bytes executionData)`; ERC-7579 modular accounts expose the same shape). Call lands on `0xUSER`. EVM sees `0xef0100||impl`, loads `impl`'s code, runs it **in the user's account context**.\n2. Because the account now runs contract code on every call, it can implement arbitrary validation instead of \"one ECDSA signature over the whole tx\":\n\n- Register an ephemeral session key (a throwaway keypair the app holds) in the account's storage, scoped by expiry, spend cap, allowed target contracts, and allowed selectors.\n- The implementation's validation function accepts a signature from that session key, checks the scope, and executes.\n- Exposed to dapps via ERC-1271 (`isValidSignature`) and, on a modular ERC-7579 / ERC-6900 implementation, added or removed as a validator module at runtime.\n\nThe root EOA key stays the ultimate owner and can revoke any session key. Nothing in the protocol removes it at the end of a block, a transaction, or a call. After the first batched swap the account is still a smart account, and remains one indefinitely.\n\n**To change the implementation:** sign a new authorization with `address` = the new implementation and the account's then-current `nonce`, and land it in any type-`0x04` transaction. It overwrites the designator in place.\n\n**To remove it entirely:** sign an authorization with\n\n```\naddress = 0x0000000000000000000000000000000000000000\n```\n\nand submit it in a type-`0x04` transaction. That clears the code field and the account is a plain EOA again.\n\nRequirements in both cases, exactly:\n\n1. A fresh signature **from the EOA's own private key** — no one else can redelegate or revoke it. Whoever holds the key holds this power; there is no admin, no timelock, no implementation-side override.\n2. A correct, non-reusable `nonce` (authorizations are nonce-bound, so an old authorization can't be replayed to silently reinstate an implementation the user removed).\n3. A type-`0x04` transaction carrying it — which any third party may pay for.\n\n**Two operational consequences worth flagging to the team:**\n\n- **Clearing the code does not clear the storage.** Slots the implementation wrote to the user's account survive revocation and survive redelegation. If they later point the same accounts at a different implementation with a different storage layout, stale slots will be misread. Use ERC-7201 namespaced storage in whatever implementation they pick, and treat migrations between implementations as a real migration.\n- **`address.code.length > 0` is now true for these users.** Every `isContract()` check, every \"EOA-only\" modifier, and every off-chain heuristic that reads `EXTCODESIZE` (which returns 23 for a delegated account) will reclassify them. Audit anything in their stack that gates on that.\n\n---\n\n## 4.
