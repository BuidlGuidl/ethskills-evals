1. Yes. As of September 22, 2026, this is possible on Ethereum mainnet today. The mechanism is EIP-7702, which lets an already-existing EOA set code for itself by signing an authorization with the same private key that controls the account. It does not migrate the user into a new account type and it does not require deploying a new wallet at a new address. The account keeps the same address, private key, ENS name, balance location, nonce/history context, and onchain identity. This shipped in the Pectra network upgrade, which activated on Ethereum mainnet on May 7, 2025.

2. After the user opts in, their account's code is not ordinary contract bytecode. It is a delegation designator: the bytes `0xef0100` followed by the address of a deployed implementation contract. In practical terms, the user's address points at that implementation for execution logic. When someone calls the user's address, Ethereum follows the delegation indicator and runs the implementation contract's code in the context of the user's own account.

   For an approve+swap, the user authorizes an implementation that exposes batching logic. The batched call is sent to the user's same address, and the delegated code performs the ERC-20 `approve` and the swap as one execution path. Because both operations happen inside one transaction, they either both succeed or the whole transaction reverts. To external contracts, the calls are being made from the user's existing address, not from a newly deployed wallet address, so the token allowance and swap behavior are tied to the original EOA address.

3. It does not automatically revert to a plain EOA after one batched transaction. The delegated behavior stays in place because the delegation indicator remains as the account's code. Running a transaction through the delegated implementation consumes that transaction, but it does not clear the delegation.

   To change the behavior, the account must make a later EIP-7702 authorization that points to a different implementation address. To remove the behavior and return to having no delegated code, the account must make a later authorization that clears the delegation by pointing to the zero address. Until one of those explicit actions happens, calls to the account continue to use the delegated implementation.

4. Deploying a fresh ERC-4337 smart-contract wallet for each user does not satisfy the constraint. ERC-4337 accounts are smart-contract accounts deployed at their own contract addresses. Even if the new wallet can batch calls, sponsor gas, or support session keys, it is a different onchain account from the user's existing funded EOA. The team would have to move funds, permissions, ENS configuration, and user identity/history assumptions over to a new address. That is exactly what the requirement rules out: the user's current address, ENS name, and onchain history must survive as the account being used.
