1. Yes. As of September 22, 2026, this is possible on Ethereum mainnet. The mechanism is EIP-7702, commonly described as setting code for EOAs or EOA code delegation. It lets an already-existing EOA authorize its account to execute already-deployed contract code while remaining the same account address, controlled by the same EOA private key, rather than migrating to a newly deployed contract account. This shipped in the Pectra network upgrade, the combined Prague execution-layer and Electra consensus-layer upgrade, which went live on Ethereum mainnet on May 7, 2025 at about 10:05 UTC, epoch 364032.

2. After the user opts in, the user's account does not contain a full wallet contract. Its account code is set to a small delegation indicator: the bytes `0xef0100` followed by the address of the chosen delegate implementation contract. In other words, the user's address points at already-deployed wallet logic. When the EOA sends, or authorizes, a set-code transaction, the protocol processes the authorization before executing the transaction body. If the transaction then calls the user's own address with calldata for a batching function, Ethereum follows the delegation pointer, loads the delegate contract's code, and runs that code in the context of the user's account.

For an approve+swap, the delegated wallet logic can make one external call to the ERC-20 token's `approve` function and then a second external call to the swap router. Both calls are made from the user's existing address, so the token allowance and the swap are attributed to that same EOA. They are part of one transaction, so they are atomic: if the delegate logic reverts because either step fails, the approve and swap effects from that execution revert together.

3. It does not automatically revert to a plain EOA after one batched transaction. The final design uses persistent delegation. Once the authorization is accepted, the account keeps pointing at the delegate implementation address via the `0xef0100 || delegateAddress` indicator. Failed execution of the transaction body also does not automatically undo a delegation that was already processed.

To change the behavior, the EOA must authorize another EIP-7702 delegation to a different delegate address. To remove the behavior and return to no delegated code, the EOA must authorize delegation to the zero address, which clears the account code back to empty code. The EOA private key remains able to originate transactions throughout, but the delegated behavior stays until it is explicitly replaced or cleared.

4. A fresh ERC-4337 smart-contract wallet does not satisfy the constraint because it is a different account at a different address. Even if the team could deploy it deterministically and move assets into it, the old EOA's address would not become that new contract wallet. The user's ENS records would have to be repointed or transferred, funds and approvals would have to move, and the user's past onchain history would remain attached to the old EOA address. That may be a valid migration path for some products, but it violates the requirement that the exact same address, ENS identity, history, and private key continue to be the account users operate from.
