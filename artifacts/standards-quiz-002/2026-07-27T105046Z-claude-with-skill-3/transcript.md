Does it revert to a plain EOA after one transaction?\n\n**No. The delegation is persistent state, not per-transaction.**\n\nThis is the most common misconception about 7702 (it comes from an early draft of the EIP where the code was transient). In the shipped version, the `0xef0100 || address` designator is written to the account's code field and **stays there indefinitely**, across any number of transactions, until it is explicitly changed. The account keeps behaving as a smart account for every subsequent call.\n\nTo change or remove it, exactly one thing is required: **a new EIP-7702 authorization signed by that same EOA private key, carried in another type-0x04 transaction.**\n\n- **Re-point to a different implementation:** sign an authorization for the new implementation address. The old designator is overwritten. (Upgrades are also why implementations should keep storage layouts compatible — the storage is the user's and survives the re-point.)\n- **Fully revoke, back to a plain EOA:** sign an authorization with `address = 0x0000000000000000000000000000000000000000`. This clears the account's code entirely and the account is an ordinary EOA again.\n\nTwo things that do **not** clear it: executing a batch, and time passing. There is no expiry. Note also that the authorization `nonce` check means a signed-but-unused authorization is invalidated by any transaction the account sends in the meantime — useful for making revocation immediate.\n\nConsequences the team should plan for:\n- The delegate is a live attack surface for as long as it's set. Pick an audited implementation; assume users will never revoke.\n- A malicious or buggy implementation can move everything in the account. Present the opt-in signature accordingly — wallets treat a 7702 authorization as a high-risk signature for good reason.\n- The account still has its key. Delegating does **not** disable ordinary key-signed transactions, so the key remains a full-power bypass of any session-key policy the implementation enforces.\n\n---\n\n## 4.
