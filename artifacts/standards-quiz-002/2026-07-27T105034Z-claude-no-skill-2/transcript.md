Does it revert to a plain EOA after one batch? No.\n\n**The delegation persists indefinitely.** This follows directly from *where* it lives: the\ndesignator is written into the account’s `codeHash` in the state trie. It is account state, not\ntransaction-scoped state. Nothing in the transaction’s post-processing clears it, and the spec\ndescribes no expiry, no TTL, and no use counter. The\n  implementation contract cannot revoke on the user’s behalf, and neither can you.\n- The tuple’s `nonce` must equal the account’s current nonce (again `+1` if the account is also the\n  transaction sender).\n- Somebody must pay gas for it (it can be a sponsored transaction — the authority does not need to\n  be the sender).\n- If multiple tuples from the same authority appear in one transaction, the **last valid\n  occurrence** wins.\n\nOne operational warning when *switching* implementations: the account’s storage is not cleared. The\nold implementation’s slot layout stays populated, and a new implementation with a different layout\nwill read garbage. Prefer implementations using namespaced storage (ERC-7201), and treat a\ndelegate swap with the same care as a proxy upgrade.\n\n---\n\n## 4. Why the “fresh ERC-4337 wallet per user” proposal fails the constraint\n\nIt fails on the one hard requirement: **the address cannot survive a migration.** Everything else is\ndownstream of that.\n\n**The addresses are derived from different pre-images, and cannot be made equal.**\n\n```\nEOA address       = keccak256(pubkey)[12:]\nCREATE2 address   = keccak256(0xff ‖ factory ‖ salt ‖ keccak256(initcode))[12:]\n```\n\nAn ERC-4337 wallet is a deployed contract, so its address is fixed by the deployer and initcode, not\nby the user’s key.
