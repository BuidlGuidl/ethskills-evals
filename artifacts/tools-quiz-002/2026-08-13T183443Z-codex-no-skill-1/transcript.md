+# No: a Foundry migration is not required
+
+The premise is out of date. Hardhat 3 has built-in support for Solidity tests and Solidity fuzz tests; no plugin is required. A public or external test function whose name starts with `test` is a normal Solidity test, and if that function has parameters, Hardhat executes it repeatedly with generated random arguments. Existing TypeScript tests can remain in place and run alongside the Solidity tests.
+
+The smallest proof of concept in the existing repo is:
+
+```bash
+# if this is currently a Hardhat 2 project, upgrade Hardhat rather than migrate the repo
+npm install --save-dev hardhat@^3
+
+# optional, but gives Solidity tests forge-std assertions and supported cheatcodes
+npm install --save-dev 'github:foundry-rs/forge-std#v1.9.7'
+```
+
+Then add a test such as `test/VaultFuzz.sol` (Hardhat also recognizes `contracts/*.t.sol`):
+
+```solidity
+// SPDX-License-Identifier: UNLICENSED
+pragma solidity ^0.8.28;
+
+import {Test} from "forge-std/Test.sol";
+import {Vault} from "../contracts/Vault.sol";
+
+contract VaultFuzzTest is Test {
+    Vault vault;
+
+    function setUp() public {
+        vault = new Vault();
+    }
+
+    // `amount` is generated by Hardhat; the assertion is the property.
+    function testFuzz_DepositAccounting(uint96 amount) public {
+        vault.deposit(amount);
+        assertEq(vault.totalAssets(), amount);
+    }
+}
+```
+
+Run it with:
+
+```bash
+npx hardhat test solidity
+
+# or run all Solidity and JS/TS suites together
+npx hardhat test
+
+# useful while iterating
+npx hardhat test solidity --grep DepositAccounting
+```
+
+No special configuration is necessary when Solidity tests live under the default `test/` directory. If the team wants to keep them separate, this is sufficient in `hardhat.config.ts`:
+
+```ts
+import {defineConfig} from "hardhat/config";
+
+export default defineConfig({
+  // preserve the repo's existing compiler, plugins, and network settings
+  paths: {
+    tests: {
+      solidity: "./test-solidity",
+    },
+  },
+});
+```
+
+Hardhat 3 also implements many Foundry-compatible cheatcodes, so using `forge-std/Test.sol`, `vm.prank`, `vm.assume`, `vm.expectRevert`, etc. does not imply switching the project to Forge. Unsupported-cheatcode compatibility should be checked if an intended suite is unusually advanced.
+
+There is a second, also non-migratory option: install the Foundry CLI and add a small `foundry.toml` that points Forge at the existing Hardhat source tree. That lets `forge test` coexist with `npx hardhat test` and is attractive for stateful invariant campaigns or when the team needs a Forge-only feature. It still does **not** require porting deployments, TypeScript tests, tasks, or the rest of the repo:
+
+```toml
+[profile.default]
+src = "contracts"
+test = "test-solidity"
+out = "out"
+libs = ["lib", "node_modules"]
+
+[fuzz]
+runs = 1000
+
+[invariant]
+runs = 256
+depth = 100
+```
+
+```bash
+forge install foundry-rs/forge-std --no-commit
+forge test
+forge test --match-test testFuzz_DepositAccounting
+```
+
+So the appropriate scope is a small spike: upgrade to Hardhat 3 if needed, add one Solidity property test, and run `npx hardhat test solidity`. Consider a side-by-side Forge runner only if the desired invariant/cheatcode functionality exceeds Hardhat's compatibility. A full-sprint migration is not a prerequisite for Solidity fuzz testing.
