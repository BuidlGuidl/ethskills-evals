Written to `answer.md`. **Short version: the plan is not safe — block it.** The CREATE2 reasoning is a real mechanism applied to the wrong conclusion. CREATE2 gives address equality across chains only if deployer, salt, *and* initcode are all held constant. For v4 they weren't: Uniswap ran a public salt-mining competition for the PoolManager and mined a different vanity salt per chain, and the constructor owner differs per chain too. Uniswap's own deployment docs state it explicitly: integrators should "no longer assume that they are deployed to the same addresses across chains." What I verified live with `cast`: - Each chain's PoolManager is **48021 bytes on its own chain and completely empty on the other two**. Mainnet `0x0000...4444c`, Base `0x498581fF...`, Arbitrum `0x360E68fa...` — three addresses, same bytecode, mutually dead. - The failure is silent. A raw `eth_call` to the mainnet PoolManager address on Base returns `{"result":"0x"}` — success, no revert. Reads return "pool uninitialized" everywhere; a write path succeeds as a no-op, so an approve+transfer sequence can move tokens with nothing on the other end. - Confirming table: every periphery contract (PositionManager, StateView, Quoter, both Universal Routers) self-reports `poolManager()` as its *own* chain's PoolManager — the contracts vouching that each per-chain set is coherent. - Permit2 and ReservesLens genuinely *are* the same address everywhere. That's likely where the team's intuition came from, and it's the dangerous part: a config that's right for Permit2 and wrong for PoolManager looks half-working. A nastier variant one layer over: the mainnet **v3** factory address is also the v3 factory on Arbitrum, but on Base that address holds 4221 bytes of an unrelated contract. So "same address" isn't reliably wrong — it's right on some chains and occupied by something else on others. Two things for the schedule: your **hooks** aren't a config edit. v4 encodes hook permissions in address bits, so hooks must be salt-mined per chain against that chain's PoolManager — real redeployment work before next week. And Base carries two USDCs (native `USDC` and bridged `USDbC`), both rendering as "USDC" in most UIs. The answer includes the full verified Base/Arbitrum/mainnet address tables and a boot-time assertion — per-chain map with *no* fallback default, plus the `poolManager()` cross-check so a copy-paste slip between two chains' tables fails at startup rather than in production.
