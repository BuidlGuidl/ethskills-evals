Payment: x402 + EIP-3009\n\n### The 402\n\nAn unpaid `GET /forecast?lat=…&lon=…` returns **402** with a `PAYMENT-REQUIRED` header\nand a JSON body containing `accepts[]`:\n\n```jsonc\n{\n  \"x402Version\": 2,\n  \"error\": \"payment_required\",\n  \"accepts\": [{\n    \"scheme\": \"exact\",\n    \"network\": \"base\",\n    \"maxAmountRequired\": \"350000\",\n    \"resource\": \"https://forecast.example.com/forecast\",\n    \"description\": \"One point weather forecast\",\n    \"mimeType\": \"application/json\",\n    \"payTo\": \"<our payout address>\",\n    \"maxTimeoutSeconds\": 120,\n    \"asset\": \"0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913\",\n    \"extra\": { \"name\": \"USD Coin\", \"version\": \"2\" }\n  }]\n}\n```\n\nTwo details that are load-bearing:\n\n- **`350000`, not `0.35`, not `350000000000000000`.** Amounts go on the wire in token\n  base units and USDC has **6 decimals**. An 18-decimal figure here asks for 350 billion\n  dollars and the signature will not verify.\n- **`asset` is native USDC on Base: `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`.**\n  `0xA0b8…eB48` is mainnet USDC and `0xd9aA…b6CA` is bridged USDbC — both are the wrong\n  contract for a Base x402 route, and both fail in confusing ways (wrong chain / a token\n  the client may not hold).\n- `extra.name` / `extra.version` are the **EIP-712 domain** the client signs against.\n  Getting them wrong produces a signature that recovers to the wrong address.\n\n### The signature — and why no ETH is fine\n\nThe client signs an **EIP-3009 `transferWithAuthorization`**: an EIP-712 typed-data\nmessage `{from, to, value, validAfter, validBefore, nonce}` over USDC's domain. Signing\nis a pure offchain key operation. It costs nothing and needs no chain access, so **an\nagent holding USDC and zero ETH can pay**.\n\nThe signature is base64'd into `PAYMENT-SIGNATURE` on the retry:\n\n```jsonc\n{ \"x402Version\": 2, \"scheme\": \"exact\", \"network\": \"base\",\n  \"payload\": { \"signature\": \"0x…\", \"authorization\": { \"from\": \"0x…\", \"to\": \"<payTo>\",\n               \"value\": \"350000\", \"validAfter\": \"0\", \"validBefore\": \"…\", \"nonce\": \"0x…\" } } }\n```\n\nWhoever submits `transferWithAuthorization(...)` to USDC pays the gas — here, the\nfacilitator. Not an ERC-4337 bundler, not ERC-2612 `permit` followed by `transferFrom`\n(that is two transactions and still needs a spender allowance dance).\n\nWe accept the legacy `X-PAYMENT` / `X-PAYMENT-RESPONSE` header names as a fallback so\nclients on the frozen 1.2.0 packages still work; `PAYMENT-*` is what we emit.\n\n### Verify and settle\n\nWe do not run a node and hold no gas. We POST the payment payload plus our requirements\nto a **facilitator**:\n\n- `POST {FACILITATOR}/verify` → is the signature valid, is the amount right, is the payer\n  funded, is the authorization unexpired.\n- `POST {FACILITATOR}/settle` → submits `transferWithAuthorization` on Base and returns\n  the `transaction` hash.\n\nCoinbase runs a public facilitator; anyone can run their own, and the URL is env config\n(`FACILITATOR_URL`) precisely so we can switch or self-host without touching the\nprotocol surface. A mainnet Coinbase facilitator needs CDP credentials, passed through\nas a bearer token — that is an offchain dependency, and the only party in this design\nwho needs an account anywhere.\n\n**Order of operations.** We `verify` first, then **produce the forecast**, then `settle`,\nthen respond. Settling before we know we can serve would take money for a call we then\nfail; producing after settlement risks the upstream being down after the client has\nalready paid. If settlement fails after a successful verify we return **502 with no\ncharge** — the authorization is unused and the client can retry or walk away.\n\n**Replay.** The `nonce` in the authorization is enforced onchain by USDC — a settled\nauthorization cannot be settled twice. We additionally keep an in-process set of seen\nnonces so two concurrent requests carrying the same signature cannot both be served in\nthe window before settlement lands. In a multi-instance deployment this set must move\nto shared storage (Redis) or the onchain nonce is the only guard and one free extra\nresponse per race is possible.\n\nOn success we return `200`, the forecast, and `PAYMENT-RESPONSE` (base64 JSON:\n`{success, transaction, network, payer}`).\n\n---\n\n## 4. Reputation: letting the caller rate us\n\nReputation is **client-attested**. The client that paid calls, on the ReputationRegistry:\n\n```\ngiveFeedback(agentId, value, valueDecimals, tag1, tag2, endpoint, feedbackURI, feedbackHash)\n```\n\nValues are fixed point: quality 95/100 is `value=95, valueDecimals=0`; 99.77% uptime is\n`value=9977, valueDecimals=2`. The registry **rejects feedback from the agent's owner and\noperators**, so we cannot rate ourselves — which is exactly why the score is worth\nanything to the next client.\n\nOur job is only to make the call trivially derivable. We never write feedback and could\nnot if we tried.\n\n**Reading.** A future client calls `getSummary(agentId, clientAddresses, tag1, tag2)`\nfiltered to clients *it* trusts. We serve `GET /reputation` returning the exact call\nparameters (chain, registry address, agentId, tags) so an agent can construct that read\nwithout parsing prose — but it reads the chain itself.
