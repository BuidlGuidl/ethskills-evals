Parse and locally pre-validate `X-PAYMENT` (scheme, network, asset, `payTo`,\n   `value >= 350000`, `validBefore` far enough in the future, EIP-712 signature\n   recovers to `from`). Cheap rejects never reach the facilitator.\n2. `POST /verify` to the facilitator (checks balance and that the nonce is\n   unused).\n3. **Produce the forecast.** If the upstream fails we return `502` *without\n   settling* — the client's authorization expires unused and it is never\n   charged for a failure.\n4. `POST /settle`. On failure, return `402` and do not release the payload.\n5. Return `200`, forecast body, `X-PAYMENT-RESPONSE` header with the settlement\n   receipt (tx hash), and the `feedbackAuth` for step 5 of the flow.\n\nBetween (3) and (5) there is a window where the client is charged but the\nresponse could be lost in transit. We therefore keep a **receipt cache keyed by\nthe EIP-3009 nonce**: a replayed `X-PAYMENT` with an already-settled nonce\nreturns the cached response instead of a second charge. The nonce is a\nclient-chosen idempotency key that the chain already enforces as single-use, so\nwe get idempotency for free.\n\n---\n\n## 4. Ratings (constraint 4)\n\n### 4.1 FeedbackAuth\n\nERC-8004's ReputationRegistry accepts feedback from anyone, but a service can\ngate its own feedback on proof of a real interaction by requiring a\nserver-signed authorization. After settlement we return, in the response body:\n\n```json\n\"feedbackAuth\": {\n  \"struct\": {\n    \"agentId\": \"1234\",\n    \"clientAddress\": \"0x<payer>\",\n    \"indexLimit\": \"1\",\n    \"expiry\": \"1787900000\",\n    \"chainId\": \"8453\",\n    \"identityRegistry\": \"0x<IdentityRegistry>\",\n    \"signerAddress\": \"0x<our operator>\"\n  },\n  \"signature\": \"0x...\",\n  \"encoded\": \"0x...\",            // abi.encode(struct, signature), pass straight through\n  \"reputationRegistry\": \"0x<ReputationRegistry>\"\n}\n```\n\nThe client then calls, from its own wallet, unaided:\n\n```\nReputationRegistry.giveFeedback(\n  agentId, score /*0-100*/, tag1 /*e.g. \"accuracy\"*/, tag2 /*e.g. \"latency\"*/,\n  fileuri /*optional ipfs:// JSON with detail*/, filehash, encodedFeedbackAuth\n)\n```\n\n`indexLimit` caps how many feedback entries that auth unlocks, so one paid call\nbuys exactly one rating. `expiry` bounds it in time. `clientAddress` is bound to\nthe EIP-3009 payer, so the rating can only come from the wallet that actually\npaid.\n\nBecause we sign these unconditionally for every settled call — including the\nones we handled badly — we cannot suppress a bad review by withholding the\nauth. We publish that policy in the agent card (`feedbackPolicy:\n\"unconditional\"`) precisely because a service that *could* withhold auths would\nhave a worthless rating average.\n\nThe auth is re-fetchable at `GET /v1/receipts/:nonce/feedback-auth` for a\nclient that crashed before storing it, and re-issuing is idempotent.\n\n### 4.2 Why other agents can act on it\n\n`giveFeedback` writes an event and updates the aggregate, so the very next\nagent's `getSummary(agentId)` — a plain `eth_call`, no permission, no API key,\nno index we host — reflects the rating. That is the same call as §2.3 step 1:\nthe rating a caller leaves is the signal the next caller reads. The loop closes\nonchain, off our infrastructure.\n\nWe may also `appendResponse` to a rating (a public reply). We can never delete\none; only the rater can revoke their own.\n\n---\n\n## 5. Edge cases, abuse, and honest weak points\n\n**Free-endpoint DoS.** `GET /v1/forecast` with no header is unauthenticated by\ndesign, and generating a 402 is cheap but not free. Rate-limit *unpaid* 402s per\nIP/ASN. We cannot rate-limit by API key — we have none — so paid requests are\ninstead rate-limited per payer address, which is naturally sybil-resistant\nbecause each identity costs $0.35 a call.\n\n**Replay.** Two layers: USDC burns the EIP-3009 nonce onchain, and our receipt\ncache returns the original response for a repeated nonce. Neither alone is\nsufficient — the cache alone is forgeable across instances, the chain alone\nwould let a lost response cost the client twice.\n\n**Settle-after-serve race.** Mitigated by settling *before* the response is\nwritten (§3.3). The residual risk is a settled payment whose response never\nreaches the client; the receipt cache converts that into a free retry.\n\n**Sybil ratings.** `FeedbackAuth` binds a rating to a wallet that paid $0.35, so\ninflating our score costs money and deflating it costs an attacker money too.\nMore importantly `getSummary` accepts a client-address filter, so a discerning\ncaller computes a *web-of-trust-weighted* average rather than the global one.\nWe should expect sophisticated clients to ignore the global number entirely.\n\n**Price changes.** The 402 is a fresh quote each time; there is no subscription\nto grandfather. A client that caches terms and signs a stale `value` gets a 402\nwith the new terms and re-signs. Keep a short grace window accepting the\nprevious price to avoid a thundering re-sign at the moment of change.\n\n**Overpayment.** We accept `value >= price` and settle the signed amount. We do\nnot refund the difference — stated in `/v1/terms` — because refunding would\nrequire us to hold and disburse balances.\n\n**Facilitator censorship.** A facilitator could refuse to settle specific\npayers. Failover to a second facilitator on `settle` failure before returning\n402, and log the discrepancy.\n\n**Our own key compromise** is the sharpest edge: whoever holds the operator key\ncan re-point `tokenURI` at a malicious card and mint feedback auths. Split cold\nowner / hot operator, and monitor `MetadataSet`/`Transfer` events on our own\n`agentId` as an intrusion alarm.\n\n---\n\n## 10.
