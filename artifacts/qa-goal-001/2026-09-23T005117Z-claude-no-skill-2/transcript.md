The headline finding is one I hit by actually running it rather than reading it: **the app 500s on every route, and `yarn next build` fails.** RainbowKit 2.2.9 guards its recent-wallet lookup with `typeof localStorage !== "undefined"`, but Next 16 runs its render workers with Node's Web Storage flag on — so `localStorage` exists server-side without working methods, and `.getItem` throws inside `RainbowKitProvider`. Reproduced on Node 22 and 25, with and without the harness `NODE_OPTIONS`. Fix is a `mounted` gate in `ScaffoldEthAppWithProviders.tsx`, which already computes `mounted` but only uses it to pick a theme.

The other blockers are in `/payouts`:

- **Wrong-chain writes.** Raw `useWriteContract` with hardcoded Base addresses and no `chainId` — a wallet on mainnet sends real transactions to those addresses *on mainnet*. No network guard, no simulation. `useScaffoldWriteContract` does all of this and AGENTS.md mandates it.
- **No validation.** `recipient as \`0x${string}\`` is a cast over free-form text; bad input throws into `catch { console.error(e) }`, so the button visibly does nothing.
- **The feed can never load.** `fromBlock: 0n` overrides the hook's `deployedOnBlock` default (33712450), making it ~67,000 sequential `eth_getLogs` calls against Base's public RPC.
- **Zero transaction feedback**, and **approve/pay is a guessing game** — no allowance check, and the generated USDC ABI has no `allowance` entry to check with.

Two config items worth flagging early because they compound the above: you're on SE-2's shared demo Alchemy key and WalletConnect project ID (S1 — and `wagmiConfig` deliberately demotes Alchemy to last when it detects the default key, so your primary Base RPC is the public endpoint), and `pollingInterval` is set to 30s on a 2-second-block L2 (S2).
