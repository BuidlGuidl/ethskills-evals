# Anonymous DAO voting — how one ballot actually works

The requirement was: the tally is public, nobody (including the DAO) can tell how
any individual member voted. Membership itself stays public — that is a given,
not something to hide.

The shape of the answer: **membership and voting are two different acts, by two
different wallets, linked only by a secret that never leaves the member's
machine.** A member joins once, publicly, from the wallet holding their NFT. Later
they prove — in zero knowledge — that they are *one of* the members who joined,
and that proof is broadcast by a relayer, not by them.

Read [What this does not hide](#what-this-does-not-hide) before you deploy it.
There are three real residual leaks and one of them is not a cryptography
problem.

---

## The pieces

| | |
|---|---|
| `circuits/vote/src/main.nr` | The proof: membership in a Merkle tree + a proposal‑scoped nullifier + a boolean vote. 3,197 ACIR opcodes, ~0.5 s to prove, 8,000‑byte proof. |
| `contracts/src/MemberRegistry.sol` | Incremental Merkle tree of identity commitments, depth 8 (256 seats, DAO has 150). Poseidon. |
| `contracts/src/AnonymousBallot.sol` | Proposals, verification, nullifier bookkeeping, tally. |
| `contracts/src/verifier/HonkVerifier.sol` | Generated by `bb write_solidity_verifier`. Never edit. |
| `contracts/src/MembershipNFT.sol` | Stand‑in for the DAO's existing NFT so the local chain has something to gate on. |
| `scripts/` | Client: `client/` (identity, offchain tree mirror, in‑process prover) plus the four member‑facing commands. |

One hash function throughout: **Poseidon over BN254 with circomlib parameters**,
in the circuit (`poseidon::poseidon::bn254::hash_2`), onchain (`PoseidonT3.hash`)
and in the client (`poseidon-lite`). Three implementations agreeing is an
assumption, not a fact, so it is pinned by test vectors in *both* directions:
`contracts/test/HashParity.t.sol` and `scripts/check-hash-parity.mjs`, both
against values printed by `nargo test --show-output`.

## The flow, one member, one proposal

### Before any transaction — the member's machine

The member generates two random field elements and never sends either anywhere:

```
secret            ← random
nullifierSecret   ← random
commitment        = Poseidon(secret, nullifierSecret)
```

Only `commitment` goes onchain. Both halves are written to `notes/member-N.json`
(gitignored). **Losing that file loses the vote permanently** — see
[Lost notes](#lost-notes).

Two secrets, not one, because every ballot must publish a nullifier. If the
nullifier were derived from the same value as the commitment, publishing it would
identify the leaf and the proof would be decoration.

### TX 1 — join the anonymity set

`MemberRegistry.join(commitment)` — `node scripts/join.mjs 3` — **~375k gas**

The registry checks `membership.balanceOf(msg.sender) > 0`, that this wallet has
not joined before, and that nobody has already published this commitment
(otherwise a bystander could front‑run someone's commitment and lock them out).
It inserts the leaf and emits `MemberJoined(leafIndex, commitment, newRoot)`.

This happens once per member, ever — not once per proposal.

### TX 2 — open a proposal

`AnonymousBallot.createProposal(descriptionHash, votingPeriod)` —
`node scripts/propose.mjs "Fund the grants program with 40 ETH"` — **~128k gas**

Any member may propose. The proposal **pins the registry root as it stands at
this block** and refuses to open if fewer than `minAnonymitySet` members have
joined.

Pinning the root is the point. If ballots were checked against a *moving* root,
the root a ballot proved against would narrow its author down to the members who
had joined by that moment — the early joiners would be nearly deanonymised.
Everyone on a proposal proves against the same root, so the root says nothing.
The cost: members who join later are ineligible for proposals already open, which
is also the behaviour you want.

### Between TX 2 and TX 3 — the member's machine again

1. Replay every `MemberJoined` log into an identical tree offchain
   (`scripts/client/tree.mjs`), truncated to the proposal's snapshot.
2. Check the rebuilt root equals the proposal's `snapshotRoot`. If not, stop —
   a proof against a wrong root is a wasted relayer fee.
3. Find own leaf index by commitment, read out the Merkle path.
4. `nullifierHash = Poseidon(nullifierSecret, proposalId)`.
5. Prove, **in process, via NoirJS + `@aztec/bb.js`** — the same code path that
   runs in a browser. Nothing is shelled out and no witness is uploaded anywhere:
   a member who sends their witness to a proving service has handed that service
   their vote.

There is deliberately no contract call that returns a Merkle path. There could
not be: the path is a function of every other member's commitment, and asking a
server for *your* path tells that server which leaf is about to vote.

### TX 3 — cast the ballot

`AnonymousBallot.castVote(proposalId, nullifierHash, vote, proof)` —
`node scripts/vote.mjs 3 yes` — **~2.51M gas**

**Sent by the relayer, not the member.** `castVote` never reads `msg.sender`;
any wallet may carry any valid ballot. This is the part people skip, and skipping
it destroys everything above: the member's wallet is on the public roster, so a
ballot paid for by that wallet is attributed in one hop, proof or no proof.

The contract rebuilds the public input array in the circuit's `pub` order —
`[snapshotRoot, proposalId, nullifierHash, vote]` — verifies, and only then
records the nullifier and increments the counter. `vote` being a public input is
what stops a relayer flipping a ballot in flight: change it and the proof stops
matching (`test_relayerCannotFlipTheVote`).

A second ballot from the same member collides on `nullifierSpent[proposalId]` and
reverts. Because the nullifier is hashed *with* the proposal id, the same
member's nullifiers on proposals 7 and 8 share nothing — their voting history
cannot be stitched together.

### TX 4 — none. Read the tally.

`AnonymousBallot.result(proposalId)` — `node scripts/tally.mjs` — a `view` call,
no transaction, no permission. It reverts while voting is open so the contract
does not itself serve a live running count. That is a courtesy, not a guarantee
(see below).

## What a chain observer learns, transaction by transaction

Assume the observer has the DAO's public roster and full chain history.

| # | Transaction | Sender | What the observer learns | What they do **not** learn |
|---|---|---|---|---|
| 0 | Deploy + `issue` | DAO admin | The contracts, and the roster of NFT holders. | — (all of this was already public) |
| 1 | `MemberRegistry.join` | **The member's own wallet** | "`0xMember` is now in the anonymity set, at leaf *i*, and the root moved to *R*." | Anything about `secret` or `nullifierSecret`. Nothing that helps link this to a later ballot. |
| 2 | `createProposal` | **A member's own wallet** | Who proposed, the description hash, the snapshot root, the anonymity‑set size, the deadline. | — (proposing is public by design) |
| 3 | `castVote` | **The relayer** — holds no NFT, is on no roster | A ballot was cast on proposal *p*; its direction (in calldata); a nullifier hash; the relayer paid. | *Which member.* The nullifier is unlinkable to any commitment; the root is shared by every ballot; the sender is nobody. |
| 4 | `result` (view) | anyone | Final yes/no/turnout. | Attribution. |

The link the design breaks is between row 1 and row 3. Row 1 is loudly public and
that is fine. Row 3 is anonymous within the set of members who joined before the
snapshot.

## What this does not hide

Being straight about the edges, because two of these are choices you should make
deliberately rather than discover later.

**1. The relayer sees the member.** This is the biggest residual leak and it is
not a cryptography problem. Whoever the member hands their proof to learns their
IP and timing, and therefore how they voted. **If the DAO runs the relayer, the
DAO can deanonymise every vote** — which is exactly the requirement you asked to
meet. Options, roughly in increasing order of seriousness: submit over Tor/VPN;
use a third‑party relayer nobody in the DAO controls; use an ERC‑4337 bundler
with a paymaster; run several independent relayers and let members choose. The
demo here uses a separate anvil account (`RELAYER_INDEX`, default 19) funded by
the deployer — fine for a DAO‑paid‑gas model where the relayer is honest, not
fine if the DAO is in the threat model. **Do not** let a member fund a fresh
burner from their own wallet: that recreates the link on-chain in one hop.

**2. Each ballot's direction is visible as it lands.** `result()` withholds the
running tally, but every ballot's `vote` sits in its own calldata. Anyone
decoding transactions keeps their own running total. This does not attribute — the
property you asked for holds — but do not describe the interim count as secret.
Hiding it too means homomorphic or committed tallying (MACI‑style), which buys
secrecy at the price of a decryption trustee: someone who *can* see individual
votes. That trade is worse against "including us".

**3. Anonymity is bounded by the set, and by timing.** A ballot is "one of *N*
members who joined before the snapshot" — nothing better. `minAnonymitySet`
refuses to open a proposal below a floor (8 in the demo; pick a real number for
150 seats). Timing still correlates: one ballot landing 30 seconds after a member
is known to be online is a hint no proof can erase. Batching, random delays and
a relayer that queues rather than forwards immediately all help.

**4. There is no receipt‑freeness.** A member holds `secret` and
`nullifierSecret`, so they can *prove to a third party* how they voted by
revealing the nullifier preimage. That makes this anonymous but not
coercion‑resistant: it does not stop vote buying, where the buyer asks for proof.
Coercion resistance needs key‑switching (MACI) and is a much bigger system.

**5. Lost notes.**<a id="lost-notes"></a> The registry stores only
`Poseidon(secret, nullifierSecret)`. There is no recovery and deliberately no
re‑join: letting a member add a second leaf would leave the first one in the tree
and hand them two votes on every future proposal. A member who loses their note
is out until a fresh registry is deployed. Real deployments need this said loudly
in the UI, plus an export‑and‑back‑up step.

**6. Trusted setup.** UltraHonk uses a universal KZG SRS (perpetual
powers‑of‑tau) — no per‑circuit ceremony, but not transparent either. If the SRS
were backdoored, proofs could be forged; it could not retroactively deanonymise
past votes.

## Things that break silently, and what pins them

Four invariants have no natural alarm. Each has a test.

| Invariant | If it breaks | Pinned by |
|---|---|---|
| The three Poseidons are the same function | Wrong tree accepted; proofs never verify | `HashParity.t.sol`, `check-hash-parity.mjs` |
| Public input **order** matches across circuit / script / contract | Verification fails with no useful reason | `AnonymousBallotTest`, assertion in `vote.mjs` |
| `HonkVerifier.sol` matches the current circuit | Every ballot reverts | `AnonymousBallotTest` runs a real proof from `contracts/test/fixtures/ballot.json` |
| Tree depth agrees in three places | Roots diverge | Constants cross‑referenced in `main.nr`, `MemberRegistry.sol`, `tree.mjs` |

Whenever the circuit changes, all three of these must be redone or the Solidity
tests will (correctly) fail:

```
npm run circuit     # nargo test && nargo compile
npm run verifier    # bb write_vk --verifier_target evm  →  write_solidity_verifier
npm run fixture     # regenerate the baked proof
```

`verifier_target evm` selects keccak transcripts **with** zero knowledge. Proof,
verification key and onchain verifier must all agree on that setting; mismatched,
verification fails with nothing useful in the error.

## Running it

```bash
npm install
npm run build                 # nargo test + compile, forge build
npm test                      # 13 Solidity tests, incl. a real proof through the real verifier

anvil                         # terminal 1
npm run deploy                # terminal 2
npm run demo                  # 12 joins, a proposal, 6 anonymous ballots, the tally
```

`npm run demo` prints the flow above end to end. The last run:
12 members joined, 6 ballots relayed from one non‑member wallet, **YES 4 / NO 2,
turnout 6 of 12** — and nothing onchain says which four.

Individual steps:

```bash
node scripts/join.mjs 3                    # member 3 joins, from member 3's wallet
node scripts/propose.mjs "text" 3600       # a member opens a proposal
node scripts/vote.mjs 3 yes                # member 3 proves; the RELAYER sends
node scripts/tally.mjs                     # anyone, after the deadline
```

## Open questions for you

1. **Who runs the relayer?** The honest answer decides whether this meets your
   requirement. A DAO‑run relayer does not.
2. **What is `minAnonymitySet` for 150 seats?** The demo uses 8. It should be
   high enough that "one of *N*" is genuinely uninformative for a contested vote,
   and low enough that you can actually open a proposal.
3. **Is receipt‑freeness in scope?** If members might be paid for their votes,
   this design is not enough and the answer is a much larger system.
4. **Depth 8 caps the registry at 256 members.** Comfortable at 150; if you
   expect to pass that, raise it now — it means a new circuit, a new verifier and
   a migrated registry.
