# Anonymous DAO voting: how it works

Membership is public, and it stays public. What we hide is the link between a
member and their ballot. We do that by splitting a member's activity into two
kinds of transaction that nothing onchain ties together:

| | Sent by | Links to member? |
|---|---|---|
| **Join** (`register`), once ever | the member's NFT wallet | yes, on purpose: "token #7 joined" |
| **Vote** (`castVote`), once per proposal | a **relayer** wallet | no. A ZK proof stands in for the signature |

When a member joins, they publish a Poseidon *commitment* to two random secrets
(their "note"). To vote, they prove in zero knowledge that they know the secrets
behind *one of* the commitments in the proposal's member tree. They also publish
a *nullifier hash* derived from their secret and the proposal. The nullifier stops
a second vote on the same proposal, but it can't be traced back to any commitment
or to that member's nullifiers on other proposals.

```
circuits/vote/src/main.nr          Noir circuit (+ nargo tests)
contracts/src/AnonVoting.sol       registry tree, proposals, nullifiers, tally
contracts/src/verifiers/HonkVerifier.sol   generated by bb (ZK UltraHonk, keccak)
contracts/src/MembershipNFT.sol    stand-in NFT for local chains only
contracts/script/Deploy.s.sol      deploy + wire everything
contracts/test/AnonVoting.t.sol    16 tests against the real verifier + a real proof
scripts/register.mjs               member joins (NFT wallet)
scripts/propose.mjs                open a proposal
scripts/vote.mjs                   note → tree → local proof → relayer   (no private key)
scripts/relayer.mjs                submits castVote from its own wallet
scripts/tally.mjs                  read + recount the result
scripts/demo-local.sh              whole flow on a fresh anvil
```

## End-to-end: one member, one proposal

Cast: **Bob** is a member holding membership NFT #2 in his public wallet
`0xB0b…`. **Alice** is another member. The **relayer** is any wallet with ETH
that isn't Bob's (the DAO can run one, and so can any member or third party).

### 0. Deploy (once): sent by the deployer wallet

`forge script script/Deploy.s.sol` deploys PoseidonT3 and LeanIMT (linked
libraries), `HonkVerifier`, and then `AnonVoting(membershipNFT, verifier, minAnonymitySet)`.
Locally it also deploys `MembershipNFT`. In production, set `MEMBERSHIP_NFT`.

**Observer learns:** the contract addresses, the circuit (through the verifier's
verification key), which NFT defines membership, and the minimum anonymity set.
`AnonVoting` has **no owner and no admin functions**. Nobody can change roots,
tallies or the verifier after deployment.

### 1. Join: `register(tokenId, commitment)`, sent by Bob's NFT wallet `0xB0b…`

Offchain first: `register.mjs` generates two random 248-bit field elements,
`identityNullifier` and `identityTrapdoor`, and computes
`commitment = Poseidon(1, Poseidon(identityNullifier, identityTrapdoor))`. It
saves all of this to `.notes/member-2.json` on Bob's machine.

Onchain, the contract checks `ownerOf(2) == msg.sender`, checks that token #2
hasn't registered yet, inserts the commitment into a LeanIMT, and emits
`MemberRegistered(2, leafIndex, commitment, newRoot)`.

**Observer learns:** `0xB0b…`, holding token #2, joined the voter set. They see
its commitment and leaf position, and the new root. That was already public
membership information. It also lets anyone audit that every leaf belongs to a
legitimate token on the public registry. **Not learned:** the secrets. The
commitment is a hiding Poseidon hash of ~496 random bits.

Bob does this **once**. The same note works for every future proposal. The tree
is the anonymity set, so all 150 members should register early, well before
contested votes.

### 2. Open a proposal: `createProposal(descriptionHash, votingPeriod)`, sent by Alice's wallet (any NFT holder)

The contract freezes the **current member root** into the proposal as
`snapshotRoot`. It also derives
`scope = keccak256(chainid, address(this), proposalId) mod p`, the proposal's
"external nullifier". It refuses to open the proposal while fewer than
`minAnonymitySet` members are registered.

**Observer learns:** Alice proposed it. They see the description hash, the
deadline, and the snapshot root, which tells them exactly which registered
tokens are eligible (the anonymity set for this vote). Members who register
later can't vote on this proposal.

### 3. Prepare the ballot: no transaction (Bob's machine, `vote.mjs`)

1. It reads `getProposal(id)` and the public tree events. These reads are the
   same for every member and reveal nothing about Bob to the RPC provider. The
   script deliberately **doesn't** query `nullifierUsed(…)`, because that would
   put Bob's IP next to his nullifier at the RPC node.
2. It replays `MemberRegistered/Rotated/Evicted` in log order until the local
   tree's root equals `snapshotRoot`, then takes Bob's Merkle path.
3. It computes `nullifierHash = Poseidon(Poseidon(2, scope), identityNullifier)`.
4. It **generates the proof locally** with NoirJS and bb.js (about 1 s). The
   public inputs are `[snapshotRoot, scope, nullifierHash, vote]`. The private
   inputs are the note and the path. The proof uses bb's `evm` target: keccak
   transcript **with zero knowledge**. A non-ZK Honk proof isn't
   witness-hiding, so it must not be used here.
5. It POSTs `{proposalId, support, nullifierHash, proof}` to a relayer. The
   script holds **no private key**.

The circuit checks that `vote ∈ {0,1}`, that the commitment is in the tree
under `snapshotRoot`, and that the nullifier hash is the correct one for this
secret and scope. The vote and scope are public inputs, so the relayer (or a
mempool front-runner) **can't change Bob's choice or move the proof to another
proposal**. It can only submit the proof unchanged or drop it.

### 4. Vote: `castVote(proposalId, support, nullifierHash, proof)`, sent by the relayer's wallet

The relayer simulates the call first, so bad proofs and double votes cost it
nothing. It can wait a random delay (`RELAY_MAX_DELAY_MS`), then broadcast from
its own wallet. The contract checks the deadline, checks that
`0 < nullifierHash < p` (which blocks the `x` vs `x+p` aliasing double vote),
checks that the nullifier is unused, and calls the verifier. Only after that
does it mark the nullifier as used, increment the yes or no count, and emit
`VoteCast(id, nullifierHash, support)`. `msg.sender` is never read.

**Observer learns:** *some eligible member* voted yes (or no) on this proposal
at this time, and the relayer paid the gas. **Not learned:** which member. The
proof is zero knowledge over the whole snapshot set. The nullifier hash is a
hash of Bob's secret and so can't be linked to his commitment. It also differs
for every proposal, so nobody can link Bob's ballots across proposals to build
a voting profile.

A second attempt from Bob's note produces the same nullifier hash, and the
contract rejects it with `AlreadyVoted`.

### 5. Tally: no transaction

After the deadline, anyone calls `result(id)`, which returns `(yes, no, passed)`.
`tally.mjs` also recounts from the `VoteCast` events. No wallet is needed.

## What the privacy guarantee rests on

"Nobody, including the DAO operators, can tell how a member voted" holds if the
following are true. Most of them are operational, not cryptographic.

1. **The vote is never sent from a wallet linked to the member.** That rules out
   the NFT wallet, and also a "fresh" wallet funded from it or from the member's
   exchange account. Use a relayer. The contract is permissionless on purpose,
   so anyone can relay.
2. **Network metadata.** A relayer, including one we run, sees the IP address
   that submitted each proof. The payload contains nothing identifying, but
   IP + timing could be enough. To hold against *us*, members should reach the
   relayer over **Tor**. Several independent relayers are also better than one.
   `relayer.mjs` doesn't log requests, but members shouldn't have to trust that.
3. **Timing.** Every vote transaction is public with its yes/no. If Bob says in
   chat "just voted!" and one `VoteCast` lands a minute later, his vote is
   exposed. The relayer's random delay helps. Batching near the deadline helps
   more.
4. **The note never leaves the member's machine.** Anyone holding the note can
   compute Bob's nullifier for every proposal and read off his entire voting
   history. So proofs are generated **locally**, never on a hosted prover. And
   if the DAO ships a web frontend, it is trusted code that could exfiltrate
   notes. To hold against us, members should run the open-source client (these
   scripts) or a pinned, reproducible build.
5. **Anonymity set size.** Each vote hides among the tokens registered at
   snapshot time, not among all 150 members. Set `minAnonymitySet` high in
   production (the local default is 3).

### Inherent limits (any system that publishes a tally has these)

- **Lopsided results reveal votes.** A 150–0 result tells you how every voter
  voted. The tally and turnout are public by requirement.
- **The running tally is visible before the deadline.** Each `VoteCast` shows
  yes/no, and storage is public, so `result()` gating the tally until the
  deadline is only a convenience. That isn't attribution, but it enables
  strategic late voting and makes timing correlation (point 3) sharper. To fix
  it you need encrypted ballots, for example timelock encryption to the
  deadline with a proven decryption, or a threshold key held by several
  members. MACI-style coordinators can decrypt every ballot, which conflicts
  with "including us". I left this out of the core.
- **No receipt-freeness.** Bob *can* prove how he voted by revealing his note,
  so vote-buying and coercion aren't prevented. Fixing this needs a MACI-style
  key-change design, which brings back a trusted coordinator.
- **Membership integrity isn't hidden, and shouldn't be.** Whoever controls the
  NFT can mint extra members. Because `register` is per-token and public,
  anyone can check registered tokens against the published registry.

### Membership changes

- **The NFT is transferred:** the new holder calls
  `rotate(tokenId, newCommitment, siblings)`, which replaces the old leaf.
  Proposals that are already open keep their snapshot, so the old holder can
  still vote on those, but the new holder can't. That keeps one vote per token
  per proposal. Future proposals only include the new commitment.
- **The NFT is burned (member removed):** anyone can call `evict(tokenId, siblings)`.
- **Lost or leaked note:** the holder calls `rotate`. A leaked note exposes
  **past** votes, and rotating doesn't undo that.

The tree ops emit events with the leaf index, and the client mirror replays
them.

## Implementation notes

- **Hash parity:** the circuit (`poseidon::bn254::hash_2`, noir-lang/poseidon
  v0.3.0), the onchain tree (`poseidon-solidity` PoseidonT3), and the JS mirror
  (`poseidon-lite` `poseidon2`) are all circomlib Poseidon. The vector
  `H(1,2) = 0x115c…189a` is asserted in both `nargo test` and `forge test`. The
  JS mirror also checks its root against every event's emitted root.
- **Public input order** is `merkle_root, scope, nullifier_hash, vote`, the same
  in `main.nr`, `AnonVoting._publicInputs`, and the checks in `vote.mjs`.
- **Tree:** LeanIMT (variable depth). The circuit supports depth up to 16
  (65,536 members) and takes the actual depth as a private input.
- **Setup:** UltraHonk uses a universal SRS, so there's no per-circuit
  ceremony. If the circuit changes, rerun `npm run circuit` (which regenerates
  the verifier) and regenerate the test fixture.
- **Gas** (forge gas report): `register` ~155k, `createProposal` ~154k, a
  successful `castVote` ~2.67M, almost all of it proof verification. Budget
  relayer ETH for about 150 × 2.7M gas per proposal.
- **Versions:** nargo 1.0.0-rc.2, bb 5.2.0, `@aztec/bb.js` 5.2.0 (it must match
  `bb`), `@noir-lang/noir_js` 1.0.0-rc.2, solc 0.8.27 with the `cancun` EVM.

## Running it

```bash
npm install                     # JS deps + Solidity deps (forge-std, lean-imt, poseidon)
npm run circuit                 # nargo test/compile → vk → HonkVerifier.sol + scripts/artifacts/vote.json
(cd contracts && forge build && forge test)
bash scripts/demo-local.sh      # fresh anvil on :8555: deploy, 3 joins, proposal, 3 relayed votes,
                                # a rejected double vote, time warp, tally
```

To run it by hand against your own node, set `RPC_URL`. Deploy with
`forge script script/Deploy.s.sol --rpc-url $RPC_URL --private-key … --broadcast`
from `contracts/`. That writes `contracts/deployments/<chainId>.json`, which
the Node scripts read. Then:

```bash
MEMBER_KEY=… TOKEN_ID=2 node scripts/register.mjs
PROPOSER_KEY=… DESCRIPTION="…" VOTING_PERIOD=86400 node scripts/propose.mjs
RELAYER_KEY=… RELAY_MAX_DELAY_MS=60000 node scripts/relayer.mjs      # separate machine / party
NOTE=.notes/member-2.json PROPOSAL_ID=0 SUPPORT=yes RELAYER_URL=… node scripts/vote.mjs
PROPOSAL_ID=0 node scripts/tally.mjs
```

`.notes/` holds ballot keys and is git-ignored. Back it up privately.
