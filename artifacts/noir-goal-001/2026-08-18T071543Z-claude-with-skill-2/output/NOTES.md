# Anonymous DAO voting — end-to-end

150 public members, public yes/no tallies, and no way for anyone — including
the DAO — to say how any one member voted.

The whole design is one idea: **the wallet that proves membership is never the
wallet that casts a ballot, and nothing onchain connects them.** A member
registers a commitment once from their known wallet, and from then on votes by
proving in zero knowledge that *some* leaf of the member tree is theirs, without
saying which.

---

## 1. The pieces

| Piece | Where | Role |
| --- | --- | --- |
| `dao_vote` circuit | `circuits/vote/src/main.nr` | proves membership + nullifier + ballot in one proof |
| `HonkVerifier` | `src/verifiers/HonkVerifier.sol` | generated by `bb write_solidity_verifier`; deployed standalone |
| `MembershipRegistry` | `src/MembershipRegistry.sol` | NFT-gated commitment tree (LeanIMT / Poseidon) — the anonymity set |
| `AnonymousVoting` | `src/AnonymousVoting.sol` | proposals, proof verification, nullifiers, tally |
| `DemoMembershipNFT` | `src/DemoMembershipNFT.sol` | local stand-in for the DAO's real NFT |
| LeanIMT + PoseidonT3 | `vendor/` | vendored Solidity deps — see `vendor/README.md` |
| deploy | `script/Deploy.s.sol` | deploys all four and wires them |
| client | `client/vote.mjs` | secret → identity → proof → vote transaction |

Wiring: `AnonymousVoting` holds the addresses of `HonkVerifier` and
`MembershipRegistry`; `MembershipRegistry` holds the address of the membership
NFT. Nothing points back the other way.

## 2. One member, one proposal, start to finish

Two wallets belong to the member's story and they must never meet:

- **M** — the member's public wallet, the one holding the membership NFT.
- **R** — a relayer (or a burner the DAO cannot tie to M). Sends the ballot.

Plus **D**, the DAO's deployer wallet, and **P**, the proposer's wallet (some
member's public wallet — possibly M's, and that is fine).

### tx 1 — deploy (once, wallet D)

`DemoMembershipNFT` → `HonkVerifier` → `MembershipRegistry(nft)` →
`AnonymousVoting(verifier, registry, daoScopeSeed)`.

*Observer learns:* the addresses and code of four contracts, and that D deployed
them. `daoScopeSeed = keccak256(chainid, registry, "dao-anonymous-voting/v1")`,
which makes every nullifier unique to this deployment.

### step 2 — derive the identity (wallet M, **no transaction**)

M signs the fixed string `dao-anonymous-voting/identity/v1`. That signature seeds
two field elements:

```
identityNullifier, identitySecret   ← keccak(signature) → Poseidon
commitment = Poseidon(1, Poseidon(identityNullifier, identitySecret))
```

ECDSA signing in ethers is deterministic, so the identity is reproducible from
M's key alone — there is no note file to lose. See §5 for the cost of that.

*Observer learns:* nothing. Nothing is sent.

### tx 2 — join the anonymity set (**wallet M**)

`MembershipRegistry.join(tokenId, commitment)`

Checks `ownerOf(tokenId) == msg.sender` and that this token has never joined,
then inserts `commitment` as a leaf and emits
`MemberJoined(commitment, leafIndex, root)`.

*Observer learns:* **that M, holder of membership token #t, registered
commitment C at leaf i, and the new tree root.** This is a permanent public link
between M and C — and it is harmless: C is a Poseidon hash of two secrets that
never left M's machine, and no later transaction ever mentions C.

Registration is keyed on the **token**, not the wallet. Gating on the wallet
would let a member hand their NFT to a second address of their own, join twice
and vote twice (`test_revert_transferringTheNftDoesNotBuyASecondLeaf`).

Every member does this once, ever — not once per proposal.

### tx 3 — open a proposal (**wallet P**, any NFT holder)

`AnonymousVoting.createProposal(description, votingPeriod)`

Snapshots `registry.root()` and the member count, sets a deadline, and derives
`scope = keccak256(daoScopeSeed, proposalId) >> 8`.

*Observer learns:* who proposed, the text, the deadline, the exact anonymity set
(root + member count) the ballots will be drawn from. Nothing about anyone's
intent.

The snapshot matters both ways: members who join later cannot vote on this
proposal, and members who join later cannot invalidate a proof already being
generated (`test_lateJoinerDoesNotDisturbAnOpenProposal`).

### step 4 — build the proof (**wallet M's machine, no transaction**)

The client replays `MemberJoined` logs into an identical LeanIMT **and stops the
moment the root equals the proposal's snapshot root** — so it proves against the
tree the proposal actually recorded, not today's. It reads its own `leafIndex`
from the events, derives siblings, and runs the circuit:

```
private: identityNullifier, identitySecret, merkle_depth, indices, siblings
public:  merkle_root, proposal_id (= scope), nullifier_hash, vote
```

The circuit asserts the commitment is in the tree, that
`nullifier_hash = Poseidon(Poseidon(2, scope), identityNullifier)`, and that
`vote ∈ {0,1}`.

*Observer learns:* nothing. This is a local computation, ~10–30 s.

### tx 4 — cast the ballot (**wallet R — never M**)

`AnonymousVoting.castVote(proposalId, nullifierHash, support, proof)`

Rejects a spent nullifier and a passed deadline, builds the four public inputs in
circuit order, calls `HonkVerifier.verify`, and only then records the nullifier
and bumps a counter. ~2.6M gas.

*Observer learns:*
- someone holds a valid proof against the snapshot root — i.e. **one of the 150
  snapshotted members** voted;
- the ballot: yes or no;
- one nullifier hash is now spent;
- `msg.sender` is R.

That is the whole disclosure. The nullifier is `Poseidon(Poseidon(2, scope),
identityNullifier)` — it is not derivable from the commitment C, and the same
member's nullifier on proposal 7 has no visible relationship to their nullifier
on proposal 8. So an observer can neither pick the member out of the 150 nor
build up a voting history across proposals.

Because the ballot is a public input of the proof, a relayer can only forward it
or drop it — flipping yes to no invalidates the proof
(`test_revert_relayerCannotFlipTheBallot`).

### step 5 — read the tally (**anyone, view call, no transaction**)

`AnonymousVoting.tally(proposalId)` → `(yes, no, eligibleMembers, passed)`,
readable once the deadline has passed.

*Observer learns:* the counts, and how large the eligible set was. Not who was
in the yes column.

## 3. Why the link cannot be made

| Attempt | Why it fails |
| --- | --- |
| Match `castVote` sender to a member | The sender is R; the contract never looks at `msg.sender`. |
| Match the nullifier back to a commitment | Different Poseidon domains (2 vs 1) over disjoint inputs; inverting Poseidon or brute-forcing a 254-bit secret is the attack cost. |
| Match one member's nullifiers across proposals | Each is hashed under a per-proposal, per-deployment `scope`. |
| Replay a proof onto another proposal | The scope is a public input, so the proof and the nullifier are both bound to one proposal (`test_revert_proofIsNotReplayableOnAnotherProposal`). |
| Narrow it down by leaf position | `leafIndex`, `indices` and `siblings` are private inputs; only the root is public. |
| Guess the ballot from its hash | The ballot isn't hashed — it's public by design. Anonymity comes from unlinkability, not from hiding the value. |
| Ask the DAO | The DAO has the same data as everyone else. There is no admin key, no decryption key, no escrow. |

---

## 4. What the contracts cannot enforce — and you must

The circuit is the easy half. These will de-anonymise members regardless of how
correct the proof is:

1. **Never let M send `castVote`.** The client refuses if member and relayer are
   the same key, but nothing onchain can stop a member doing it by hand.
2. **R's gas must not come from M.** A burner funded by M's wallet is M. Use a
   DAO-independent relayer, an ERC-4337 paymaster, or an already-mixed wallet.
3. **Timing.** With 150 members and a 3-day window, one ballot arriving 4 seconds
   after M's laptop wakes up is a signal. Encourage a wide submission window; a
   relayer that batches ballots is better still.
4. **The network layer.** Same IP for `join` and `castVote`, or a single RPC
   provider seeing both, defeats everything above.
5. **Anonymity set size.** 1-of-150 is the ceiling here, and only if all 150 join.
   `snapshotMemberCount` on every proposal makes the real number auditable — if a
   proposal snapshots 6 members, its ballots are 1-in-6.

## 5. Known limits (deliberate, not oversights)

- **Not receipt-free.** A member can prove *to a third party* how they voted, by
  revealing `identityNullifier` and pointing at the nullifier they spent. Enough
  against surveillance; not enough against a briber or a coercive employer. That
  needs MACI-style encrypted ballots with a re-voting window and a coordinator.
- **The running tally is public.** Ballots are plaintext, so the yes/no split is
  derivable from `VoteCast` events before the deadline. `tally()` gates on the
  deadline, but do not read that as secrecy — it is not. Hiding intermediate
  counts requires homomorphic tallying, which is a different system.
- **Identity is derived from a wallet signature.** No backup file to lose, but
  anything that tricks a member into signing
  `dao-anonymous-voting/identity/v1` can recompute their identity and
  de-anonymise every vote they have ever cast. `MEMBER_SECRET` switches to a
  passphrase identity for members who would rather not take that trade.
- **No key rotation.** Lose the identity secret and that membership token's leaf
  is dead — the token cannot re-join. Recovery needs a nullify-and-reinsert
  path with an admin, which is a governance decision, not a technical one.
- **`MAX_DEPTH = 16`** — 65 536 members. Growing past that needs a recompiled
  circuit *and* a redeployed verifier; existing proofs would not carry over.
- **Proposal creation is open to any NFT holder.** No spam control, no quorum,
  no execution of passed proposals. Out of scope here.
- **Verifier gas** is ~2.6M per ballot. On mainnet at scale, batch through a
  relayer or move to an L2.

## 6. Running it

```bash
./scripts/setup.sh                  # forge install + npm install + forge build
./scripts/build-circuit.sh          # nargo compile + nargo test + regenerate HonkVerifier
forge test                          # 16 tests, real proofs against the real verifier

anvil                               # terminal 1
./scripts/deploy-local.sh           # writes deployments/31337.json
node client/demo.mjs                # 8 members join, one opens a proposal
npm run vote                        # one member casts an anonymous ballot
node client/demo.mjs tally 0        # fast-forward past the deadline, read the result
```

`npm run fixtures` regenerates the real proofs in `test/fixtures/` — required
after any change to the circuit, the scope derivation, or the identity
derivation.

**If you change `circuits/vote/src/main.nr`, you must rerun
`./scripts/build-circuit.sh` *and* `npm run fixtures` *and* redeploy the
verifier.** The verifier embeds a hash of the circuit's verification key; a
stale verifier rejects every proof.

### Hash parity

Three Poseidon implementations have to agree bit for bit — `hash_2` in the
circuit, `poseidon2` from `poseidon-lite` in the client, `PoseidonT3` onchain.
Each asserts the same anchor value (`Poseidon(1,2)`), in
`circuits/vote/src/main.nr::poseidon_parity_anchor`, `client/make-fixtures.mjs`
and `test/HashParity.t.sol`. `test_offchainAndOnchainTreesAgree` then checks the
whole tree, not just one hash.
