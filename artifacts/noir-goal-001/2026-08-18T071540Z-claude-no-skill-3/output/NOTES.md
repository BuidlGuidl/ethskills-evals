# Anonymous DAO voting — how one vote works, end to end

The requirement driving every decision here: **nobody, including the DAO
operators, should be able to tell how any individual member voted.**

Membership is public and stays public. What this system breaks is the link
between *a member* and *a vote*.

---

## 1. The idea in one paragraph

Each member registers a **commitment** to a secret, once, from their
NFT-holding wallet. Those commitments form an on-chain Merkle tree. To vote, a
member proves in zero knowledge: *"I know the secret behind one of the leaves in
this tree, and I am voting X on proposal N"* — without revealing which leaf. The
proof also publishes a **nullifier**, `keccak(2, secret, proposalId)`, which is
deterministic per member per proposal, so the contract can reject a second vote
without learning whose it is. The proof is valid no matter who submits it, so it
is submitted by a wallet that is **not** the member's.

Two separate things have to hold, and both are load-bearing:

| | Broken by | Fixed by |
|---|---|---|
| The vote data must not name the member | putting an address or index in calldata | ZK membership proof + nullifier |
| The vote *transaction* must not name the member | member paying gas from their own wallet | submission by a relayer / unlinked key |

Skipping the second is the usual way these systems leak. A perfect circuit does
nothing if `tx.from` is the member's well-known wallet.

## 2. Pieces

| Component | Where | Role |
|---|---|---|
| `vote` circuit | `circuits/vote/src/main.nr` | Proves membership + binds the vote, hides which member |
| `HonkVerifier` | `contracts/src/verifier/` | Generated by `bb write_solidity_verifier -t evm` |
| `MembershipNFT` | `contracts/src/` | Stand-in for the DAO's existing NFT (delete in production) |
| `MemberRegistry` | `contracts/src/` | NFT-gated append-only Merkle tree of commitments |
| `PrivateBallot` | `contracts/src/` | Proposals, proof checking, nullifiers, tally |

All three implementations of the hash — Noir, Solidity, JS — are pinned to the
same vectors by tests (`nargo test`, `forge test`). A drift would silently make
every proof unverifiable, so it is asserted rather than assumed.

## 3. The flow for one member, one proposal

Wallets in play, deliberately disjoint:

- **`ADMIN`** — DAO operator. Deploys, mints NFTs, opens proposals.
- **`MEMBER`** — holds membership NFT #42. Sends exactly one transaction, ever.
- **`RELAYER`** — a throwaway/service key. Holds no NFT, never registered.

### TX 1 — `MembershipNFT.mint` · sent by `ADMIN`

Pre-existing in the real DAO; here it is part of deploy.

> **Observer learns:** wallet `0xF0fa…3C1` is a DAO member. Already public.

### TX 2 — `MemberRegistry.register(tokenId, commitment)` · sent by `MEMBER`

Once per member, ever — not per proposal. Before sending, offline:

```
secret     = keccak(signature over a fixed message) >> 8      # never transmitted
commitment = keccak(1, secret, 0) >> 8                        # published below
```

The secret is derived from a deterministic wallet signature, so it is
reproducible on any device and never has to be stored anywhere.

> **Observer learns:** member `0xF0fa…3C1` joined the anonymous voter set, and
> their commitment `0x0095e8…edb`. The commitment is a keccak digest of a secret
> they never disclose — it is not linkable to any later nullifier.
>
> **Deliberately attributable.** It says "this member can vote", which the DAO
> already publishes. It says nothing about *any* future vote, on this or any
> other proposal.

### TX 3 — `PrivateBallot.createProposal(description, period)` · sent by `ADMIN`

Snapshots `registry.root()` into the proposal.

> **Observer learns:** a proposal exists, its text, its deadline, the member root
> and the anonymity-set size (150). Nothing about anyone's intent.

Two guards live here:

- **Root snapshot** — members who register later cannot vote on this proposal.
  Nobody, admin included, can grow or reshape the tree underneath a voter after
  they have reasoned about their anonymity set.
- **`minAnonymitySet`** — a proposal cannot open against a member set too small
  to hide in. A "private" ballot with three registered members is not private.

### Offline — no transaction, nothing observable

The member, on their own machine:

1. Reads every commitment from the registry and **rebuilds the tree locally**,
   checking it against `registry.root()`. If the root did not follow from the
   registered commitments, the client refuses to vote. This is what stops the DAO
   from serving a root whose leaves it controls — which would shrink the
   anonymity set to one and deanonymise the voter.
2. Finds its own leaf index and Merkle path.
3. Computes `nullifier = keccak(2, secret, proposalId) >> 8`.
4. Generates the proof (~2.5 s, 9,536 bytes).

Public inputs: `root`, `proposalId`, `nullifier`, `vote`.
Private witness: `secret`, Merkle path, leaf index — these never leave the machine
and are not recoverable from the proof (the `evm` target is the ZK one).

### TX 4 — `PrivateBallot.castVote(proposalId, nullifier, support, proof)` · sent by `RELAYER`

The member hands the proof to a relayer over any off-chain channel. **`MEMBER`
sends nothing and pays nothing**; its nonce is unchanged from TX 2. `castVote`
never reads `msg.sender` — anyone may submit any valid proof.

> **Observer learns:**
> - Someone among the 150 members in the snapshotted root voted. Which one:
>   **unknown** — the proof reveals nothing beyond the four public inputs.
> - The nullifier `0x00c714…afa`. Unlinkable to the member's commitment without
>   the secret, and different on every other proposal, so votes cannot be joined
>   across proposals into a voting history.
> - **The `support` bit of this vote.** It is in calldata; see §5.
> - That `RELAYER` paid ~2.78M gas. `RELAYER` is not a member.

### Read — `PrivateBallot.tally(proposalId)` · no transaction

Reverts until the deadline, then returns `(yes, no)` to anyone.

### Summary

| # | Call | Sender | What a chain observer learns |
|---|---|---|---|
| 1 | `mint` | `ADMIN` | This wallet is a member (already public) |
| 2 | `register` | `MEMBER` | This member joined the voter set + their commitment. **Nothing about their vote** |
| 3 | `createProposal` | `ADMIN` | Proposal text, deadline, member root, anonymity-set size |
| — | *proof generation* | *nobody* | *Nothing — fully offline* |
| 4 | `castVote` | `RELAYER` | One of 150 members voted; the nullifier; that vote's yes/no bit. **Not who** |
| — | `tally` | *nobody* | Final counts after the deadline |

## 4. Why the guarantee holds

- **Vote → member is severed.** The only member-derived value on-chain at vote
  time is the nullifier, a keccak digest of an undisclosed secret. Linking it to
  a commitment means inverting keccak.
- **Sender → member is severed.** The submitting wallet is not the member's, and
  the contract ignores `msg.sender` entirely.
- **One member, one vote survives anyway.** The nullifier is deterministic in
  `(secret, proposalId)`, so a second vote is rejected — without ever learning
  which member was blocked.
- **Cross-proposal linkage is severed.** The proposal id is inside the nullifier
  hash, so the same member produces unrelated nullifiers on every proposal. No
  voting history accumulates.
- **The DAO has no special power.** It cannot forge a root (the tree is built
  on-chain from NFT-gated registrations and every client re-derives it), cannot
  decrypt anything (there is no key), and cannot alter a vote in flight (`support`
  is a public input, so changing it invalidates the proof — tested).

## 5. What is still visible — read this part

Honest limits. None of these reveal *who* voted, but they are real.

1. **Each vote's yes/no bit is public as it lands.** The contract must add votes
   up, and the chain is public, so `support` sits in calldata. Observers see an
   unattributed stream of yes/no over time.
   *Hiding this too requires homomorphic tallying with threshold decryption —
   which reintroduces a committee that could decrypt individual votes. That is
   exactly the trust the DAO asked to avoid, so the bit is left visible and the
   anonymity is placed entirely in the submission path.*
   Practical consequence: **anonymity now rests on the sender being unlinkable.**
   If a member relays their own vote from a wallet traceable to them, that single
   slip reveals their vote, because the bit is right there. This is the one thing
   to get right operationally.

2. **Turnout is visible while voting is open**, and if turnout is very low the
   tally is close to revealing individual choices — with turnout 1, the tally
   *is* that person's vote. Still not attributable to a *person*, but worth
   knowing. Long voting windows and batched submission help.

3. **The relayer sees the vote it carries** (not who wrote it) and could censor
   by choice. Mitigation: anyone can relay, so a censored member can submit
   through another relayer or a fresh key. Use several independent relayers.

4. **Funding graph.** If the throwaway key is funded directly from the member's
   main wallet, that funding transaction re-links them. Use a real relayer that
   pays its own gas, or a key funded through something that breaks the graph.
   This is the most likely way to get this wrong in practice.

5. **Network metadata.** The RPC endpoint sees the submitter's IP and the
   proof-request timing. Submit over Tor/VPN, or through a relayer.

6. **Timing correlation.** A member who registers, then votes 30 seconds later
   through "their" relayer, is correlatable. Random delays and batching help.

7. **The anonymity set is the members who *registered*,** not all 150. If only
   20 register, the set is 20. `minAnonymitySet` enforces a floor; the real fix
   is getting everyone registered before the first contested vote.

8. **Trusted setup / verifier.** The verifier is generated from the circuit by
   `bb`. Anyone should be able to rebuild it and diff against what is deployed —
   `npm run circuit:build && npm run circuit:verifier` is deterministic.

## 6. Running it

```bash
npm run setup                  # npm install + forge install (forge-std)
npm run circuit:build          # compile circuit + verification key
npm run circuit:verifier       # regenerate HonkVerifier.sol
npm run build                  # forge build
npm run test                   # 24 tests, incl. a real proof verified on-chain
npm run circuit:test           # Noir hash/Merkle vectors

./scripts/e2e.sh               # whole thing on a throwaway anvil
```

Step by step against a running chain:

```bash
npm run chain                  # terminal 1: anvil
npm run deploy                 # deploy + wire + mint 150 NFTs
npm run register               # 150 members join, each from their own wallet
npm run propose                # ADMIN opens a proposal
MEMBER=42 SUPPORT=yes npm run vote   # secret -> proof -> relayed transaction
npm run tally                  # result, after the deadline
```

`scripts/vote.mjs` is the member-side reference (shared helpers in
`scripts/common/`): it prints each of the five
steps, and which wallet does what. The CLI prover (`nargo` + `bb`) stands in for
`@noir-lang/noir_js` + `@aztec/bb.js`, which run the same circuit in a browser
with identical inputs and proof bytes.

## 7. Before production

- Point `MemberRegistry` at the real membership NFT and delete `MembershipNFT.sol`.
- Run at least two independent relayers; publish how to reach them, and let
  members submit directly from a fresh key as a fallback.
- Raise tree depth if membership may exceed 256 (`DEPTH` in the circuit, the
  registry, and `crypto.mjs` must move together).
- Have several people independently regenerate `HonkVerifier.sol` from the
  circuit and diff it against the deployed bytecode.
- Decide the deregistration story: today a commitment is permanent, so a member
  who leaves the DAO keeps the ability to vote. Fixing that needs either a
  nullifier-per-epoch scheme or a rebuildable tree with removals.
- Consider gas: ~2.78M per vote. On mainnet that is the main cost driver, and a
  reason to run this on an L2.
