# Anonymous DAO voting — how it works

The goal is that a vote is counted without anyone being able to tell which member cast it. Membership stays public (the NFT and the registry), each vote's direction is public, and the tally is public. The only thing hidden is **which member cast which vote**. That includes the DAO operators, the relayer and the RPC provider.

Here's how:

- **Registration.** Each member registers a Poseidon commitment to a secret note, once per NFT (not once per proposal). The commitments form an onchain Merkle tree (LeanIMT).
- **Snapshot.** When a proposal is opened, the contract stores a snapshot of that tree's root.
- **Voting.** To vote, a member proves in zero knowledge that they know the secret behind one of the leaves in the snapshot. The proof also carries a nullifier hash tied to that proposal.
- **Double-vote check.** The contract rejects a nullifier hash it has already seen, so each member votes at most once per proposal. Nullifier hashes for different proposals can't be linked to each other.
- **Relaying.** The vote transaction is sent by a **relayer wallet**, never by the member's wallet.

## Running it

```bash
npm install
npm run build:circuit          # nargo test + compile, bb write_vk -t evm, regenerate HonkVerifier.sol
(cd contracts && forge build && forge test)
anvil                          # separate terminal
npm run deploy:local           # writes deployments/local.json
npm run demo                   # 4 members, 2 proposals, relayer, failure paths, tally
```

Manual flow for one member (anvil keys: member = account 1, relayer = account 9):

```bash
MEMBER_PRIVATE_KEY=$K1 node scripts/register.mjs --token-id 1
MEMBER_PRIVATE_KEY=$K1 node scripts/create-proposal.mjs --description "Fund X?" --period 3600
RELAYER_PRIVATE_KEY=$K9 node scripts/relayer.mjs &                     # 127.0.0.1:8799
node scripts/vote.mjs --note .notes/member-1.json --proposal 0 --support yes --relayer http://127.0.0.1:8799
node scripts/tally.mjs --proposal 0
```

The toolchain used was nargo 1.0.0-rc.2 and bb 5.2.0, with `@noir-lang/noir_js@1.0.0-rc.2` and `@aztec/bb.js@5.2.0` pinned to match. The bb.js version must match the `bb` CLI that generated the verifier.

## One member, one proposal: end to end

The legend below is for the wallets that send transactions. "Observer" means anyone reading the chain, including us.

- **D**: deployer. Used once.
- **M**: the member's wallet, which holds membership NFT #T and is public in the registry.
- **P**: any member's wallet that opens the proposal.
- **R**: relayer wallet. It holds no NFT, has never registered, and has no funding link to any member.

### 0. Deployment (once) — sender **D**

`Deploy.s.sol` sends these transactions:
- `HonkVerifier`
- the `PoseidonT3` library
- `AnonVoting(nft, verifier, minAnonymitySet)`
- locally only: `DemoMembershipNFT` and its mints

**What an observer learns:** the contract addresses and the configuration, including which NFT defines membership and the minimum anonymity set.

### 1. Joining: `register(tokenId, commitment)` — sender **M**, once per NFT

Offchain, on the member's machine, `register.mjs` does the following:
- It generates two random field elements, `nullifier` and `secret`.
- It computes `commitment = Poseidon(1, Poseidon(nullifier, secret))`.
- It saves the note to `.notes/member-T.json` (mode 600) **before** sending the transaction.

The note is the member's voting credential for every future proposal. If it's lost, the member can't vote until they rotate it (step 1b). If it leaks, whoever holds it can vote as that member.

The contract checks that `M` owns NFT #T and that #T has no seat yet. It then inserts the commitment into the member tree and marks `M` as a registrant.

**What an observer learns:** "wallet M, holder of #T, now has a seat, and its commitment is C at leaf index i." This link is intended. C reveals nothing about the note, and no vote ever references C or i.

The timing of registration doesn't matter, because registration isn't tied to any proposal.

**1b. (Optional) `replaceCommitment(tokenId, newCommitment, siblings)` — sender: the current holder of #T.** This is for a new holder after an NFT transfer, or when a note is lost or leaked. **What an observer learns:** "#T's seat changed commitment." Proposals that are already open keep their snapshot.

### 2. Opening the proposal: `createProposal(descriptionHash, period)` — sender **P**

The contract does three things:
- It requires that `P` holds an NFT and that the tree has at least `minAnonymitySet` leaves.
- It stores the current tree root as the proposal's `memberRoot`, which becomes the anonymity set for the vote.
- It stores `externalNullifier = keccak(chainId, contract, proposalId) mod p` and the deadline.

**What an observer learns:** who proposed it (that isn't secret), the description hash, the deadline, and the anonymity set size N (the snapshot's member count). All voters prove against this same root, so the root can't be used to split voters into smaller groups.

### 3. Proving (offchain, no transaction) — on the member's machine

`vote.mjs` runs these steps:
1. It downloads **all** `MemberRegistered` and `MemberCommitmentReplaced` events up to the `ProposalCreated` log, and replays them into a LeanIMT mirror (`memberTreeAtProposal`). It then checks that the mirror's root equals `memberRoot`. Because every member downloads the same full set of events, the RPC provider can't tell which leaf belongs to this member.
2. It finds its leaf and builds the Merkle path.
3. It computes `nullifierHash = Poseidon(Poseidon(2, externalNullifier), nullifier)`.
4. It runs the circuit with NoirJS and produces an UltraHonk proof with bb.js (`verifierTarget: 'evm'`, the zero-knowledge variant). This takes about 0.5 s.

The circuit proves the following:
- the member knows a note whose commitment is in `memberRoot`
- `nullifierHash` was derived correctly for this proposal
- `vote` ∈ {0, 1}

The public inputs are `[memberRoot, externalNullifier, nullifierHash, vote]`, in that order both in the circuit and in `AnonVoting._publicInputs`.

5. It sends only `{proposalId, support, nullifierHash, proof}` to the relayer. It never sends the note or the member's wallet key.

### 4. Voting: `castVote(proposalId, support, nullifierHash, proof)` — sender **R** (relayer)

The contract makes these checks, in order:
- the proposal exists and the deadline hasn't passed
- `nullifierHash` hasn't been used
- **the sender is not an NFT holder or a past registrant** (`SenderIsLinkable`). This is a safeguard against the most common mistake, a member submitting from their own wallet.
- the proof verifies against the snapshot root, rebuilt from contract storage

Only then does it mark the nullifier as used, increment the yes or no count, and emit `VoteCast(proposalId, nullifierHash, support)`.

**What an observer learns:**
- that *one of the N snapshot members* voted yes (or no) on this proposal
- a nullifier hash. It looks random, is unique to this member and this proposal, and can't be linked to the same member's hash on any other proposal.
- the relayer's address, and the time of the vote

**What an observer does not learn:** which of the N members it was. The proof is zero-knowledge, and the sender is R, not M.

The relayer can't flip the vote or move it to another proposal, because both are public inputs to the proof (this is tested: a flipped vote fails with `InvalidProof`). What the relayer *can* do is refuse to relay it (see below).

Gas is about 3.8M per vote, mostly from the verifier and about 8 KB of proof calldata. That's fine on an L2 but noticeable on mainnet.

### 5. Tally: `tally(proposalId)` — a view call, no transaction, anyone

This returns `(yes, no, closed)`. The counts are final once `closed` is true, meaning `block.timestamp >= deadline`. Anyone can also recount from the `VoteCast` events.

**What an observer learns:** the counts. As step 4 already showed, the counts are also visible while voting is open.

## What still has to be done right (and what this doesn't cover)

These points are about how the system is operated. The cryptography doesn't handle them.

1. **Never send the vote from a linked wallet.** `castVote` blocks NFT holders and registrants. It can't detect a fresh wallet that M funded, or a wallet that later sends funds to M. The supported path is a relayer.
2. **The relayer sees network metadata.** It sees the IP address and timing of each request. If the DAO runs the relayer, the DAO sees that too. `relayer.mjs` doesn't log IPs, but members shouldn't have to take that on trust. For contested votes:
   - Members should connect to the relayer over Tor.
   - Or they should use a relayer run by someone else. `castVote` accepts any sender, so anyone can run one.
   - `RELAY_MAX_DELAY_MS` adds a random delay, so the transaction's timing doesn't reveal when the member clicked. For best results, submit well before the deadline.

   A relayer can **censor** a vote but can't forge or change it. If votes are going missing, use a second relayer.
3. **The anonymity set is the number of registered seats at the snapshot, not 150.** `minAnonymitySet` enforces a minimum. The demo default is 3; in production, set it close to the full membership (for example 100 of 150), and get members registered before the first contested vote.
4. **The tally itself can reveal votes.** A unanimous result reveals every voter's choice, although it doesn't reveal who voted. For example, if every seat voted and the result is 150–0, everyone's vote is known. This is true of any published tally.
5. **Running counts are public.** Each vote is public as soon as it's cast, so members can vote strategically based on the running count. It doesn't reveal who voted. Hiding the counts until the deadline would need encrypted ballots (threshold decryption or MACI), which this design doesn't include.
6. **No protection against coercion or vote-buying (no receipt-freeness).** A member can *prove* how they voted by revealing their note, since anyone who has it can recompute the nullifier hash. So "nobody can tell" holds against observers and against us, but not against a member who chooses to reveal their note, or is forced to. If bribery or coercion is a real risk in your contested votes, you need MACI-style key-change voting.
7. **Generate proofs on the member's device, from code the member trusts.** If the DAO serves the proving code from its website, a malicious or compromised build could leak notes. Publish reproducible builds, or let members run `scripts/vote.mjs` themselves.
8. **Keep the ZK variant everywhere.** The verifier is built with `bb ... -t evm` and proofs with `verifierTarget: 'evm'`. The non-ZK `evm-no-zk` variant, which is also what bb.js's old `{ keccak: true }` flag selects, doesn't formally hide the witness.
9. **What happens when an NFT is transferred.** A seat belongs to the tokenId, and a new wallet can't create a second seat for it. Until the new holder calls `replaceCommitment`, the previous holder's note still works for proposals created before the rotation. It also still works for proposals created after the transfer but before the rotation. The new holder should rotate immediately after receiving the NFT.

UltraHonk uses a universal SRS, so there is no per-circuit trusted setup. If you change the circuit, run `npm run build:circuit` again and redeploy. Also regenerate the Forge fixture with `node scripts/gen-fixture.mjs`.
