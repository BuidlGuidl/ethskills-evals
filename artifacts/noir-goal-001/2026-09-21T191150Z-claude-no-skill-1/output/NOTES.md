# Anonymous DAO voting: design and end-to-end flow

## The idea in one paragraph

Membership stays public. Each member links their NFT wallet, once and in
public, to a **commitment** `C = Poseidon(secret)`, which becomes a leaf in an
on-chain Merkle tree. When a proposal opens, the contract **snapshots** that
tree's root. To vote, a member proves in zero knowledge that "I know the secret
behind *some* leaf of this root". The proof also publishes a **nullifier**
`N = Poseidon(secret, scope)`, where `scope` is unique to the proposal, and the
vote itself (0/1). The contract counts the vote and refuses to see `N` twice.
Nothing in the proof, the nullifier or the vote tells anyone which leaf
produced it. The vote transaction is sent by a **relayer**, not by the member, so
the transaction sender doesn't reveal the voter either.

## Components

| Path | What |
|---|---|
| `circuits/vote/src/main.nr` | Noir circuit: membership proof, nullifier, vote ∈ {0,1}. Private: `secret`, Merkle path. Public (in this order): `merkle_root, scope, vote, nullifier`. |
| `src/AnonVoting.sol` | Member tree (Poseidon, depth 16), proposals with snapshotted root, nullifier set, tally. No owner and no admin functions. |
| `src/HonkVerifier.sol` | Generated by `bb write_solidity_verifier -t evm`. This is the **zero-knowledge** UltraHonk verifier (keccak transcript). |
| `src/MembershipNFT.sol` | Local stand-in for your existing NFT. In production, point `MEMBERSHIP_NFT` at the real one. |
| `script/Deploy.s.sol`, `scripts/deploy-local.sh` | Deploy the verifier, AnonVoting (with the PoseidonT3 library linked automatically) and the NFT, wire them together, and write `deployments/<chainId>.json`. |
| `js/vote.mjs` | **Member flow:** secret → rebuild tree → Merkle path → nullifier → proof → relayer (or an unlinked account). |
| `js/relayer.mjs` | Minimal relayer: simulates the call, then submits `castVote` and pays the gas. |
| `js/identity.mjs`, `js/register.mjs`, `js/proposal.mjs` | Create an identity, register it, create a proposal or read a tally. |
| `js/e2e-local.mjs` | Whole flow on anvil: 5 members, 1 proposal, 5 real proofs, a rejected double vote, the tally. |
| `test/AnonVoting.t.sol` | Contract logic tests using a mock verifier. The real verifier is exercised by the e2e run. |

## End-to-end: one member, one proposal

Actors and wallets:

- **Member wallet `W`**: holds membership NFT `#T`. It is publicly known to be
  member T (it's in your registry).
- **Member secret `s`**: a random field element that lives only on the
  member's machine (`js/identity.mjs new`). It never goes on-chain and is never
  sent to anyone.
- **Relayer wallet `R`**: run by the DAO or by anyone. It holds no NFT (the
  contract enforces this) and is shared by every voter.
- **Proposer wallet `P`**: any NFT holder.

### Step 0: deployment (once). Sent by: the deployer wallet

Transactions: deploy `PoseidonT3`, `HonkVerifier` and `AnonVoting(nft, verifier, minAnonymitySet)`.

**What an observer learns:** the contract code, the verification key (which is the
circuit), the NFT address, and the minimum anonymity set. There's no admin key
and no trusted party holding a trapdoor. UltraHonk uses the universal
Aztec Ignition SRS, so there's no per-circuit trusted setup.

### Step 1: join (once per member, reused for every future proposal)

Off-chain: `node js/identity.mjs new ~/.dao/identity.json` generates `s` and
computes `C = Poseidon(s)`.

**Tx `register(T, C)`. Sent by: member wallet `W`.**
The contract checks `ownerOf(T) == W`, that token T hasn't registered before,
and that `C` is fresh. It then appends `C` as leaf `i`.

**What an observer learns:** "wallet `W` / token `T` owns leaf `i` with
commitment `C`", plus the new root. This is deliberately public: it's the same
fact your member registry already publishes. `C` is a hash of a random secret
and shows nothing about any vote. It isn't even computable from the nullifiers
the member will publish later.

### Step 2: proposal opens. Sent by: proposer wallet `P`

**Tx `createProposal(descriptionHash, votingPeriod)`.**
The contract stores the current `memberRoot` and `memberCount` as the proposal's
snapshot, along with `deadline` and
`scope = keccak256(chainid, contract, proposalId) mod p`.

**What an observer learns:** who proposed (unrelated to how anyone votes), the
deadline, and the **anonymity set**, which is exactly leaves `0..memberCount-1`,
i.e. a known list of member wallets. Everyone who votes on this proposal is
hidden among all of them, voters and non-voters alike.

Snapshotting matters. If voters could prove against the latest root, someone who
registered after the proposal opened would have to use a newer root, and
that would single them out. With the snapshot, every vote on a proposal uses
the identical root. Late registrants simply vote on the next proposal.

### Step 3: the member prepares a vote (off-chain, local)

`node js/vote.mjs --identity ~/.dao/identity.json --proposal 7 --vote yes --relayer https://relayer.example`

1. Read `getProposal(7)` and **all** `MemberRegistered` events. These are public
   and every member downloads the same data, so the RPC node can't tell which
   leaf is yours. The script never asks the chain anything that depends on your
   identity, such as "is my nullifier used?".
2. Rebuild the tree from the first `memberCount` leaves and check that its root
   equals the snapshot. Find your own leaf `i` and its Merkle path.
3. Compute `N = Poseidon(s, scope)`.
4. Execute the Noir circuit and produce a **ZK** UltraHonk proof
   (`verifierTarget: "evm"`, about 1 s on a laptop). The proof establishes: leaf
   `Poseidon(s)` is in the snapshot tree, `N` is correctly derived from the same `s`,
   and `vote ∈ {0,1}`. It reveals nothing else: not `s`, not `i`, not the path.
5. POST `{proposalId, support, nullifier, proof}` to the relayer. The relayer
   receives the same data the chain will publish. Beyond that it sees only
   network metadata (IP and timing), so connect through Tor or a VPN.

### Step 4: the vote lands. Sent by: relayer wallet `R`

**Tx `castVote(7, support, N, proof)`.**
The contract checks that the proposal is open, that neither `msg.sender` nor
`tx.origin` holds an NFT, that `N` is a canonical field element and unused, and
that the proof verifies against the public inputs `[snapshotRoot, scope, support, N]`.
It then marks `N` as used and increments `yes` or `no`.

**What an observer learns:** "*some* member of proposal 7's snapshot voted
`support`", the nullifier `N`, the block time, and that relayer `R` paid gas
(about 3.8M gas, mostly for proof verification). It can't learn which
member voted:

- `N` is a Poseidon output keyed by `s`. Without `s`, you can't link it to `C`,
  and it's unlinkable to the same member's nullifiers on other proposals,
  because the scopes differ.
- The proof is zero-knowledge, and the root and scope are shared by every voter.
- The sender `R` is the same for everyone.
- The vote is a public input, so neither `R` nor a mempool front-runner can flip it.
  A copied proof can only be submitted as the same vote, once.

A second vote by the same member produces the same `N` and reverts with
`NullifierAlreadyUsed`. The e2e run demonstrates this.

### Step 5: tally. No transaction

After `deadline`, anyone can call `tally(7)`, which returns `(yes, no, eligible)`.
It's a free `eth_call`. Before the deadline it reverts. Anyone can also
recount from the `VoteCast` events.

**What an observer learns:** the counts, the turnout, and the eligible-set size.

## What this does *not* protect against (read before relying on it)

1. **The running tally is visible before the deadline.** Every `VoteCast` is
   public calldata, and `tally()` refusing to answer early is only a courtesy.
   This doesn't reveal *who* voted what, but people can see which way the
   vote is going. Hiding it requires encrypted ballots with threshold
   decryption (MACI-style) and a coordinator or key committee. That's a
   substantial step up in complexity.
2. **Aggregate results can themselves attribute votes.** A 5–0 result reveals
   everyone's vote. So does "149 people said publicly how they voted, and
   the tally reveals the 150th". No tally-publishing scheme can avoid this.
   `minAnonymitySet` (constructor argument) stops proposals from opening while
   the registered set is tiny. Set it to something meaningful in production
   (the local deploy uses 3).
3. **The secret unlocks the member's whole voting history.** Anyone who
   obtains `s` can compute `Poseidon(s, scope)` for every past proposal and see
   every vote that member cast. A member can also *voluntarily* prove their vote
   to a briber or coercer by revealing `s`. This scheme isn't receipt-free. If
   coercion is a real threat, you need MACI-style key changing.
4. **Network metadata.** The relayer and the RPC node see IPs and timing. If
   the DAO runs both and a member connects directly, a vote could be matched
   to their IP. Use Tor or a VPN, and don't vote seconds after doing something
   identifiable (for example, registering and immediately voting on a quiet chain).
   A production relayer should add random delays or batch submissions.
   The relayer keeps no logs.
5. **Self-submitting.** If a member sends `castVote` from `W`, their vote is
   public. The contract refuses NFT holders and `vote.mjs --direct` refuses
   too. But a fresh wallet funded from `W`, or from an exchange account in the
   member's name, is just as linkable. Use the relayer.
6. **Who serves the prover code.** If members generate proofs in a web page the
   DAO hosts, whoever controls that page can steal secrets. Members should run
   this open-source script locally, or use a pinned build they can audit.
7. **Sybil leaves shrink the real anonymity set.** Whoever controls NFT minting
   can mint tokens to themselves and register fake leaves. That lets them vote
   more than once and makes the anonymity set look bigger than it is. Members
   can check that every leaf's `tokenId` belongs to a real person in the public
   registry. Governance over minting is the real control.
8. **Membership changes aren't handled.** The registration belongs to the token.
   If NFT `#T` is transferred or burned, the old holder's secret still votes on
   proposals that open later, and the new holder can't register `#T`.
   Production needs a revoke/replace path. The contract knows each token's leaf
   index, so on transfer it can set that leaf to zero (tree update with siblings)
   and let the new owner register. Note that revoking a leaf is public and says
   nothing about past votes.
9. **Cost.** Proof verification costs about 3.8M gas per vote. Deploy on an L2
   and fund the relayer. The contract doesn't reimburse relayers.

## Running it

Prerequisites: nargo 1.0.0-rc.2, bb 5.2.0 (matching `@aztec/bb.js@5.2.0` and
`@noir-lang/noir_js@1.0.0-rc.2`), foundry, and node ≥ 20.

```sh
npm install
npm run circuit:test                 # nargo test
npm run circuit:build                # nargo compile + vk + regenerate src/HonkVerifier.sol
forge build && forge test

anvil                                # separate terminal
./scripts/deploy-local.sh            # deploys and mints NFTs #1..#5 to anvil accounts 1..5
node js/e2e-local.mjs                # register 5, propose, 5 relayed ZK votes, double-vote rejected, tally
```

Manual flow (anvil account keys can be derived with `cast wallet private-key --mnemonic "test test test test test test test test test test test junk" --mnemonic-index N`):

```sh
node js/identity.mjs new .demo/me.json
MEMBER_PRIVATE_KEY=<acct1> node js/register.mjs --identity .demo/me.json --token 1
# ...at least MIN_ANONYMITY_SET members register...
MEMBER_PRIVATE_KEY=<acct1> node js/proposal.mjs create "Fund X" 600
RELAYER_PRIVATE_KEY=<acct9> node js/relayer.mjs &
node js/vote.mjs --identity .demo/me.json --proposal 1 --vote yes --relayer http://127.0.0.1:8787
node js/proposal.mjs tally 1         # after the deadline
```

If you change the circuit, rerun `npm run circuit:build`. `TREE_DEPTH` must stay
in sync across `main.nr`, `AnonVoting.sol` and `js/common/tree.mjs`. The verifier
must always be generated with `-t evm`, the ZK target. `-t evm-no-zk` would
produce proofs that aren't guaranteed to hide the witness.
