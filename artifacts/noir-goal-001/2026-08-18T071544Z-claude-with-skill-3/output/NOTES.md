# Anonymous DAO voting — how it works

Yes/no governance for a DAO whose membership is public, where no one — including
whoever operates the DAO — can tell how any individual member voted.

The shape of the answer: membership stays public and auditable, but a member's
*ballot* is separated from their *identity* by a zero-knowledge proof. Each member
publishes a commitment to a secret once. To vote they prove "I know the secret
behind one of the commitments in the member set" without saying which one, and a
different wallet puts that proof onchain. A per-proposal nullifier stops them
voting twice without ever pointing back at the commitment.

This is the Semaphore construction, specialised to yes/no proposals.

## One member, one proposal, start to finish

Alice holds a membership NFT at `0xAlice…`. There are 150 members.

### Step 0 — Alice derives her voting identity (offline, no transaction)

Alice's wallet signs the fixed string `dao-anon-voting/v1/identity`. That
signature is hashed into two field elements:

```
identityNullifier = H_keccak("identity-nullifier" ‖ seed)  mod p
identityTrapdoor  = H_keccak("identity-trapdoor"  ‖ seed)  mod p
commitment        = poseidon(1, poseidon(identityNullifier, identityTrapdoor))
```

Signing is deterministic, so Alice can re-derive the same identity on any machine
from her wallet alone — there is no note file to back up or leak. The two secrets
never leave her machine; only `commitment` is ever published.

The `1` is a domain tag. Nullifiers use `2`, so a commitment can never be mistaken
for a nullifier or vice versa.

**Onchain:** nothing.

### TX 1 — `register(commitment)`

| | |
|---|---|
| **Sender** | `0xAlice…`, her own membership-NFT wallet |
| **Contract** | `AnonVoting.register` |
| **Observer learns** | `0xAlice…` holds the NFT and has joined the anonymous vote, with commitment `C_alice` at leaf index `i`; the new member-tree root |
| **Observer does not learn** | anything about `identityNullifier` / `identityTrapdoor` — `commitment` is a Poseidon hash blinded by the trapdoor |

This transaction deliberately links wallet to commitment. That link is the point:
anyone can check that the anonymity set contains exactly the 150 NFT holders and
no phantom entries. It is also the last time Alice's member wallet appears.

The commitment goes into a Poseidon LeanIMT (`@zk-kit/lean-imt.sol`) held in
contract storage. The contract emits `MemberRegistered(commitment, leafIndex,
newRoot)`; clients replay those events to rebuild the identical tree offchain,
because the contract never hands out Merkle witnesses.

Once per member, ever. `hasRegistered[msg.sender]` blocks a second commitment.

### TX 2 — `createProposal(description, votingPeriod)`

| | |
|---|---|
| **Sender** | any member wallet (holds the NFT). In the demo, member 1 |
| **Contract** | `AnonVoting.createProposal` |
| **Observer learns** | who opened the proposal, its text, its deadline, the member-tree root it pinned, and how many members are in that set |
| **Observer does not learn** | nothing new about anyone's secrets |

**Root policy — pinned snapshot.** The proposal stores exactly one root: the tree
root at the moment it opened. There is no rolling window of accepted roots. So a
member who registers after the proposal opens cannot vote on it, and equally, no
commitment can be inserted into the eligible set once voting has started. Clients
prove against that pinned root, which means rebuilding the offchain tree only up
to the `ProposalCreated` block (`js/vote.mjs` does this automatically).

A proposal also cannot open unless the tree already holds `minAnonymitySet`
commitments. A 1-of-2 anonymity set is not anonymity.

### Step 3 — Alice builds her ballot (offline, no transaction)

1. Read the proposal's pinned root and deadline.
2. Replay `MemberRegistered` events up to the proposal's block, rebuild the
   LeanIMT, and check the root matches.
3. Take her own Merkle witness out of that tree: `leafIndex`, `depth`, sibling
   hashes and left/right bits.
4. Compute her nullifier for this proposal:
   `nullifierHash = poseidon(poseidon(2, proposalId), identityNullifier)`.
5. Run the Noir circuit and generate an UltraHonk proof (~1–3 s).

The circuit proves, with these four values public and everything else private:

| public input | order | meaning |
|---|---|---|
| `merkle_root` | 0 | the set she is claiming membership of |
| `proposal_id` | 1 | which proposal this ballot belongs to |
| `nullifier_hash` | 2 | her one-time marker for this proposal |
| `vote` | 3 | 0 = no, 1 = yes |

and asserts:

- `vote * (vote - 1) == 0` — it is a bit, and it is *inside* the proof, so a
  relayer can forward the ballot but cannot change it;
- `commitment = poseidon(1, poseidon(nullifier, trapdoor))` folds through the
  supplied siblings to exactly `merkle_root`;
- `nullifier_hash` really is this identity's nullifier for *this* `proposal_id`.

Because `proposal_id` is mixed into the nullifier, Alice's ballots on two
different proposals produce two unrelated-looking nullifiers. Nobody can group a
member's votes into a voting history.

### TX 3 — `castVote(proposalId, vote, nullifierHash, proof)`

| | |
|---|---|
| **Sender** | a **burner or relayer wallet with no NFT and no registration** — never `0xAlice…` |
| **Contract** | `AnonVoting.castVote` |
| **Observer learns** | that *somebody* under the pinned root voted, and how they voted; the nullifier value; the relayer's address; the timestamp; gas paid |
| **Observer does not learn** | which commitment, which leaf index, which member wallet. The proof is zero-knowledge over all of it |

The contract checks the deadline, checks the nullifier is unspent, refuses
`msg.sender` if it is a registered member wallet, and only then calls
`HonkVerifier.verify`. Nothing is written until the proof passes.

`msg.sender` is *not* an input to the proof — authorisation is the proof itself.
That is what lets anyone relay a ballot on Alice's behalf. The
`BallotFromMemberWallet` check is the guard rail: the single most likely way to
destroy this scheme's privacy is a member cheerfully submitting their own ballot
from their own wallet, so the contract simply refuses.

The relayer sees the ballot it is relaying but has no idea whose it is: it
receives a proof and a nullifier, nothing else. Alice should still reach it over
Tor/VPN so it does not learn her IP.

### Reading the tally

`result(proposalId)` returns `(yesVotes, noVotes)` once the deadline has passed.
No transaction, no key, no privileged role — the counters were incremented by the
ballots themselves.

## Why nobody, including you, can attribute a vote

There is no admin key, no tally authority, no coordinator, and no decryption step.
The link between a member and a ballot is not encrypted-and-held-somewhere; it is
never created:

- The only onchain record tying `0xAlice…` to anything is her commitment.
- The only onchain record of her ballot is a nullifier and a vote bit.
- Connecting the two requires `identityNullifier`, which exists only on her
  machine. Everyone else — you, us, the relayer, an archive node — faces a
  Poseidon preimage.
- The proof leaks nothing beyond its four public inputs. Leaf index and depth are
  private inputs.

The scheme's strength is the 150-member anonymity set, and it degrades honestly:
with 150 registered members and 90 ballots cast, a ballot is 1-in-150 by
construction, before any turnout reasoning.

## What is *not* hidden — read this before shipping

1. **Turnout and the running tally are public.** Each ballot is its own
   transaction carrying a plaintext `yes`/`no`, so anyone watching sees the tally
   move in real time. `result()` reverting before the deadline is a convenience,
   not secrecy — the counters sit in public storage. For contested votes this
   enables late-voter strategising and bandwagoning. Hiding the running tally as
   well needs homomorphic ballots plus a threshold-decryption committee, and that
   committee would be exactly the "including us" party you ruled out. We chose
   unlinkability over tally secrecy; if you want both, MACI is the direction, at
   the cost of trusting a coordinator not to *deanonymise* (it can already see
   votes) and a much larger build.

2. **Who registered is public, by design.** Non-registration is visible: a member
   who never joins is publicly known not to have voted.

3. **Gas funding is the real-world weak point.** A burner wallet funded by a
   direct transfer from `0xAlice…` links right back to her. Options, best first:
   a shared relayer (member sends the ballot over HTTPS/Tor, relayer pays gas and
   never learns who sent it); an ERC-4337 paymaster; a burner funded from an
   exchange withdrawal. Never fund a burner from the member wallet.

4. **Timing correlates.** A ballot landing ninety seconds after Alice's only
   forum post of the week is a signal. Sensible relayer behaviour is to batch and
   randomly delay submissions, especially for votes with few participants.

5. **Small proposals leak.** If only three members vote, the ballots are still
   unlinkable, but the possible-voter set is small enough for social inference.
   `minAnonymitySet` guards the registered set, not turnout.

6. **A ballot in the mempool can be copied.** Anyone watching can grab a pending
   ballot and submit it themselves. The result is identical — the vote bit and
   the nullifier are fixed inside the proof — so the only damage is the original
   relayer wasting gas on a reverted duplicate. We deliberately do not bind
   `msg.sender` into the proof, because that is exactly what would make relaying
   impossible.

7. **The relayer can censor.** It cannot alter or forge a ballot — the vote bit
   and the proposal id are inside the proof — but it can drop one. Mitigation:
   several independent relayers, and let members fall back to self-submitting
   from an independently funded burner.

## Running it

Prerequisites: `nargo` 1.0.0-beta.26, `bb` 5.1.0, `forge`, Node 20+.

```bash
npm install                       # JS: noir_js, bb.js, poseidon-lite, lean-imt, ethers
(cd contracts && npm install)     # Solidity: lean-imt.sol, poseidon-solidity
(cd contracts && forge install foundry-rs/forge-std@v1.9.6)   # if contracts/lib/ is empty
```

Build the circuit and regenerate the Solidity verifier:

```bash
./scripts/build-circuit.sh
```

Stand it up on a local chain:

```bash
anvil                                                    # terminal 1
cd contracts
forge script script/Deploy.s.sol --rpc-url http://127.0.0.1:8545 --broadcast
```

That deploys `HonkVerifier`, a `MembershipNFT` (minting to anvil accounts 1–8),
and `AnonVoting` wired to both; forge auto-deploys and links the `PoseidonT3`
library the tree needs. Addresses land in `deployments/local.json`, which the
Node scripts read.

The whole flow, including the failure cases:

```bash
node js/demo.mjs
```

Or one member at a time (anvil account 3 votes, account 9 relays):

```bash
node js/register.mjs       --member-key 0x7c8521…
node js/create-proposal.mjs --member-key 0x7c8521… --description "Fund the Q3 grants round" --period 3600
node js/vote.mjs --proposal 0 --vote yes \
  --member-key  0x7c8521…   # signs offline only, sends nothing
  --relayer-key 0x2a871d…   # pays gas, holds no NFT
```

Point any of them at another chain with `--rpc` or `RPC_URL`.

### Tests

```bash
(cd circuits/ballot && nargo test)   # 5 circuit tests incl. non-member + non-binary vote
(cd contracts && forge test)         # 16 tests against the real verifier
```

`forge test` uses genuine proofs from `contracts/test/fixtures/ballots.json`
(regenerate with `node js/fixtures.mjs`), never a mock verifier. It covers the
happy path, the tally, and: reused nullifier, flipped vote, replay onto another
proposal, swapped nullifier, a nullifier shifted by the field order, tampered proof
bytes, ballot from a member wallet, ballot after the deadline, pinned-root
immutability, and Poseidon parity between
Noir, poseidon-lite and `PoseidonT3` (a mismatch there would silently break
everything, so it is asserted with hard-coded vectors printed by
`nargo test --show-output print_parity_vectors`).

## Sizing for 150 members

- Circuit `MAX_DEPTH` is 16 (65 536 members); 150 members is depth 8. Raising the
  cap costs gates, so it is set once at compile time with headroom.
- ~6.5k ACIR opcodes; proving takes 1–3 s on a laptop, in-browser too.
- `castVote` costs ~2.6 M gas, essentially all of it Honk verification. On L1 that
  is expensive per ballot; on an L2 it is minor. This is the main reason to run a
  relayer that batches, or to move the DAO's voting to an L2.
- `HonkVerifier` is 18.1 KB with the optimizer on — under the 24 KB limit, but
  regenerate and re-check `forge build --sizes` if the circuit grows.

## Known gaps

- **Lost wallet, lost vote.** The identity is derived from a wallet signature, so
  losing the member wallet loses the voting identity. There is no rotation path:
  `register` is once per address. Adding one means a `rotate` that *removes* the
  old leaf (`LeanIMT._update`, which needs the caller to supply siblings) —
  otherwise a member ends up with two live commitments and two ballots. Worth
  building before this runs a real treasury vote.
- **Membership is checked at registration, not at vote time.** A member who
  registers and then sells their NFT can still vote on proposals opened before
  the sale, since the pinned root already contains their commitment. Fixing it
  needs leaf removal, same machinery as rotation.
- **No relayer service is included here.** `js/vote.mjs` submits from a key you
  supply. A production deployment needs an actual relayer (or paymaster) so
  members never touch gas — see point 3 above.
- **Eligibility is per wallet, not per human.** One NFT-holding wallet gets one
  commitment and therefore one ballot. `MembershipNFT` here enforces one token per
  address, but if your real membership NFT lets one person hold several tokens
  across several wallets, that person gets several ballots. The privacy property
  is unaffected; the one-member-one-vote property is not.
- **Proposal creation is unrestricted among members.** Any member can open any
  number of proposals; add a deposit or a proposer threshold if that matters.
