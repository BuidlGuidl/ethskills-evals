# Anonymous DAO voting: how it works

Membership is public, but votes can't be tied to members. A member registers
once, from their NFT wallet, with a Poseidon commitment to two random secrets.
For each proposal they prove in zero knowledge that they own *some* leaf in the
member tree. The proof carries a per-proposal nullifier hash, which blocks a
second vote. A relayer sends the proof onchain, so the member's wallet never
touches the vote.

```
circuits/vote/src/main.nr     Noir circuit: membership + nullifier + binary vote
contracts/AnonymousVoting.sol registry (LeanIMT of commitments), proposals, castVote, tally
contracts/HonkVerifier.sol    generated by `bb write_solidity_verifier` from the circuit's EVM VK
contracts/MembershipNFT.sol   local stand-in for the DAO's existing NFT
script/Deploy.s.sol           deploy + wire (verifier and NFT -> AnonymousVoting; PoseidonT3 linked)
test/AnonymousVoting.t.sol    contract rules + Poseidon cross-layer vector
scripts/lib.mjs               notes, tree mirror from events, NoirJS/bb.js proving
scripts/register.mjs          member wallet: new note -> register(tokenId, commitment)
scripts/vote.mjs              note -> proof -> relayer (holds no private key)
scripts/relayer.mjs           relayer: simulate, then send castVote from its own wallet
scripts/demo.sh               full run on a fresh anvil
```

## Running it

Toolchain: nargo `1.0.0-rc.2`, bb `5.2.0` (it must match `@aztec/bb.js` exactly), and foundry.

```bash
npm install
npm run build     # nargo test+compile, VK (--verifier_target evm), Solidity verifier, forge build
npm test          # forge tests
npm run demo      # anvil on :8599: deploy, 4 registrations, proposal, 4 relayed votes,
                  # a rejected double vote, tally  ->  yes=3 no=1 eligible=4
```

To deploy against an existing NFT, pass `MEMBERSHIP_NFT=0x...` (and optionally
`MIN_ANONYMITY_SET`) to `forge script script/Deploy.s.sol --broadcast`. The
deployed addresses go to `deployments/<chainId>.json`, and the Node scripts read
them from there.

## The flow for one member and one proposal

In this walkthrough Alice holds membership NFT #7. The table shows who sends each
transaction and what a chain observer learns from it.

| # | Step | Sender | What an observer learns |
|---|------|--------|-------------------------|
| 0 | Deploy `HonkVerifier`, `PoseidonT3`, `AnonymousVoting` (and the demo NFT) | DAO admin wallet | Contract addresses, which NFT gates registration, which verifier (and therefore which circuit) is wired in, and `minAnonymitySet`. The admin keeps no special power afterwards: no owner, no upgrade path, no way to add leaves. |
| 1 | `register(7, C)` | **Alice's own NFT wallet** | "The holder of NFT #7 joined anonymous voting with commitment C at leaf index i. The tree root is now R." C = Poseidon3(nullifier, secret, 1), where both inputs are random 254-bit values, so C reveals nothing and can't be brute-forced. This step is intentionally public, like membership. |
| 2 | `createProposal("…", period)` | Any member's wallet (here Bob's) | Bob proposed. The event also shows the snapshotted root, the eligible-voter count N (tree size), the deadline, and the proposal `scope` = keccak(chainId, contract, id) mod p. |
| – | Alice's client reads **all** `MemberRegistered` events, rebuilds the LeanIMT (`@zk-kit/lean-imt`), checks every emitted root and the snapshot root, and builds the proof in-process with NoirJS + bb.js (`verifierTarget: "evm"`) | none (offchain) | Nothing onchain. Her RPC provider sees a read of the public log, the same read every client makes, so it doesn't reveal which leaf is hers. |
| – | Alice POSTs `{proposalId, vote, nullifierHash, proof}` to a relayer | none (offchain) | The relayer sees the vote and her network origin, but not her identity (see limits). |
| 3 | `castVote(id, vote, nullifierHash, proof)` | **Relayer wallet** | "One of the N members in the snapshot voted yes/no." The observer also sees the nullifier hash, which is Poseidon(nullifier, scope). Without the nullifier it can't be linked to any commitment, and because the scope changes per proposal, the same member's nullifier hashes on different proposals are unrelated. `msg.sender` is the relayer for every voter. The transaction is ~2.58M gas, mostly the Honk verification. |
| 4 | `tally(id)` after the deadline | nobody (a `view` call) | The yes, no and eligible counts. |

The contract enforces these rules in `castVote`:
- the deadline hasn't passed
- `vote ∈ {0,1}` (the circuit enforces this too)
- the nullifier hash is unused
- `verifier.verify(proof, [root, scope, vote, nullifierHash])` returns true

The root and scope come from the proposal's storage, not from the caller. Only
after all four checks pass does it record the nullifier and count the vote. The
public inputs are in the same order as the circuit's `pub` parameters. The
script checks that order against bb.js output, and the contract builds the
array in `_publicInputs`.

## Why nobody, including the DAO, can attribute a vote

- **The proof hides the leaf.** The verifier learns only that the prover knows an
  opening of some leaf under the snapshot root. UltraHonk with the `evm` target
  is zero-knowledge, and it uses a universal SRS, so there's no per-circuit
  trusted setup the DAO could have tampered with.
- **The sender hides nothing, so it isn't the member.** Votes always come from
  the relayer. `scripts/vote.mjs` has no private key at all. A burner wallet
  funded from Alice's own wallet would recreate the link, so don't use one.
- **The nullifier is scoped per proposal.** Double voting is blocked, but her
  votes on different proposals can't be linked to each other.
- **The anonymity set is fixed per proposal.** Each proposal snapshots the
  root, and every vote on it proves against that one root. Anyone registered
  before the proposal opened could have cast any given vote. A per-voter choice
  of root would split the set, so the contract doesn't allow it. Proposals
  can't open over fewer than `minAnonymitySet` members.
- **Registration is keyed by token ID.** Moving an NFT to a fresh wallet
  doesn't produce a second leaf.
- **Leaves are domain-separated from tree nodes.** Leaves use a 3-input
  Poseidon and tree nodes a 2-input one. Without that, anyone could present an
  internal node, whose two children are public, as a leaf and get extra votes.
  This matters because LeanIMT paths have variable length.

## Hash consistency across layers

Every layer uses the same circomlib-compatible Poseidon over BN254 (not Poseidon2):

| Use | Noir | Solidity | JS |
|-----|------|----------|----|
| tree node (left, right) | `poseidon::bn254::hash_2` | `PoseidonT3.hash` (via `@zk-kit/lean-imt.sol`) | `poseidon2` (poseidon-lite) |
| leaf = (nullifier, secret, 1) | `hash_3` | — | `poseidon3` |
| nullifier hash = (nullifier, scope) | `hash_2` | — | `poseidon2` |

The shared test vector is `hash_2([1,2]) = 0x115cc0f5…17189a`. The Noir test
prints it, the forge test asserts it, and the demo cross-checks every onchain
root against the JS mirror.

## Limits and what to operate carefully

These don't break the core property, but members and the DAO should know about them.

- **The relayer sees the requester's IP and the vote.** If the DAO runs the
  relayer, "not even us" depends on members connecting over Tor or a VPN.
  `castVote` is permissionless and the proof pins the vote, so any member can
  also use a relayer run by someone else or submit through an ERC-4337
  paymaster. The worst a relayer can do is censor a vote. It can't change one.
  A member who is refused can switch relayers.
- **Timing and live counts are public.** `VoteCast` events and storage show the
  running tally before the deadline. `tally()` only gates the convenience
  getter. Someone who says "I'm voting now" in chat can be matched to the next
  `VoteCast`. The relayer's `MAX_DELAY_MS` adds random hold times. If a hidden
  running tally matters for contested votes, the next step is commit-reveal
  (commit the vote hash in the proof, reveal through a relayer after the
  deadline).
- **Counts can leak what the tally implies.** A 150–0 result, or a proposal
  where only 3 members registered, reveals votes by arithmetic. The eligible
  count published with each proposal makes this visible. `minAnonymitySet`
  sets a floor, so pick a meaningful one for production, e.g. 50.
- **Members who never registered** provably didn't vote. That reveals
  participation, not direction.
- **Votes aren't receipt-free.** Alice can prove how she voted by revealing
  her nullifier, which lets anyone recompute her nullifier hash. That means a
  buyer or coercer can demand proof. If coercion is a real threat, look at a
  MACI-style design with key changes and a coordinator.
- **The note is the credential.** It's saved to `notes/…json` with mode 0600
  before the register transaction goes out. If Alice loses it, she can't vote.
  If someone steals it, they can vote as her. There's no revocation or
  re-registration for a token yet, and a member who leaves the DAO keeps their
  leaf. Adding an admin removal path (LeanIMT `_remove`) is a governance
  decision, and it would make every snapshot depend on that admin.
- **Browser proving uses the same code path.** `proveVote` in `scripts/lib.mjs`
  uses only NoirJS and bb.js, with no `bb` CLI, so it ports to a browser client
  unchanged. Proving takes about 0.5 s in Node for the ~20k-gate circuit
  (MAX_DEPTH 16, room for 65k members).
