**How it works**
- **Joining:** a member registers once, from the wallet holding their NFT, by submitting a commitment made from two random secrets. That links the wallet to the commitment, which is fine because membership is already public and the commitment reveals nothing. Registration is tied to the NFT, so passing it to a new wallet doesn't get a second registration.
- **Voting:** the member's script proves they are *some* registered member without saying which one. The proof also produces a per-proposal code (a nullifier hash) that blocks a second vote. Members' votes on different proposals can't be linked to each other.
- **Who sends the vote:** the vote script holds no private key. It hands the proof to a relayer, which sends the transaction from its own wallet. The relayer can't change or fake a vote; the worst it can do is refuse to send one, and anyone can run another relayer.
- **Who can vote on a proposal:** each proposal freezes the member list when it opens. Every vote proves against that list, so all of those members are equally likely to have cast any given vote. A proposal can't open with fewer members than a set minimum.
- **Tally:** `tally()` returns yes, no and the number of eligible voters once the deadline has passed.

**Where things are**
- `circuits/vote/src/main.nr` — the Noir circuit.
- `contracts/AnonymousVoting.sol` — registration, proposals, voting and tally. `HonkVerifier.sol` is generated from the circuit, and `MembershipNFT.sol` stands in for your real NFT on a local chain.
- `script/Deploy.s.sol` — deploys and wires everything. Point it at your existing NFT with `MEMBERSHIP_NFT=0x...`.
- `scripts/` — `register.mjs`, `vote.mjs`, `relayer.mjs`, plus `demo.sh` for the full local run.
- `NOTES.md` — the end-to-end flow, with a table of each onchain transaction, who sends it, and what an observer learns.

Run it with `npm install`, `npm run build`, `npm test`, then `npm run demo`. The demo uses port 8599 because something else on this machine was already using 8545.

**What this doesn't protect against** (all written up in NOTES.md):
- **The relayer sees the voter's IP address and their vote.** If you run the relayer yourselves, "not even us" only holds if members connect through Tor or a VPN, or use someone else's relayer.
- **The running count is visible before the deadline.** Each vote is public onchain as it lands; `tally()` only waits for the deadline as a convenience. Someone who says "voting now" in chat could be matched to the next vote. If hiding the running count matters for contested votes, the next step is a commit-then-reveal scheme.
- **Lopsided or tiny results reveal votes by arithmetic.** A 150–0 result tells everyone how each member voted. Set the minimum member count to something meaningful in production (the demo uses 3).
- **Votes aren't coercion-proof.** A member can prove how they voted by revealing their secret, so a vote buyer could demand that proof. Guarding against that needs a heavier design (MACI-style).
- **The secret file is the member's voting credential.** If it's lost the member can't vote; if it's stolen someone else can vote as them. There's no way yet to revoke or re-register, and members who leave keep their registration.
