# Anonymous DAO ballots

Yes/no governance votes where membership stays public and **no one — including
whoever runs the DAO — can tell how any individual member voted.**

The property is anonymity, not encryption. A ballot proves "I am one of the N
members in this snapshot, and I have not voted on this proposal yet" without
revealing which one. The direction (yes/no) is public per ballot; who cast it is
not. That choice is deliberate and the reasoning is in
[Why the direction is public](#why-the-direction-is-public).

---

## The pieces

| Path | What it is |
| --- | --- |
| `circuits/lib` | `dao_zk`: Poseidon2 commitments, nullifiers, Merkle path. Both circuits share it so they cannot disagree. |
| `circuits/join` | Proves one append to the membership tree is legal. |
| `circuits/vote` | Proves membership + nullifier + ballot direction. |
| `contracts/src/MemberRegistry.sol` | Append-only Merkle tree of member commitments. Gated on the membership NFT. |
| `contracts/src/PrivateBallot.sol` | Proposals, ballots, nullifiers, tally. |
| `contracts/src/verifiers/` | Generated by `scripts/build-circuits.sh`. Do not hand-edit. |
| `contracts/src/dev/DevMembershipNFT.sol` | Local stand-in for the DAO's real NFT. Not used in production. |
| `scripts/member-vote.mjs` | One member, one proposal: secret → proof → submitted ballot. |
| `scripts/demo-local.sh` | The whole thing on anvil, start to tally. |

## End-to-end: one member, one proposal

Four kinds of on-chain transaction. Two are attributable on purpose; the one
that matters is not.

### 1. `MemberRegistry.join` — once per member, ever

**Sender: the member's own NFT-holding wallet.**

The member derives a secret by signing a fixed string with their wallet
(`scripts/lib/identity.mjs`), hashes it into `commitment = H(1, secret)`,
rebuilds the current tree from the registry's own event log, and proves that
appending their commitment at the next free slot takes the root from `old` to
`new` and changes nothing else. They send that proof with their token id.

An observer learns: this wallet holds membership token *k*, and it registered
commitment *C* at leaf *i*. Nothing else. `C` is a one-way hash of a secret that
never left the member's machine, and no future ballot references `C`, the leaf
index, or the wallet.

This transaction is attributable and that is fine — membership is already public
on the DAO's site. It happens once, long before any particular proposal, which
also keeps it from being correlated with a vote by timing.

### 2. `PrivateBallot.createProposal` — once per proposal

**Sender: any member's own wallet.**

Snapshots the registry root and member count, sets the deadline, stores
`keccak256(proposal text)`.

An observer learns: who proposed what, when voting closes, and that the
anonymity set for this proposal is the *N* members registered at that moment.
Nothing about anyone's ballot. What a member proposes is not what a member
votes.

The snapshot is what makes the anonymity set well defined: it is every member
registered at creation time, whether or not they turn up to vote. Members who
join later cannot vote on this proposal — they vote on the next one.

### 3. `PrivateBallot.castBallot` — the one that has to be anonymous

**Sender: a relayer. Never the member's own wallet.**

The member, entirely offline:

1. re-derives their secret from their wallet signature;
2. rebuilds the snapshot tree from the registry's public log — *locally*, so no
   server ever learns which leaf is about to vote;
3. computes `nullifier = H(2, secret, externalNullifier(proposalId))`;
4. proves, in `circuits/vote`, that they know a secret whose commitment sits at
   some leaf of the snapshot root, that the nullifier is the right tag for that
   secret and proposal, and that the direction is a bit.

Then they hand `(proof, nullifier, direction)` to a relayer, who sends it.

An observer learns:

- a transaction from the relayer's address;
- a nullifier, which is a fresh, unlinkable 32-byte value — it is a hash of a
  secret nobody else has, so it matches nothing in the registry, nothing from
  any other proposal, and nothing from any other member;
- the direction, yes or no;
- that the sender is *not* the voter (the relayer holds no membership token).

An observer does **not** learn which of the *N* registered members it came from.
Every one of them is an equally good explanation, and there is no on-chain value
that narrows it down.

`castBallot` never reads `msg.sender` — the proof is the authorisation, the
sender is just postage. `test_anyoneCanSubmitABallot` pins that.

Two things stop a relayer from misbehaving with a ballot it is carrying:

- **It cannot flip the vote.** The direction is a public input to the proof, so a
  "yes" proof fails verification if resubmitted as "no"
  (`test_voteProofRejectsAFlippedDirection`, against a real proof).
- **It cannot replay it.** The external nullifier covers the chain id, the ballot
  contract address and the proposal id, so a proof is valid for exactly one
  proposal on exactly one deployment
  (`test_voteProofRejectsAnotherProposal`).

A relayer *can* drop a ballot. See [censorship](#censorship) below.

### 4. `PrivateBallot.tally` — after the deadline

**Sender: nobody. It is a `view` call.**

Anyone reads yes, no and turnout once `block.timestamp >= deadline`. No key, no
membership, no transaction.

## Why the design is shaped this way

### One global tree, not one per proposal

Members register once and vote on every future proposal. The alternative —
registering per proposal — leaks turnout intent up front and, worse, shrinks the
anonymity set to whoever bothered to register for *that* vote. Here the
anonymity set is every registered member (150 when everyone has joined), for
every proposal, even if only three people vote. Low turnout does not weaken
anonymity.

The `nullifier` is keyed on the proposal, so one registration yields exactly one
ballot per proposal, forever.

### The contracts hash nothing

`MemberRegistry` stores a root and a count. Every append arrives with a `join`
proof that the new root is the old root with one empty slot filled. Two reasons:

- There is no Solidity Poseidon2 to keep bit-identical with Noir's. That
  mismatch is the classic silent failure in designs like this, and here it
  cannot happen — the only Poseidon2 in the system is barretenberg's, reached
  from Noir in-circuit and from bb.js off-chain.
- The root is trustless. Nobody, including the DAO, can move it to a tree of
  their choosing — for instance one padded with extra leaves whose secrets they
  hold, which would let them mint ballots. The only reachable roots are the ones
  honest sequential appends produce.

`EMPTY_ROOT` is a hardcoded constant rather than a constructor argument, so a
deployer cannot seed the registry with a pre-stuffed tree. `nargo test -p
dao_zk` and `node scripts/print-constants.mjs` both re-derive it.

### Why the direction is public

Hiding per-ballot direction as well would need homomorphically added ciphertexts
and someone to decrypt the sum at the end. Whoever holds that key can decrypt
individual ballots — which is precisely the thing the requirement rules out —
so it would have to be a threshold key split across members, with a
distributed key generation, a liveness requirement at reveal time, and a
recovery story when members go missing.

Anonymity gets the stated property without any of that. There is no key, so
there is no key holder to compromise, subpoena or lose. The cost is that an
observer sees "someone voted yes", which reveals nothing about any individual as
long as the anonymity set is meaningful.

If per-ballot secrecy is later required on top of unattributability, the
upgrade path is threshold ElGamal on Baby Jubjub with the tally decrypted by
brute-force discrete log over 0..150 — the circuit and registry here would
carry over unchanged.

## What is *not* hidden

Stated plainly, because the gap between "anonymous" and "private" is where these
systems get people hurt.

**The running tally.** `tally()` reverts before the deadline, but that is about
voting process, not confidentiality: the counters are in public storage and each
ballot's direction is in its calldata, so anyone can follow the count live.
Treat the deadline gate as a convenience, not a guarantee.

**Turnout, and who is eligible.** The number of ballots, their timing, and the
full list of registered members are all public.

**Metadata, which is the real residual risk.** The chain is clean; the network is
not. A relayer sees the IP address that handed it a ballot, and it sees the
direction. It does not learn *which member* — that is what the proof hides — but
an operator who logs IPs and knows members' IPs from elsewhere can bridge the
gap. Mitigations, in order of effect: submit over Tor or a VPN; use relayers the
DAO does not run; use more than one; do not submit a ballot in the same minute
as any other identifiable action.

**Anonymity set size.** With one registered member the scheme hides nothing;
`member-vote.mjs` warns below two. The property is only as strong as *N*.

**Receipt-freeness — this scheme does not have it.** A member can prove how they
voted by revealing their secret and pointing at the nullifier they spent. So it
resists surveillance but not vote-buying or coercion by someone the member
cooperates with. Fixing that needs a MACI-style design where a coordinator
re-randomises ballots and members can invalidate an earlier vote with a key
change — a much larger system, with a coordinator who must be trusted for
correctness (though not for privacy).

<a id="censorship"></a>**Censorship.** A relayer can silently drop a ballot. The
contract cannot tell. Members should be able to reach several independent
relayers, and should be able to fall back to self-submission from a wallet with
no history — accepting that self-submission from their *known* wallet
de-anonymises them (`member-vote.mjs` refuses to do it without `--self-submit`).

**Secret custody.** The voting secret is `keccak(signature over a fixed string)`.
Anyone who obtains that signature can vote as the member *and* can recompute
every nullifier they have ever spent, retroactively de-anonymising their entire
voting history. The DAO must never ask a member to sign that string, and a
member must never sign it for a site they do not control. Losing the wallet
loses the vote: a tree entry cannot be rotated without a fresh membership token.

**Deploy-time trust.** The verifier contracts must be the ones generated from
these circuits. Anyone can check: run `scripts/build-circuits.sh` and compare the
deployed bytecode. The registry and ballot contracts hold their verifier
addresses as immutables, so a circuit change means redeploying both and starting
a new tree.

## Costs

Measured on anvil (`scripts/demo-local.sh`) and in `forge test --gas-report`.

| Operation | Total gas | Of which contract logic |
| --- | --- | --- |
| `join`, once per member | ~2.35M | ~112k |
| `castBallot`, per ballot | ~2.24M | ~66k |
| `createProposal` | ~128k | all of it — no proof involved |
| proving, either circuit | ~200 ms on a laptop | — |

The circuits are small (85 and 67 ACIR opcodes); ~95% of the gas is the ZK-Honk
verifier, which costs the same no matter how trivial the circuit. On mainnet
that is real money per ballot, which is another argument for relayers — and for
an L2.

## Running it

Needs `nargo` 1.0.0-beta.26, `bb` 5.1.0, Foundry, and Node 22.

```bash
npm install
./scripts/build-circuits.sh          # compile circuits, regenerate verifiers
(cd contracts && forge build && forge test)
(cd circuits && nargo test)

anvil                                 # in another terminal
./scripts/demo-local.sh               # deploy, 8 joins, proposal, 3 ballots, tally
```

One member's flow on its own:

```bash
node scripts/member-join.mjs   --member 3 --token 3
node scripts/create-proposal.mjs --proposer 0 --text "Fund the grants round" --hours 24
node scripts/member-vote.mjs   --member 3 --proposal 0 --support yes --relayer <relayer key>
node scripts/read-tally.mjs    --proposal 0
```

Against a real network, set `MEMBERSHIP_NFT` to the DAO's existing NFT so no dev
token is deployed, plus `RPC_URL` and `DEPLOYER_KEY`.

If `node` cannot find `node_modules` here, check `NODE_OPTIONS` — a Yarn PnP
loader inherited from an enclosing project hijacks module resolution.
`unset NODE_OPTIONS` fixes it.

## Tests

- `circuits/`: 13 Noir tests — the Merkle path, the empty root constant, and
  every rejection the circuits are supposed to make.
- `contracts/test/MemberRegistry.t.sol`, `PrivateBallot.t.sol`: contract logic
  against a mock verifier, including which public inputs each contract binds
  into a proof.
- `contracts/test/RealProofs.t.sol`: real Honk proofs through the real
  verifiers — the seam where a stale verifier or a reordered public input would
  otherwise go unnoticed. Fixtures from `node scripts/generate-fixtures.mjs`.

## What I would do before this holds real money

- An audit of the circuits and of the `join` insertion argument in particular.
- Multiple independent relayers, and a client that picks one at random over Tor.
- Deploy on an L2; 2.24M gas per ballot is unpleasant on mainnet.
- Decide whether receipt-freeness matters to this DAO. If contested votes are
  the point, it probably does, and that is a MACI-shaped rewrite rather than an
  addition.
