# Anonymous DAO voting — notes

Goal: yes/no votes that anyone can tally but that **nobody, including the DAO,
can attribute to a member**. This follows the Semaphore pattern: members sign up
once with a hidden identity, and each vote proves "I am one of the registered
members, and this is my only vote on this proposal" without saying which member.

## Pieces

| Path | What it is |
| --- | --- |
| `circuits/vote/src/main.nr` | Noir circuit. Private inputs: member secret, leaf index, Merkle path. Public inputs: `root`, `scope`, `vote`, `nullifier`. |
| `contracts/src/MemberGroup.sol` | NFT-gated registration. One commitment per token, stored in an append-only Poseidon Merkle tree (depth 10, up to 1024 members). |
| `contracts/src/AnonymousVoting.sol` | Proposals, proof-checked `castVote`, nullifier set, `tally`. |
| `contracts/verifier/HonkVerifier.sol` | UltraHonk verifier generated by `bb` from the circuit (ZK, keccak transcript). |
| `contracts/src/MembershipNFT.sol` | Soulbound stand-in for your existing NFT, for local chains only. |
| `contracts/vendor/PoseidonT3.sol` | Poseidon hash in Solidity, vendored. Same hash as `poseidon::bn254::hash_2` in Noir and `poseidon-lite` in JS. |
| `contracts/script/Deploy.s.sol` | Deploys and wires NFT → MemberGroup → AnonymousVoting ← HonkVerifier. Writes `deployments/<chainId>.json`. |
| `scripts/member.mjs` | The member's client: `join` (secret → commitment → register) and `vote` (secret → proof → relayer). |
| `scripts/relayer.mjs` | A small HTTP relayer that submits `castVote` from its own wallet. |
| `scripts/demo.sh` | Full run on a fresh anvil chain. |

Wiring: `AnonymousVoting` holds immutable references to `MemberGroup` (current
root, member count, NFT address) and `HonkVerifier`. `MemberGroup` holds the NFT
address. Nothing has an owner or admin key after deployment.

### Cryptography in one paragraph

- `secret`: 31 random bytes, generated and kept on the member's machine.
- `commitment = Poseidon(secret)`: registered publicly as a Merkle leaf.
- `scope = keccak(chainId, votingContract, proposalId) mod p`: set by the contract.
- `nullifier = Poseidon(secret, scope)`: one per member per proposal. You can't
  link it to the commitment, and you can't link one member's nullifiers across
  proposals, unless you have the secret.

The circuit checks that `vote ∈ {0,1}`, that `Poseidon(secret)` is a leaf under
`root`, and that `nullifier` is computed correctly. The contract checks that
`root` and `scope` are the proposal's own values, that `nullifier < p` and
hasn't been used, and then counts `vote`. The vote and nullifier are public
inputs to the proof, so whoever submits the proof can't change them.

## End-to-end: one member, one proposal

Actors: **Deployer** (the DAO, deploys once), **Alice** (a member; their wallet
`A` holds NFT #7), **Proposer** (any NFT holder), **Relayer** (wallet `R`, which
anyone can run; the DAO may run one).

### 0. Deployment (once, not per vote)
- **Tx sent by:** the deployer's wallet.
- **Observer learns:** the contract addresses, which NFT gates registration, the
  verifier code (so it can be checked against the circuit), and
  `minAnonymitySet`. Nothing about members.

### 1. Alice joins anonymous voting (once, for all future proposals)
Off-chain, on Alice's machine (`node scripts/member.mjs join --token-id 7`):
generate `secret`, save it locally (mode 0600), and compute `commitment`.

- **Tx:** `MemberGroup.register(7, commitment)`
- **Sent by:** Alice's NFT wallet `A`. It has to be: the contract checks
  `ownerOf(7) == msg.sender`, and this is how one-member-one-leaf is enforced.
- **Observer learns:** "wallet A / token #7 has joined, with commitment C at leaf
  index i", plus the new root. That's public by design: membership is already
  public, and a commitment reveals nothing about any vote. The observer also
  learns who has *not* joined, and so can't vote anonymously.

### 2. A proposal opens
- **Tx:** `AnonymousVoting.createProposal("…", votingPeriod)`
- **Sent by:** the proposer's own wallet (any NFT holder). Proposing isn't anonymous.
- **Observer learns:** the proposer, the text, the deadline, and `scope`. It also
  learns the **frozen root** and `eligible` = number of members registered at that
  moment. Only those members can vote, and each vote hides among exactly those
  `eligible` people. Anyone who joins later can vote on later proposals only. The
  contract refuses to open a proposal if `eligible < minAnonymitySet`.

### 3. Alice votes (`node scripts/member.mjs vote --proposal 1 --yes`)
Off-chain, on Alice's machine, with no transaction and no signature from `A`:
1. Read the proposal (`root`, `scope`, `eligible`) and all `MemberRegistered`
   events. Rebuild the tree from the first `eligible` leaves and check that it
   reproduces the proposal root. This uses no data from the DAO's website.
2. Compute `nullifier = Poseidon(secret, scope)` and their Merkle path.
3. Run the Noir circuit (noir_js) and produce an UltraHonk proof (bb.js,
   `verifierTarget: 'evm'`, the zero-knowledge variant). This takes a few
   seconds on a laptop.
4. POST `{proposalId, support, nullifier, proof}` to a relayer. Nothing in that
   payload identifies Alice.

- **Tx:** `AnonymousVoting.castVote(1, true, nullifier, proof)`
- **Sent by:** the **relayer's wallet `R`**, never `A` and never a wallet funded
  from `A`. `castVote` is permissionless, and the contract only trusts the proof.
- **Observer learns:** "one of the `eligible` members voted yes on proposal 1 at
  time t through relayer R", plus a nullifier that looks random. It can't tell
  which leaf, token or wallet cast the vote. It can't tell whether this voter
  also voted on other proposals, because nullifiers differ per scope. It can't
  link the vote to Alice's registration either. A second vote from Alice
  (`AlreadyVoted`), a vote after the deadline, or a changed `support` (invalid
  proof) all revert.

### 4. Tally (after the deadline)
- **No transaction.** Anyone calls `tally(1)` (an `eth_call`), which returns
  `(yes, no, eligible)` and reverts while voting is open. Every vote is also a
  public `VoteCast` event, so anyone can recount independently.
- **Observer learns:** the totals and turnout (`yes + no` out of `eligible`), but
  not who voted or who abstained.

`scripts/demo.sh` runs all of the above for 5 members and prints which wallets
sent the vote transactions: all 5 came from the relayer.

## What each party can learn

| Party | Learns | Does not learn |
| --- | --- | --- |
| Chain observer | Who joined, proposals, every vote's direction and time, totals | Which member cast any vote |
| DAO (deployer / site operator) | Same as the chain observer; there is no admin key or private data | Member secrets, and therefore vote attribution |
| Relayer operator | The vote and nullifier (both public anyway), **the requester's IP address, and the exact time** | The member's identity, unless the IP gives it away (see below) |
| RPC provider Alice reads through | Their IP address and which proposal they queried | Their vote. Proving is local and the proof is not sent through the RPC |

## What still leaks (rules for members and the DAO)

The cryptography only hides *which leaf* voted. These leaks are outside the
proof, and in practice they break anonymity more often than the crypto does:

1. **Sending the vote from your own wallet** (or a wallet funded from it)
   attributes the vote on the spot. `member.mjs vote` never loads a member key.
   If no relayer is available, submit from a wallet with no funding link to you.
2. **IP address at the relayer.** If the DAO runs the relayer and its website
   logs member IPs, the DAO can match the two. Reach relayers over Tor or a
   shared VPN, and let members choose any relayer (all relayers are equivalent).
   `relayer.mjs` logs nothing, but members have no way to verify that.
3. **Timing.** Votes are public and appear right away. "I just voted", combined
   with a single `yes` appearing a minute later, is an attribution. Relayers
   should batch requests or add random delays (not implemented here). Members
   shouldn't vote right after telling someone they are about to.
4. **Running tally is public.** Counts are chain state, and `tally()` reverting
   before the deadline doesn't hide them. This doesn't reveal who voted what,
   but it allows bandwagoning. Hiding it until the deadline needs
   threshold or timelock encryption (e.g. Shutter-style keypers) or a MACI
   coordinator, which is a larger system.
5. **Small or unanimous electorates.** The tally itself can reveal votes: if all
   `eligible` members vote and the result is unanimous, everyone's vote is known.
   `minAnonymitySet` is 3 in the demo. For contested votes, set it much higher,
   and encourage all 150 members to join before proposals open.
6. **Custody of the secret.** Anyone who gets a member's secret can vote as that
   member. They can also recompute the member's nullifier for every past
   proposal, which **de-anonymises that member's entire voting history**. Treat
   it like a private key. Never paste it into a website, including the DAO's.
   The proving client must run locally (this repo) or be a pinned,
   reproducibly built static bundle. A DAO-served web prover could exfiltrate
   secrets.
7. **Receipts and coercion.** A member can *prove* how they voted by revealing
   their secret, so votes can be bought or coerced. Preventing that
   (receipt-freeness) needs MACI-style key changes through a coordinator. That
   design is out of scope here.
8. **ZK flavour.** The verifier and prover must use the ZK target (`-t evm` /
   `verifierTarget: 'evm'`). The `*-no-zk` targets don't hide the witness.

## Operational caveats in this core

- **No key rotation or revocation.** A lost secret means that token can't vote
  (the token is already registered). Adding rotation means removing leaves,
  which requires tree updates and a root history.
- **Transferable NFTs.** Registration is per token, and the leaf stays with
  whoever registered it. If your membership NFT is transferable, the old holder
  keeps voting power and the new holder can't register. Use a soulbound NFT, or
  add revocation.
- **Proposal creation** is open to any NFT holder. Put it behind your governor
  if you want.
- **Setup:** UltraHonk uses a universal SRS, so there is no per-circuit trusted
  setup ceremony. If you change the circuit, rerun `scripts/build-circuit.sh` and
  redeploy the verifier.

## Running it

Requires nargo 1.0.0-rc.2, bb 5.2.0 (versions must match the npm packages),
foundry, node ≥ 20 and jq.

```sh
npm install
./scripts/build-circuit.sh   # nargo test + compile, regenerate HonkVerifier.sol
forge build && forge test    # contracts (verifier is mocked in unit tests)
./scripts/demo.sh            # own anvil on a free port (default 28545), relayer on the next port, full flow with real proofs
```

Against a chain you already have running:

```sh
PRIVATE_KEY=0x… [MEMBERSHIP_NFT=0x…] forge script contracts/script/Deploy.s.sol --rpc-url $RPC_URL --broadcast
RELAYER_PRIVATE_KEY=0x… RPC_URL=$RPC_URL PORT=8546 node scripts/relayer.mjs
MEMBER_PRIVATE_KEY=0x… RPC_URL=$RPC_URL node scripts/member.mjs join --token-id 7
RPC_URL=$RPC_URL node scripts/member.mjs vote --proposal 1 --yes --relayer http://127.0.0.1:8546
```

Generated and ignored: `node_modules/`, `circuits/vote/target/`, `out/`,
`cache/`, `broadcast/`, `deployments/`. The generated `HonkVerifier.sol` is
committed under `contracts/verifier/` so that `forge build` works without bb.
