# Anonymous DAO voting — notes

## The idea in one paragraph

Each member registers once, from their own wallet, putting a random
**identity commitment** `C = Poseidon(identityNullifier, identityTrapdoor)`
into an onchain Merkle tree. Every NFT gets one leaf. When a proposal opens it
records a snapshot of that tree's root. To vote, a member proves in zero
knowledge: *"I know the secrets behind one of the leaves under this root, my vote
is 0 or 1, and `nullifierHash = Poseidon(identityNullifier, scope)`"*. `scope`
is a value unique to the proposal. The proof doesn't say which leaf. The
nullifier hash stops a second vote on the same proposal, and it looks unrelated
to the same member's nullifier on any other proposal. The vote transaction is
sent by a **relayer** wallet, never the member's, so `msg.sender` doesn't link
the vote to anyone.

### Running it

Toolchain: nargo 1.0.0-rc.2, bb 5.2.0, `@noir-lang/noir_js` 1.0.0-rc.2 and
`@aztec/bb.js` 5.2.0 (both pinned to match the CLIs), and foundry.

```bash
npm install
npm run build:circuit     # nargo test + compile, bb write_vk / write_solidity_verifier (--verifier_target evm)
npm run build:contracts   # forge build
(cd contracts && forge test)
npm run demo              # anvil on :8546, relayer on :8788, 3 members, 3 votes, replay rejected, tally
```

To deploy against an existing chain and the real NFT:
`RPC_URL=... PRIVATE_KEY=... MEMBERSHIP_NFT=0x... MIN_ANONYMITY_SET=100 scripts/deploy.sh`.

If you change the circuit, run `npm run build:circuit` to regenerate the
verifier, then `node scripts/make-fixture.mjs` to regenerate the test proof.

## End-to-end: one member, one proposal

Wallets involved:
- **Deployer**: the DAO's deploy key.
- **Member wallet**: Alice's public wallet that holds membership NFT #7.
- **Proposer wallet**: any member's wallet.
- **Relayer wallet**: a hot wallet the relayer operator funds. It has nothing to
  do with any member.

### 0. Setup (once): deploy

`HonkVerifier`, `MemberRegistry(nft)`, `AnonymousVoting(registry, verifier, minAnonymitySet)`.

- **Sent by:** deployer wallet (three contract creations).
- **Observer learns:** the contract addresses and the parameters. There are no
  admin functions. After deployment the deployer can't add leaves, change roots,
  change the verifier or read anything anyone else can't.

### 1. Alice joins the vote (once, reused for every future proposal)

Offchain, `register.mjs` generates two random field elements
(`identityNullifier`, `identityTrapdoor`) and computes `C`. It saves them to an
identity note (`.notes/…json`, mode 0600) **before** sending anything, so a
crash can't lose a registered identity.

**Tx: `MemberRegistry.register(tokenId=7, C)`**
- **Sent by:** Alice's member wallet. It has to be, because the contract checks
  `ownerOf(7) == msg.sender`.
- **Observer learns:** "the holder of NFT #7 (Alice, per your public registry)
  registered commitment `C` at leaf index *i*". The event is
  `MemberRegistered(tokenId, commitment, leafIndex, newRoot)`. `C` is a hash of
  two random 254-bit values, so it can't be brute-forced and says nothing about
  any vote. Membership is public anyway, so this leaks nothing new.
- The contract keys registration by **token**, not wallet. Moving the NFT to
  another wallet doesn't get a second leaf.

Registration isn't tied to any proposal. Ideally every member registers as part
of onboarding, well before any contested vote.

### 2. A proposal opens

**Tx: `AnonymousVoting.createProposal(tokenId, descriptionHash, votingPeriod)`**
- **Sent by:** the proposer's member wallet (it must hold an NFT).
- **Observer learns:** who proposed and the description hash. The contract also
  publishes a snapshot of the current member-tree `root` and `memberCount`, plus
  `scope = keccak256(chainId, votingContract, proposalId) mod p` and the
  deadline. The snapshot defines the **anonymity set**: everyone registered at
  that moment. The call reverts if fewer than `minAnonymitySet` members are
  registered.

### 3. Alice votes (`scripts/vote.mjs`, no private key involved)

Offchain, on Alice's machine:
1. Read the proposal (`root`, `memberCount`, `scope`, `deadline`).
2. Rebuild the member tree by replaying `MemberRegistered` events into a
   `@zk-kit/imt` mirror (Poseidon, depth 10, zero leaf 0), up to `memberCount`
   leaves. After each leaf, check the local root against the event's `newRoot`,
   and at the end against the proposal's root. This is also a live check that
   Solidity and JS Poseidon agree.
3. Find her leaf and build the Merkle path. Compute
   `nullifierHash = Poseidon(identityNullifier, scope)`.
4. Run `Noir.execute` to get the witness, then
   `UltraHonkBackend.generateProof(witness, { verifierTarget: "evm" })` (about
   0.4 s natively). The same code runs in a browser. Verify the proof locally
   and check that the public inputs are `[root, scope, vote, nullifierHash]` in
   that order.
5. POST `{proposalId, support, nullifierHash, proof}` to a relayer. Nothing in
   the payload identifies her.

**Tx: `AnonymousVoting.castVote(proposalId, support, nullifierHash, proof)`**
- **Sent by:** the **relayer wallet**. The relayer does a `staticCall` first so
  it never pays gas for a bad proof, can wait a random delay
  (`RELAY_MAX_DELAY_MS`), then sends. `castVote` ignores `msg.sender`, so anyone
  can submit it.
- **Contract:** takes `root` and `scope` from the proposal's storage, not from
  calldata. It rejects closed proposals and used or out-of-field nullifiers,
  calls `verifier.verify(proof, [root, scope, vote, nullifierHash])`, and only
  after that returns true does it mark the nullifier used and add 1 to yes or
  no. It emits `VoteCast(proposalId, nullifierHash, support)`.
- **Observer learns:** "some member of this proposal's snapshot voted yes (or
  no)", plus the relayer's address and the time. The nullifier hash is a fresh
  pseudorandom value per proposal. Without Alice's `identityNullifier` it can't
  be linked to her leaf, her NFT, her wallet or her votes on other proposals.
- The relayer (or a mempool front-runner) can't change the vote. `support` is a
  public input bound by the proof (see `test_FlippedVoteRejected`). The proof
  also only counts against this proposal's root and scope
  (`test_WrongProposalScopeRejected`). A replay reverts with `AlreadyVoted`
  (checked in `demo.sh`).

Gas: about 3M per `castVote`, most of it in UltraHonk verification. The
relayer pays it, so the DAO should fund the relayer wallet(s).

### 4. Tally

No transaction. After the deadline, anyone calls `result(proposalId)`, which
returns `(yes, no, passed)`. Before the deadline it reverts with `VotingOpen`.

## Who can learn how Alice voted?

**Nobody**, from chain data, as long as:
1. Her identity note stays secret.
2. She never sends `castVote` from a wallet linked to her. That includes a
   burner she funded from her own wallet.
3. The anonymity set is reasonably large.
4. The relayer doesn't see her network identity.

"Us" included: the DAO has no admin key and no view of the offchain proving,
and the relayer only gets the same data that lands onchain.

Limits you should know about. None of these break the design, but all of them
are real:

- **The tally itself leaks in extreme cases.** If 150 of 150 vote yes, everyone's
  vote is known. More generally the result bounds what each member could have
  done. Any public tally has this limit.
- **The running tally is public.** `result()` is gated by the deadline, but
  `yes`/`no` live in storage and every `VoteCast` event carries `support`, so
  anyone can watch the count move. Combined with timing ("Alice said she just
  voted, and a yes landed 20 s later"), this can point to her. Mitigations:
  relayer random delay or batching, and members voting at unremarkable times.
  Fully hiding the running tally needs encrypted votes (MACI-style coordinator
  or threshold decryption). That is a bigger system with its own trust
  assumptions, so it isn't built here.
- **The relayer sees the requester's IP and timing.** Members should reach it
  over Tor or a VPN. Because `castVote` is permissionless, more than one
  relayer can run (not only the DAO's), and a member can run their own. A
  relayer can **drop** a vote but not alter it. Alice knows her own
  `nullifierHash`, so she can check for her `VoteCast` event and resend through
  a different relayer if it's missing.
- **The anonymity set is whoever was registered at the snapshot.** It is not
  all 150 members. Early on, if only 5 have registered, Alice is 1 of 5. Set
  `MIN_ANONYMITY_SET` high (for example 100) in production and make
  registration part of onboarding.
- **The identity note is both the voting key and the voting history.** Anyone
  holding `identityNullifier` can compute Alice's nullifier for every proposal
  and match them against `VoteCast` events, which reveals all her past votes.
  It is also what can vote for her. Store it like a private key.
- **Not coercion-resistant.** Alice can prove how she voted (by revealing her
  note) if she chooses to. Nothing stops vote-selling. MACI addresses this;
  this design doesn't.
- **No member removal.** Leaves are append-only. A member whose NFT is revoked
  keeps their leaf, so they can still vote on proposals whose snapshot
  includes it. If you need that, run a fresh registry per membership epoch.
- **The NFT contract is trusted for integrity, not privacy.** Whoever can mint
  membership NFTs can add sybil voters. They still can't learn anyone's vote.
- Event replay uses `queryFilter` from `deployBlock` in one call. Public RPCs
  with log-range limits will need chunked queries or an indexer.
- Proving happens client-side and doesn't depend on any server. NoirJS +
  bb.js are the same libraries used in the browser. The Node script is the
  reference, not the final member UX.
