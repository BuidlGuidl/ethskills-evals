# Why every route except `/` is 404 on IPFS

## 1. How the gateway handles your layout

An IPFS gateway has no app server and no rewrite rules. It takes the URL path and looks it up, one piece at a time, in the uploaded folder tree (UnixFS, the IPFS file format):

```
https://<gateway>/ipfs/<CID>/debug
                            └─ look for an entry named exactly "debug" in the root folder
```

Your root folder has these entries: `index.html`, `debug.html`, `404.html`, `_next`. None of them is named `debug`. The gateway **does not guess file extensions**. It never tries `debug` → `debug.html`. So there is no match, and you get **404**. Every other route fails the same way: `/foo` needs an entry called `foo`, but only `foo.html` exists.

`next start`, Vercel, and many local dev servers (`npx serve` with `cleanUrls`) quietly map `/debug` to `debug.html`. That hides the bug locally. A plain IPFS gateway does no such mapping.

Your `out/404.html` doesn't help either. Gateways don't use Next's `404.html` as a fallback. Kubo only uses a file named `ipfs-404.html`, and even then the status code stays 404.

### Why `/` still works

`/` points to the root **folder**, not a file. Gateways have one built-in rule: when a path is a folder that contains `index.html`, serve that file. That's why `/` → `index.html` works. It's the only page that reaches the gateway as a folder.

(Clicking a link from the home page to `/debug` can sometimes work, because the Next router renders it in the browser. A refresh, a shared link, or typing the URL makes the gateway resolve the path, and that returns 404.)

## 2. The fix in `next.config.ts`

Tell Next to put each route in its own folder with an `index.html`, so every route uses the one rule gateways support. SE2 pattern:

```ts
const isIpfs = process.env.NEXT_PUBLIC_IPFS_BUILD === "true";

if (isIpfs) {
  nextConfig.output = "export";          // static HTML files
  nextConfig.trailingSlash = true;       // THE fix: debug.html -> debug/index.html
  nextConfig.images = { unoptimized: true }; // no image optimizer server on IPFS
}
```

`trailingSlash: true` does two things:
- The build writes `debug/index.html` instead of `debug.html`.
- Links generated by Next point to `/debug/`, so they go straight to the folder.

Now a request for `/debug` finds an entry named `debug`. That entry is a folder. The gateway redirects `/debug` → `/debug/` (301) and serves `debug/index.html` (200).

Rebuild from scratch. Don't reuse old output:

```bash
cd packages/nextjs
rm -rf .next out
NEXT_PUBLIC_PRODUCTION_URL="https://myapp.yourname.eth.link" \
  NODE_OPTIONS="--require ./polyfill-localstorage.cjs" \
  NEXT_PUBLIC_IPFS_BUILD=true \
  NEXT_PUBLIC_IGNORE_BUILD_ERROR=true \
  yarn build
```

## 3. What `out/` looks like after the change

```
out/index.html              # /
out/debug/index.html        # /debug/
out/404.html                # not-found page (Next may also emit 404/index.html)
out/<route>/index.html      # one folder per other route, e.g. blockexplorer/index.html
out/_next/...               # JS/CSS chunks, unchanged
```

(Next also writes client-side navigation data files, e.g. `index.txt` and `debug/index.txt`, next to them.)

Key check: apart from `404.html`, **no `<route>.html` files should be left at the root**. A route that is missing from the output entirely probably crashed during prerendering and was skipped without a warning. The usual cause in SE2 is `blockexplorer` touching `localStorage` at import time. Fix that page or rename it to `app/_blockexplorer-disabled`.

## 4. Check from the command line before re-uploading

**a) Check the file layout**

```bash
cd packages/nextjs
ls out/*/index.html                                   # expect out/debug/index.html, ...
find out -maxdepth 1 -name '*.html' ! -name index.html ! -name 404.html
# ^ must print nothing; any hit (e.g. out/debug.html) = trailingSlash not applied
```

**b) Serve `out/` with a server that behaves like a gateway (no extension guessing)**

`python3 -m http.server` works well here: it only serves folder `index.html` files and redirects `/x` → `/x/`, like a gateway. Don't use `npx serve` for this check, because its clean-URL feature hides the bug.

```bash
python3 -m http.server 8080 -d out &
for r in / /debug /debug/; do
  printf '%-10s ' "$r"
  curl -s -o /dev/null -L -w '%{http_code}\n' "http://localhost:8080$r"
done
kill %1
```

Expected: `200` for every route. With the old layout, `/debug` returns `404` here too, so this test catches the bug.

**c) (Optional) Real IPFS check without publishing**

```bash
ipfs add -r --only-hash -Q out          # CID you'd get; must differ from the broken deploy
# or with a local Kubo node:
CID=$(ipfs add -r -Q out); ipfs daemon &
curl -s -o /dev/null -w '%{http_code}\n' -L "http://$CID.ipfs.localhost:8080/debug"   # 200
```

If the CID is the same as the broken deploy, you're uploading the old build.

**d) After uploading, check the public gateway**

```bash
curl -s -o /dev/null -w '%{http_code}\n' -L "https://<CID>.ipfs.<gateway>/debug"   # 200, not 404
```

Test through a subdomain gateway (`<CID>.ipfs.<gateway>`) or your `.eth.link` name. Next's `/_next/...` asset paths start at the site root, so on a path gateway (`/ipfs/<CID>/...`) the page can load without its JS and CSS even when the route itself resolves.
