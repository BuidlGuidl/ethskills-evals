# Unblocking the contract verification ticket

## Short version

The ticket isn't blocked. There is nothing to wait on from ops, and the work is
one command. Run it today, from the machine that did the deploy, not at launch.

## The ticket's premise is wrong

"Waiting on a block explorer API key from ops (ETA next sprint)" is waiting for
nothing. In Scaffold-ETH 2 (foundry flavor), `packages/foundry/.env.example`
already ships a working `ETHERSCAN_API_KEY`, and postinstall copies it to
`packages/foundry/.env`. That is why `yarn verify` works on a fresh checkout
with no setup. Verification has been runnable since the moment the deploy
finished three days ago.

Getting our own key is optional housekeeping we can do whenever — it is not a
launch dependency, and it should never appear as a step in a launch plan. (Same
reason we should never hand a teammate an env template with a blank
`ETHERSCAN_API_KEY=` to fill in: the value is already there.)

So: take the ticket off "blocked".

## What we run

```bash
yarn verify --network base
```

That's it. Same `--network base` we used for the deploy.

## What actually needs to be in place

One real constraint, and it is not an API key:

- **Run it from the checkout that performed the deploy.** `yarn verify` replays
  `packages/foundry/broadcast/run-latest.json` to learn what was deployed at
  what address with what constructor args. Whoever ran
  `yarn deploy --network base` three days ago has that file; nobody else does.
  If they run it on a different clone, or that broadcast directory has been
  cleaned/regenerated by other work, the command has nothing to replay.
- Corollary: whoever did the deploy should run this, and should do it before
  anything else touches `broadcast/` — which is a second reason not to sit on
  it for a month.
- `packages/foundry/.env` exists with `ETHERSCAN_API_KEY` (true by default via
  postinstall; confirm with a quick look if unsure).

If the broadcast artifacts turn out to be gone, verification is still possible
but stops being one command — it becomes a per-contract
`forge verify-contract <address> <Contract> --chain base` with the exact
constructor args and the exact compiler settings reconstructed by hand. That is
the failure mode we are risking by deferring, and it gets harder, not easier,
with time.

## Timing: now, not at launch

Verify belongs in the same breath as deploy — immediately after
`yarn deploy --network base`, not folded into a launch checklist weeks out. We
already missed that window by three days; the fix is to close it today, not to
push it another month.

Why the timing matters:

1. **Right now, every user and integrator looking at our contracts on Basescan
   sees opaque bytecode.** The contracts are live and the app is working against
   them — that is already a public surface. Anyone evaluating us, integrating
   with us, or trying to audit what they're approving has nothing to read.
2. **We are debugging a live contract without source on the explorer.** If
   something goes wrong on Base between now and launch, we lose the explorer's
   read/write tabs, decoded transactions and readable revert reasons — exactly
   when we most want them.
3. **The `run-latest.json` dependency decays.** A month of branch switching,
   clean checkouts, a new laptop, or a teammate running a local deploy in that
   repo can all cost us the artifact that makes this a one-liner.
4. **Bundling it into the launch run reintroduces risk at the worst moment.**
   Launch day is when you want a checklist of things already known to work, not
   a first-ever run of a command against mainnet. If verification hits a
   surprise (metadata mismatch, wrong compiler version pinned, missing
   artifact), we want to find that out on a quiet Tuesday, not ten minutes
   before the announcement.

There is no upside to batching it. Verification is idempotent, costs nothing,
touches no onchain state, and changes nothing about the deployed contracts.

## What I'd tell the teammate

Fold verification *out* of the launch checklist. A launch checklist should carry
go/no-go conditions — walk the full user journey against the live contracts with
a real wallet and real money before the frontend is publicly reachable, and put
one real transaction through the public URL after it's deployed. "Verify the
contracts" isn't one of those; it's deploy-time hygiene we owe from three days
ago.

## Concrete next step

Whoever ran the deploy: from that same checkout,

```bash
cd packages/foundry   # or from repo root
yarn verify --network base
```

then paste the Basescan links into the ticket and close it.
