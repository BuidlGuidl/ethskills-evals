The tip jar works locally from start to finish on a Base fork. I sent a tip from the terminal and one through the page in a real browser, and each moved real Base USDC from a test identity to the recipient. Nothing was uploaded and nothing is committed.

**Contract** (`packages/foundry/contracts/TipJar.sol`)
- `tip(amount, message)` takes USDC from the tipper and sends it straight to a fixed `recipient`, so the contract never holds money. The tipper has to approve first, and messages are capped at 280 bytes.
- The latest tips are stored onchain and read with `getRecentTips(n)`. That way the static site shows the feed without an indexer. Scanning Base event history from the browser would overload the RPC.
- The deploy script checks that USDC exists on the chain, so running it against a plain `yarn chain` fails. On Base it requires `TIP_RECIPIENT` to be set.
- 6 tests pass. One of them runs against real Base USDC and is skipped unless `BASE_RPC_URL` is set.

**Local workflow** (full steps in README.md)
- `yarn fork:base` starts a copy of Base on your machine with chain id 31337. Transactions signed for 31337 can't be replayed on Base, so no real money is at risk.
- `yarn deploy`, then `yarn start`.
- `yarn fund-usdc <address> [amount]` gives a test identity USDC in the real USDC contract on the fork, plus gas. It refuses to run unless the local chain is the Base fork.
- `yarn fork base` didn't pass the network name through and forked Ethereum mainnet instead, which is why there's a separate `fork:base` script.
- Funding changes a balance without creating a block, and the page only refreshes on new blocks. The script now mines a block so the new balance shows up right away.

**Page** (`app/page.tsx` plus `app/_components/`): stats, a tip form that does approve then tip, and the recent-tips feed.

**Production build**
- With `NEXT_PUBLIC_IPFS_BUILD=true`, the site targets Base only (the throwaway browser wallet is off) and builds as plain static files.
- `next.config.ts` stops the build if there is no Base TipJar deployment, so a site with no contract can't ship.
- `yarn ipfs:build` runs the whole build. I tested it with a fake Base entry, then removed the entry.
- The TypeScript types for `targetNetworks` come from the local chain, because SE-2 only derives contract types from the first network. Both chains run the same contract, so this is safe.

**DEPLOY.md** gives exact commands in order:
1. Deploy to Base and check the result onchain, then verify on Basescan.
2. Build and check the files before uploading, including a local test serve.
3. Upload with `bgipfs`, which the project already includes.
4. After upload: fetch the gateway's `index.html` and compare it byte-for-byte with the local build, load every script, check routes, confirm the contract address is in the served code, then send a small real tip.

- **Gateway choice matters.** The build uses paths that start at the site root, so it only works on subdomain gateways, DNSLink or ENS, not on `/ipfs/<cid>/` path URLs.
