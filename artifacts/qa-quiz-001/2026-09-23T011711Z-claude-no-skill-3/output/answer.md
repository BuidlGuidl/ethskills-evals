# Why `useScaffoldReadContract({ contractName: "USDC" })` silently returned `undefined`

## 1. The silence: the hook never made a request

`useScaffoldReadContract` is not a thin wrapper around wagmi's `useReadContract`. It is
name-based, not address-based. Internally it does roughly this:

```ts
const { data: deployedContract } = useDeployedContractInfo({ contractName });

return useReadContract({
  chainId: targetNetwork.id,
  address: deployedContract?.address,
  abi: deployedContract?.abi,
  functionName,
  args,
  query: {
    // the important line
    enabled: !Array.isArray(args) || !args.some(arg => arg === undefined),
    ...
  },
});
```

`useDeployedContractInfo` looks `contractName` up in the **contracts registry** —
the merge of `packages/nextjs/contracts/deployedContracts.ts` and
`packages/nextjs/contracts/externalContracts.ts`, keyed by the *current target
network's chain id*. There was no `USDC` key for chain `8453`, so
`deployedContract` was `undefined`, so `address` and `abi` were both `undefined`.

wagmi's `useReadContract` treats a missing `address`/`abi` as "not ready yet": the
query is left disabled and it never reaches the transport. So:

- **No runtime error** — a missing key in a plain TS object is `undefined`, not a throw.
  The typing is `GenericContractsDeclaration`, and `"USDC"` was still an accepted
  string at the call site, so TS didn't complain either (and would only have complained
  if the registry had been narrow enough to produce a union of known names — with
  nothing registered on 8453 the inferred name union is empty/`never`-ish and the error,
  if any, is easy to ignore in a dev overlay).
- **No failed request in the network tab** — because there was no request at all. The
  query was never enabled, so no `eth_call` was ever sent to the RPC.
- **`data` stays `undefined` forever**, and `undefined` renders as nothing in JSX.

The only breadcrumb Scaffold-ETH leaves is a console warning from
`useDeployedContractInfo` along the lines of `"<contractName> not found on chain <id>"`
(and `useScaffoldWriteContract` pops a `notification.error` for the same condition —
reads just stay quiet). If you're only watching the UI and the network tab, you see
absolutely nothing.

**Debugging rule of thumb:** a Scaffold-ETH read hook that yields `undefined` with zero
network traffic is almost always a *registration/chain-id* problem, not an RPC or ABI
problem. An actually-wrong address or ABI produces a visible failed `eth_call`.

## 2. Why the teammate's fix self-destructed

`packages/nextjs/contracts/deployedContracts.ts` is **generated output, not source**.
Its header says so:

```ts
/**
 * This file is autogenerated by Scaffold-ETH.
 * You should not edit it manually or your changes might be overwritten.
 */
```

In the hardhat flavor, `yarn deploy` runs `hardhat deploy` and then the
`generateTsAbis` script (`packages/hardhat/scripts/generateTsAbis.ts`, wired as a
hardhat-deploy post-run script). That script reads `packages/hardhat/deployments/**`
and **rewrites the whole file from scratch**. It does not merge, patch, or preserve
anything already in there.

So pasting USDC into that file works exactly until the next `yarn deploy` (or
`yarn deploy --network base`, or a fresh `yarn chain` + deploy), at which point the
file is regenerated from the deployments directory — which contains only contracts
*this repo* deployed. USDC was deployed by Circle, has no artifact in
`packages/hardhat/deployments`, and therefore vanishes. Blank page again.

This is also why it "worked all week": nobody ran a deploy for a week.

## 3. The correct registration

Third-party / pre-existing contracts go in **`packages/nextjs/contracts/externalContracts.ts`**.
That file is hand-maintained, is never touched by codegen, and is merged with
`deployedContracts` by `utils/scaffold-eth/contract.ts` (`contracts = deepMergeContracts(deployedContracts, externalContracts)`),
so `useScaffoldReadContract`, `useScaffoldWriteContract`, `<Address />`,
the Debug Contracts page, etc. all pick it up under the name you give it.

Keys are chain ids. Base mainnet is **8453**. Native (Circle-issued) USDC on Base is
**`0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`** — 6 decimals. (Do not use
`0xd9aA...` USDbC, the bridged legacy token, unless you specifically want that.)

USDC on Base is a **proxy** (`FiatTokenProxy`), so the ABI you want is the
implementation's ERC-20 ABI, not the proxy's. For `balanceOf` the standard ERC-20 ABI
is plenty, and viem ships one:

```ts
// packages/nextjs/contracts/externalContracts.ts
import { erc20Abi } from "viem";
import { GenericContractsDeclaration } from "~~/utils/scaffold-eth/contract";

/**
 * @example
 * const externalContracts = {
 *   1: { DAI: { address: "0x...", abi: [...] } },
 * } as const;
 */
const externalContracts = {
  8453: {
    USDC: {
      address: "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      abi: erc20Abi,
    },
  },
} as const;

export default externalContracts satisfies GenericContractsDeclaration;
```

If you need USDC-specific methods (`permit`, `transferWithAuthorization`,
`blacklist`, `masterMinter`, …), paste the full FiatTokenV2_2 ABI in place of
`erc20Abi` — fetch it from the *implementation* address on BaseScan, not the proxy.
The `as const` matters: it's what gives Scaffold-ETH's generics the literal ABI needed
to type `functionName` and `args`.

### Two things to check alongside it

1. **Target network.** The chain-id key must match
   `scaffoldConfig.targetNetworks` in `packages/nextjs/scaffold.config.ts`. If the app
   is still pointed at `chains.hardhat` (31337) in dev, a `8453` entry won't be found
   and you get the exact same silent `undefined`. Either set
   `targetNetworks: [chains.base]`, or add a 31337 entry too (e.g. a mock USDC you
   deploy locally, or a mainnet fork where the real address exists).
2. **Guard the `args`.** `connectedAddress` is `undefined` before the wallet connects,
   which also disables the query — that's expected, but it means "renders nothing" has
   two possible causes. Render an explicit "connect your wallet" state so the two are
   distinguishable, and format with 6 decimals:
   `formatUnits(usdcBalance ?? 0n, 6)`.

## Summary of the arc

| Stage | What happened |
|---|---|
| Original bug | `USDC` was in no contracts file for chain 8453 → `useDeployedContractInfo` returned `undefined` → wagmi query stayed disabled → no RPC call, no error, `data === undefined`, blank render |
| The "fix" | Entry pasted into `deployedContracts.ts`, which *is* the registry, so lookups succeeded |
| The regression | `yarn deploy` ran `generateTsAbis`, which regenerates `deployedContracts.ts` wholesale from `packages/hardhat/deployments/` — the hand-added USDC entry had no deployment artifact and was overwritten away |
| The fix | Put USDC in `packages/nextjs/contracts/externalContracts.ts` under key `8453`, address `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`, ERC-20 ABI, `as const` — that file is source, never regenerated, and is deep-merged into the same registry |
