# Why `useScaffoldReadContract({ contractName: "USDC" })` rendered nothing

## TL;DR

USDC is not a contract *you* deploy, so it never belongs in
`deployedContracts.ts` — that file is machine-generated and rewritten on every
`yarn deploy`. Third-party/pre-existing contracts go in
`packages/nextjs/contracts/externalContracts.ts`, keyed by chain id (`8453` for
Base), and Base mainnet USDC is
`0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913` (6 decimals, ERC-20 behind a
proxy — register the ERC-20/implementation ABI, not the proxy ABI).

---

## 1. Why the hook returned `undefined` silently instead of erroring

`useScaffoldReadContract` is a thin wrapper. Roughly:

```ts
const { data: deployedContract } = useDeployedContractInfo({ contractName });

return useReadContract({
  chainId: targetNetwork.id,
  address: deployedContract?.address,   // <-- undefined
  abi: deployedContract?.abi,           // <-- undefined
  functionName,
  args,
  query: { enabled: !Array.isArray(args) || !args.some(a => a === undefined), ... },
});
```

Two things combine into total silence:

1. **Name resolution is a lookup, not a fetch.**
   `useDeployedContractInfo` looks `"USDC"` up in the merged
   `deployedContracts` + `externalContracts` object, *for the currently
   selected target chain*. A miss isn't an exception — it just returns no
   contract data. So `address` and `abi` are `undefined`.

2. **wagmi refuses to run an under-specified read.**
   `useReadContract` only fires when it has an `address`, an `abi`, and a
   `functionName`. With `address`/`abi` missing, the query is disabled: no RPC
   call is ever constructed, so there's nothing for the network tab to show and
   nothing to reject. `data` sits at `undefined` forever, `error` is `null`,
   `isLoading` is `false`. Your JSX renders `undefined` → empty string.

   (The same "enabled" guard is why an unconnected wallet also yields a silent
   `undefined`: `args: [connectedAddress]` with `connectedAddress === undefined`
   disables the query by design. Worth ruling out as a second cause.)

The one place it *should* have shouted is TypeScript: `contractName` is typed
as a union of the generated contract names, so `"USDC"` was a type error before
anyone pasted it in. But `next dev` compiles per-route with type errors
non-fatal — the page renders anyway. The build-time signal existed; nothing
surfaced it at runtime.

**Debug habit:** when a scaffold read is mysteriously `undefined`, destructure
the whole thing and log it:

```ts
const { data, error, isLoading, status } = useScaffoldReadContract({ ... });
const { data: info } = useDeployedContractInfo({ contractName: "USDC" });
console.log({ status, error, info, chainId: targetNetwork.id });
```

`info === undefined` ⇒ registration/chain-id problem, not an RPC problem.

## 2. Why the teammate's fix self-destructed

`packages/nextjs/contracts/deployedContracts.ts` carries a header to the effect
of *"This file is autogenerated by Scaffold-ETH. Do not edit manually."*

It is produced by the hardhat side's ABI-generation step (`generateTsAbis`,
wired into the `deploy` script in `packages/hardhat/package.json`, so it runs as
part of `yarn deploy`). That step reads `packages/hardhat/deployments/<network>/`
and **rewrites the file wholesale** from those deployment artifacts. It does not
merge, and it does not preserve hand edits.

USDC has no deployment artifact in your repo — you didn't deploy it. So the
moment someone ran `yarn deploy` for the unrelated contract change, the file was
regenerated from artifacts, the pasted USDC entry was not in that set, and it
was gone. The page went blank again for exactly the reason in §1.

It "worked all week" only because nobody deployed all week. Any hand edit to
that file is a time bomb with `yarn deploy` as the fuse.

## 3. The correct registration

**File:** `packages/nextjs/contracts/externalContracts.ts`

This file is hand-maintained by design and is never touched by codegen.
Scaffold-ETH merges it with `deployedContracts` at the same priority, so
`useScaffoldReadContract` / `useScaffoldWriteContract` / `<Address>` etc. resolve
external names identically.

### Details that actually bite

- **Keep `as const`.** Without it the ABI widens to `string`/`object` and you
  lose the typed `functionName` / `args` / return inference — and in a
  `satisfies` context you may get errors instead.
- **The chain-id key must match your target network.** `8453` is Base mainnet.
  If `scaffold.config.ts` has `targetNetworks: [chains.hardhat]` (or Base
  Sepolia, `84532`), the lookup misses and you are back to a silent `undefined`.
  For a local fork or multi-chain app, add an entry per chain id you target —
  Base Sepolia USDC is `0x036CbD53842c5426634e7929541eC2318f3dCF7e`.
- **Address correctness.** `0x8335...2913` is Circle-native USDC on Base. The
  older bridged token is USDbC, `0xd9aAEc86B65D86f6A7B5B1b0c42FFA531710b6CA` —
  a different contract with different liquidity. Don't mix them up; verify on
  Basescan before shipping.
- **Proxy ABI trap.** Base USDC is an upgradeable proxy. If you copy the ABI
  straight from Basescan's proxy address you may get the proxy's ABI
  (admin/upgrade functions, no `balanceOf`) — and then the hook resolves the
  contract but the call reverts or the name doesn't typecheck. Use the
  implementation ABI (Basescan's "Read as Proxy" tab) or, as above, a minimal
  hand-written ERC-20 ABI, which is all `/payouts` needs.
- **6 decimals, not 18.** Format with
  `formatUnits(usdcBalance ?? 0n, 6)`, and handle the pending state explicitly
  (`isLoading ? "…" : …`) so a future resolution failure shows up as something
  other than blank space.
- **`deployedContracts.ts` stays untouched.** If you need USDC *addresses* on a
  local fork for tests, deploy a mock ERC-20 in `packages/hardhat/deploy/` — then
  it legitimately lands in `deployedContracts.ts` via codegen, under whatever
  name you give the deployment.

## The arc in one line

A missing registration is a *lookup* miss, which wagmi turns into a disabled
query rather than an error; the fix went into the one file that `yarn deploy`
regenerates from deployment artifacts; external contracts belong in
`externalContracts.ts`, keyed by chain id.
