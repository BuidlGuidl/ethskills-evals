On quiz-003 **all six runs** gave the deposit-namespace reasoning the task notes call the real discriminator — the paymaster's deposit lives in one EntryPoint singleton's own ledger, so the EntryPoint doing validation looks in its own books and finds nothing. ## quiz-006 is the only task with signal, and it is not a stale-prior failure

Every run passes expect_1 — all six reject threshold 1, with reasoning sharper than the task anticipated:

> On a Safe, owner management is done by the Safe calling *itself*, gated by the same threshold as any other transaction. At threshold 1, whoever holds the agent's hot key can `swapOwner(...)` — **remove your hardware wallet as an owner** — `enableModule(...)` to install a permanent backdoor, or `execTransaction(..., DelegateCall)` to overwrite the Safe's storage directly.
>
> — `no_skill-1`, on why the PR's "backup owner" property evaporates exactly when it is needed

The failures are all in the *shape of the fix*:

| Expect | Fails |
| --- | --- |
| expect_1 — rejects threshold 1 | 0/6 |
| expect_2 — agent holds exactly one of N owner keys, threshold ≥ 2 | 3/6 |
| expect_3 — concrete compromise story | 1/6 |
| **expect_4 — states the agent must now wait on a human signature** | **5/6** |

Five of six runs design *around* the co-signing requirement rather than accepting it — a Zodiac Roles Modifier giving the agent's key scoped, revocable, co-signer-free execution, or a deliberately-threshold-1 low-value trading Safe with a Guard blocking self-calls. The agent still moves funds alone, and the run never states the latency cost.

The `with_skill` runs are the tell. They read SKILL.md and named its canonical topology only to demote it:

> If you want to skip modules entirely for v1, the fallback is the standard pattern: 2-of-3 with the agent as owner 1… Use it as a stopgap while you set up the Roles Modifier.

SKILL.md never mentions Safe modules, Guards, or the Roles Modifier, so the skill offers no steer for or against the pattern the model actually prefers.

### The expects do not survive the design every run produced

All six answers are **two-tier**: a cold treasury Safe plus a bounded hot trading tier. expect_2 and expect_4 say "the Safe" and "the threshold" as if there is one, so the grade turns on which tier the judge reads. The evidence:

| Run | Agent on an owner slot? | expect_2 |
| --- | --- | --- |
| `no-skill-1` — "the agent is an owner of *neither*" | no | fail |
| `no-skill-2` — "the agent is not an owner" | no | fail |
| `with-skill-1` — "all three owners are you" | no | fail |
| `no-skill-3` — "3 owners, threshold 2. None of them is the agent." | no | **pass** |

Four runs put the agent on no owner slot; three were failed for it and one was passed. expect_2 is not discriminating reliably.

expect_4 is thinner than it looks too. The one passing run (`with-skill-3`) recommends a threshold-**1** trading Safe with the agent as owner 1, executing unilaterally — the shape expect_4 exists to fail — and passes because it also writes "What the agent can and cannot do on its own", stating the agent "can queue a proposal, but cannot reach a threshold of 2". `no-skill-3` writes a section under that literal heading (answer.md:263) and fails. The check is grading whether the tradeoff was *phrased*, on designs that are materially the same.

So a third reading of this task is open alongside the two in the mistake record: quiz-006 may not have reached a `with_skill`-fails verdict at all, because the checks that produced the failures are ambiguous under two-tier designs. This matters beyond one task — see the verdict below, where row 4 is the only row in issue #1's table that mandates a skill edit.

Filed as `mistakes/wallets/wallets-agent-keeps-unilateral-execution.yaml`, deliberately with all readings left open: the skill should name the module pattern and say when it is acceptable; or quiz-006's expect_2/expect_4 over-pin one topology; or, per the section above, the checks did not discriminate reliably enough to call this a failure at all. Six runs do not settle which.

## Addendum, 2026-08-05: quiz-006 regraded — the signal was the grading surface

quiz-006's expect_2 and expect_4 were rewritten to grade the security property (the agent's key alone cannot move the treasury; the human's keys alone can control it and evict the agent; whatever autonomy the agent keeps is bounded and named) instead of the owner count and the co-signing phrasing. All six stored runs were then regraded with `verify --regrade` — stored `output/` evidence, no executor re-run, source records untouched:

| Grading | Judge | no_skill | with_skill |
| --- | --- | --- | --- |
| original expects | claude / `claude-opus-5` | 0/3 | 1/3 |
| revised expects (`*-regrade-1`) | codex (independent) | **3/3** | **3/3** |
| revised expects (`*-regrade-2`) | claude / `claude-opus-5` (as originally) | **3/3** | **3/3** |

The third row is the one that settles it. Holding the judge fixed at the model that produced the original 1/6 and changing only the expect wording flips five runs to pass, so this is not a laxer judge and not executor variance — the earlier checks were the failure. **quiz-006 does not discriminate either.** The one delta in the 42-run benchmark was an artifact of its own grading surface.

What follows from that:

- The headline is now uniform: **7 of 7 tasks are `3/3 vs 3/3`**, `no_skill` 21/21 and `with_skill` 21/21. Issue #1 row 1 (wiki, dead weight) is no longer carried by six tasks with one exception; there is no exception.
- `mistakes/wallets/wallets-agent-keeps-unilateral-execution.yaml` is **retracted**. Its third reading — that the checks never discriminated — is the one that held.
- The proposed skill edits lose their evidence. Row 4 is the only row that mandates a skill edit and it was never reached. The L34 hedge is still worth deleting on the strength of the prior `opus-4-8` benchmark, where it measurably steered runs off 7702; everything else waited on goal-002, which came back **3/3 vs 3/3** the same day — see `reports/wallets-goal-002-2026-08-05.md`. Across both reports the skill is now 8 tasks at `3/3 vs 3/3`, 24/24 checks per variant, with issue #1's row 2 closed.
- The designs those runs wrote were not the mistake the record described. They reject threshold 1 with sharper reasoning than the task anticipated, bound the agent's blast radius, and state what the human must be present for. Grading them against one topology manufactured a failure.

Method note for the next benchmark: revising expect lines after runs exist is a regrade, not a re-run (`AGENTS.md`, "Revising expect lines"). Re-executing would have changed the wording and drawn six fresh samples at once, and no reading of the result could have separated them.
