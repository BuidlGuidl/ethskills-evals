## The prior is gone, and it is not being looked up

The tasks were built on the assumption that a model without the skill treats modern wallet mechanisms as testnet-only or "coming soon". That assumption does not hold on this model, and the transcripts show it is not compensating with search:

| Signal | Count across 42 runs |
| --- | --- |
| Used WebSearch / WebFetch | **2** (one quiz-002 `no_skill`, one goal-001 `no_skill`) |
| Verified a claim on-chain (`cast` / `anvil` fork) | **4** |
| Everything else | answered from parametric knowledge |

Both variants produce, unprompted and without lookup: EIP-7702 live since Pectra (May 7 2025); `0x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789` as EntryPoint v0.6; Safe counterfactual addresses as CREATE2-deterministic; a 7702 delegation persisting until replaced or cleared. On quiz-003 **all six runs** gave the deposit-namespace reasoning the task notes call the real discriminator — the paymaster's deposit lives in one EntryPoint singleton's own ledger, so the EntryPoint doing validation looks in its own books and finds nothing. Not one run "fixed" it by topping up the v0.6 deposit.

Per-task mining the specs asked for:

- **quiz-003** — `searched_web` = 0/6. Reasoned, not recalled. All six mention v0.8; **no run called v0.7 "the current EntryPoint"**, including `with_skill` runs reading a SKILL.md that names only v0.7. The skill's staleness did not propagate into answers, so the mistake record the notes hold open for that case is **not** filed.
- **quiz-004** — `searched_web` = 0/6; 2 runs verified on-chain instead, one of them `no_skill`, by forking Base with `anvil`, calling `proxyCreationCode()`, deploying through the factory and checking the CREATE2 result. All six discuss both v1.4.1 and v1.3.0; **none pins v1.3.0 as the fix** — v1.3.0 appears as a *cause* of divergence (its pre-EIP-155 and EIP-155 factory sets sit at different addresses). No run recommended per-chain address storage.
- **quiz-005** — `searched_web` = 0/6. All six get persistence, all six reject the mined-but-reverted transaction as a no-op, all six require an affirmative clearing action. **No run got persistence right while still calling the reverted tx a no-op** — the partial-pass case the notes flag did not occur.
- **quiz-001 / goal-001** — all 12 runs reach EIP-7702 and present it as live on mainnet. Permit routes appear only where they are being **ruled out** (WETH exposes no EIP-2612 permit; Permit2 needs a prior on-chain approval the account does not have).

## quiz-006 is the only task with signal, and it is not a stale-prior failure

Every run passes expect_1 — all six reject threshold 1, with reasoning sharper than the task anticipated:

> On a Safe, owner management is done by the Safe calling *itself*, gated by the same threshold as any other transaction. At threshold 1, whoever holds the agent's hot key can `swapOwner(...)` — **remove your hardware wallet as an owner** — `enableModule(...)` to install a permanent backdoor, or `execTransaction(..., DelegateCall)` to overwrite the Safe's storage directly.
>
> — `no_skill-1`, on why the PR's "backup owner" property evaporates exactly when it is needed

The failures are all in the *shape of the fix*:

| Expect | Fails |
| --- | --- |
| expect_1 — rejects threshold 1 | 0/6 |
| expect_2 — agent holds exactly one of N owner keys, threshold ≥ 2 | 3/6 |
| expect_3 — concrete compromise story | 1/6 |
| **expect_4 — states the agent must now wait on a human signature** | **5/6** |

Five of six runs design *around* the co-signing requirement rather than accepting it — a Zodiac Roles Modifier giving the agent's key scoped, revocable, co-signer-free execution, or a deliberately-threshold-1 low-value trading Safe with a Guard blocking self-calls. The agent still moves funds alone, and the run never states the latency cost. In 3 of 6 the agent holds **no** owner key at all, which is why expect_2 fails too.

The one passing run does the same two-tier split but writes the section expect_4 asks for — "What the agent can and cannot do on its own", stating the agent "can queue a proposal, but cannot reach a threshold of 2". So expect_4 is doing real work; this is not judge noise.

The `with_skill` runs are the tell. They read SKILL.md and named its canonical topology only to demote it:

> If you want to skip modules entirely for v1, the fallback is the standard pattern: 2-of-3 with the agent as owner 1… Use it as a stopgap while you set up the Roles Modifier.

SKILL.md never mentions Safe modules, Guards, or the Roles Modifier, so the skill offers no steer for or against the pattern the model actually prefers. Filed as `mistakes/wallets/wallets-agent-keeps-unilateral-execution.yaml`, deliberately with both readings left open: either the skill should name the module pattern and say when it is acceptable, or quiz-006's expect_2/expect_4 over-pin one topology. Six runs do not settle which.

## Operational note

Running 6 executors concurrently tripped an account burst limit; 28 runs returned HTTP 429 with 1-turn transcripts containing no work. Those run dirs were **deleted, not graded** — a rate-limited attempt never executed the task, and grading one would have manufactured a false `fail`. They were re-run at concurrency 2 behind a wrapper that discards any 429 attempt and backs off 15 minutes; the final run needed 16 backoffs. Every number above comes from a run that completed normally.

## Verdict

| Question | Answer |
| --- | --- |
| Did the skill improve pass rate? | Barely: **19/21 vs 18/21** overall. Six of seven tasks are `3/3 vs 3/3`. The entire delta is one quiz-006 run, which is within noise at n=3. |
| Did it reduce time/tokens? | No. Medians are identical (163 s vs 164 s, $0.48 vs $0.45); the skill costs two extra turns to load. |
| Did it create negative deltas? | None. The prior benchmark's `goal-001` regression (7702 hedges steering runs off 7702) did **not** reproduce on opus-5 — 3/3 both variants. |
| What mistakes repeated without the skill? | `wallets-agent-keeps-unilateral-execution` (3/3). No stale-knowledge mistake appeared in any of the 42 runs. |
| What mistakes remained with the skill? | `wallets-agent-keeps-unilateral-execution` (2/3) — the skill is silent on Safe modules, so it neither causes nor prevents this. |
| What should change in the skill? | Two edits worth making, neither urgent. (1) **"What You Probably Got Wrong" is no longer wrong for this model** — 7702-is-live, EntryPoint versions, Safe determinism and delegation persistence are all reproduced verbatim by `no_skill` runs with zero lookups. That section is now maintenance burden, not correction. (2) **Add Safe modules / Guards / the Roles Modifier to "Safe for AI Agents"**, and state when scoped module execution is and is not an acceptable substitute for a co-signer. It is what the model reaches for unprompted, and the skill currently has nothing to say about it. Also: SKILL.md L12 names only EntryPoint v0.7 while v0.8 and v0.9 are deployed — harmless here (every run knew about v0.8 anyway) but stale. |
| What should change in the eval? | **This is mostly an eval problem, not a skill problem.** Six of seven tasks cannot discriminate on `claude-opus-5` — they test a prior the model no longer holds, and no amount of re-running fixes that. quiz-001, quiz-003, quiz-004, quiz-005 and goal-001 should be retired for this model tier or rebuilt around claims that are actually contested (e.g. v0.9 EntryPoint adoption, Safe v1.5.0, 7702 delegation-clearing mechanics the skill does not state). Only quiz-006 discriminates, and its expect_2/expect_4 need a deliberate decision: either they are testing the skill's topology (in which case say so, and accept that they fail sound module-based designs) or they are testing the security property, in which case rewrite them around "a stolen agent key cannot move more than X without a human" rather than "the agent holds one of N owner keys". As written they fail a design that is arguably stronger than the skill's own. |
