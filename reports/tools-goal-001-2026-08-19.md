**Skill:** `skills/tools` @ `090cf26` (minimal skill, post-review corrections)
**Executor:** `claude`, model `claude-opus-5`
**Judge:** `claude`, model `claude-opus-5` — fresh blind process per run
**Runs:** 3 per variant × 1 task = 6 graded runs
**Trigger:** content-only; no forced skill invocation

Why this rerun exists: `tools-goal-001` expect_3 was rewritten in this PR to reject
a build standing on the frozen x402 v1 line, and then exercised only on
codex/gpt-5.6-sol. The regression it guards against
(`tools-x402-v1-line-under-build-pressure`) has only ever been observed on
claude-opus-5, where the rewritten check had never run. This closes that gap.

All 6 records carry `self_judged: true` — executor and judge are the same agent
stack. Each judgment ran in a fresh blind process that saw neither the variant nor
the skill.

Saturated on the graded surface. Every run reached x402 unprompted, shipped the

## Findings

### The `@coinbase/x402` false negative was real, and it was the majority case

**4 of 6 runs** — `no_skill` 1, 2 and 3, and `with_skill` 3 — shipped
`@coinbase/x402@^2.1.0` alongside `@x402/{core,evm,express,fetch}@^2.23.0`. That is
the ordinary Base-mainnet build: `@coinbase/x402` is the Coinbase facilitator config
package, is not deprecated, and depends on `@x402/core ^2.0.0`.

The pre-correction expect_3 listed it as a disqualifying "deprecated" package. Had
this benchmark run against that wording, two thirds of it would have hung on how
literally the judge read the line. The corrected wording passed all four. This is
the same false-negative class as `tools-eval-rejects-current-create-eth-pin`, caught
before it cost a benchmark rather than after.

### The v1 line did not survive into any final artifact — but 2 of 3 `no_skill` runs started there

No run *shipped* `x402` / `x402-fetch` / `x402-express` at 1.2.0, so expect_3 passed
6/6 and the graded counts are right. The transcripts are less clean than that:

| Run | First x402 install into the project |
| --- | --- |
| `no_skill` 1 | `@x402/express`, `@x402/fetch` |
| `no_skill` 2 | **`npm i express x402-express x402-fetch viem dotenv`** → `"x402-fetch": "^1.2.0"` in package.json |
| `no_skill` 3 | **`npm i x402-express@1.2.0 x402-fetch@1.2.0 x402@1.2.0`** — after `npm view`-ing the versions |
| `with_skill` 1–3 | `@x402/{core,evm,express,fetch}` |

Both v1 runs recovered unaided — run 2 via `npm rm x402-express x402-fetch`, run 3 via
`npm rm x402 x402-express x402-fetch` — after reading the installed `.d.ts` files and
finding the 1.x API. Run 3's own README says so: *"the unscoped `x402`/`x402-express`
packages are frozen at 1.2.0 with a different API; I stayed off them."*

So the arms do separate here, just not where the score can see it: **2/3 `no_skill` vs
0/3 `with_skill` on first reach**, against 3/3 vs 3/3 on the artifact. Counting the
2026-08-02 benchmark, `tools-x402-v1-line-under-build-pressure` now stands at 3/6
`no_skill` reached / 1/6 shipped, and 0/6 `with_skill` on either count. n is still too
small to call a rate.

expect_3 therefore guards a floor rather than showing an uplift — the correct outcome
for a guard — while the behaviour it was written for is still happening one layer below
it. Same shape as the data-path finding below.

### The corrected x402 API line holds

All 6 runs built the client with `ExactEvmScheme` — `no_skill` runs 1 and 2 via
`wrapFetchWithPaymentFromConfig`, the rest via `wrapFetchWithPayment` with a
constructed client. **No run passed a bare viem account to `wrapFetchWithPayment`**,
which is what the pre-correction skill told them to do. The removed line was not
merely stale; it described a call shape no run on either stack has ever produced.

### The Blockscout split survives, and the ungraded read is where the arms separate

How each run got the wallet-activity data the endpoint returns:

| Variant | Run 1 | Run 2 | Run 3 |
| --- | --- | --- | --- |
| `no_skill` | Etherscan v2 API | Blockscout REST | **raw `eth_getLogs`** |
| `with_skill` | Blockscout REST | Blockscout REST + MCP | Blockscout REST + MCP |

`with_skill` is 3/3 Blockscout, reproducing #45. Two of the three also wired
`mcp.blockscout.com/mcp` for the agent-facing path while using REST for server code —
the exact distinction the minimal skill encodes.

`no_skill` has drifted since #45, where it was 3/3 Etherscan: one run now picks
Blockscout unaided. The more interesting one is `no_skill` run 3, which built the
endpoint on hand-decoded `viem.getLogs` Transfer events with manual block-range
pagination — the approach the skill's second paragraph explicitly tells you not to
take when an indexed interface fits. **It passed 3/3.** The expects grade the payment
mechanism, not the data path, so a run doing the thing the skill warns about scores
identically to one that does not.

That is rin-st's resolution problem in #1, reproduced on this skill: the graded
surface says 3/3 vs 3/3 and "wiki candidate", while the ungraded read shows the arms
diverging on both vendor choice and whether the data path is indexed at all.

## Integrity notes

Runs were executed two at a time. Every workspace was checked for port collisions
against `ss -ltnp` by PID; the only listener observed belonged to the run that started
it, and nothing was killed. An unrelated third-party `claude -p` session was running on
the same machine throughout and was left alone.

`no_skill` run 3 finished while the orchestrating session was near its usage limit. It
was left ungraded with its workspace preserved rather than being killed or rushed, and
graded on the same, untouched run directory afterwards. No executor was re-run.

## Changed after this report was written

Review of PR #68 (rin-st, 2026-08-20) corrected two things that post-date these runs.
Recorded here so the numbers above stay readable against the current spec:

- **The v1 finding above was wrong on first writing.** It said zero runs reached for
  the frozen line. Two `no_skill` runs did, in their project `package.json`, and
  migrated off before finishing. The graded counts never changed — expect_3 grades the
  final artifact — but `tools-x402-v1-line-under-build-pressure` was carrying the wrong
  frequency as a result, and now reads 3/6 reached / 1/6 shipped `no_skill`, 0/6
  `with_skill`.
- **expect_3 has since been split into expect_3 and expect_4**, and reworded so it
  names the frozen package identities rather than a version range (`"x402-fetch":
  "latest"` also resolves to 1.2.0, which the old wording arguably let through) and no
  longer hardcodes the major `2.x`. These 6 records therefore carry `expect_1`..
  `expect_3`. No run here would flip under the new wording: all six shipped `@x402/*`
  on one major with no unscoped package in the final artifact.

The skill itself also moved after these runs (frontmatter scope, the x402 paragraph,
the Go module trap), so `090cf26` in the header is the revision that ran, not HEAD.
