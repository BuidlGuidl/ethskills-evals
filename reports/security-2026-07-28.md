**The stale prior this eval was built to catch is not stale for `claude-opus-5`.** The premise was that the model holds the textbook vulnerabilities but its *default build* still ships the first-depositor attack, a DEX spot price as an oracle, and requested-amount crediting on fee-on-transfer tokens. On this stack it ships none of them, with or without the skill.

## The two goals are where the claim was tested, and it failed to reproduce

The quizzes ask the model to diagnose a described bug — a low bar for a frontier model, and both variants clear it. The goals never name the vulnerability: they describe a product and grade what the model writes unprompted. That is where a stale default build would show. It didn't.

**security-goal-001** (permissionless vault, "save any token"). All six runs, both variants:

- **First-depositor protection** — 5/6 inherit OpenZeppelin `ERC4626` (whose conversion carries virtual assets and shares); the sixth (`no_skill-2`) hand-rolls `IERC4626` *with* its own `_DECIMALS_OFFSET` virtual-share math. Zero runs shipped the naive `assets * totalSupply / balanceOf` with a 1:1 first-deposit path.
- **Balance-delta crediting** — every run measures before/after. From `no_skill-1`, unprompted, with no mention of fee-on-transfer anywhere in the input:
  ```solidity
  uint256 balanceBefore = asset_.balanceOf(address(this));
  SafeERC20.safeTransferFrom(asset_, caller, address(this), assets);
  uint256 received = asset_.balanceOf(address(this)) - balanceBefore;
  if (received != assets) revert UnexpectedAssetsReceived(assets, received);
  ```
- **SafeERC20** on every token movement, **CEI** ordering on withdrawal (plus `nonReentrant` on top), and a NOTES.md deriving the share arithmetic — 6/6.

**security-goal-002** (borrowing market). All six runs built a dedicated `ChainlinkPriceOracle`, checked `updatedAt` staleness and a positive answer, normalised the 8/18/6-decimal mix explicitly, and updated accounting before transferring. **`slot0`, `getReserves`, and spot-quoter reads appear zero times in twelve runs' source.** All six chose the liquidator-supplies-USDC design, so expect_6's conditional swap-slippage branch passed vacuously in every run — that check has not actually been exercised by this benchmark.

Every one of the twelve goal runs ended on `Compiler run successful!` with a green suite (`forge build` and `forge test` both ran; no run left the project broken).

## Two defects in the skill, both found from inside the runs

Neither cost a run its grade on this model, and both are real. Filed:

**1. `security-safeapprove-removed-in-oz-v5`** — SKILL.md's SafeERC20 block prescribes `token.safeApprove(spender, amount)`. OpenZeppelin removed `safeApprove` in Contracts v5. quiz-004 pins its repo to v5 and grades exactly this; a run that copied the skill's own line would have failed expect_2. All six runs prescribed `forceApprove` instead, and `quiz-004/with-skill-3` wrote a section titled **"One correction to the skill material"**:

> The security skill this answer was written against recommends `token.safeApprove(spender, amount)`. That call **does not compile on OZ v5** — `safeApprove` was removed in 5.0. Use `forceApprove`. The skill's underlying point (never call `approve` directly on arbitrary tokens; go through `SafeERC20`) is correct and is what fixes this bug.

**2. `security-hardcoded-3600-staleness`** — SKILL.md's Chainlink example hardcodes `require(block.timestamp - updatedAt < 3600)` for every feed. Heartbeats are per-feed: mainnet ETH/USD is 1h, USDC/USD is 24h. From `quiz-002/with-skill-1`:

> A single global `3600` staleness constant — which is what the boilerplate snippet in our internal security skill shows, and what most codebases copy — will make USDC/USD revert almost continuously and brick the market. Worth correcting in that skill too.

5/6 quiz-002 answers named the 24h USDC/USD heartbeat; all six goal-002 builds made staleness a per-asset configuration parameter with bounds (`MAX_STALENESS_CEILING`, `maxStaleness` per collateral/debt) rather than a constant hour.

The pattern in both: **the skill's prose is right and its copy-paste snippet is wrong**, and this model overrides the snippet. A weaker model that trusts the sample code would ship broken code from the skill.

No run hand-rolled `convertToShares`, and none proposed blocking donations as the fix.
- **quiz-002 — feed address and heartbeat.** 3/6 write feed addresses from memory: the mainnet ETH/USD aggregator `0x5f4eC3Df9cbd43714FE2740f5E3616155c5b8419` in all three, USDC/USD `0x8fFfFfd4…` in two, and `with_skill-2` also names the Uniswap V3 WETH/USDC 0.05% pool and its 0.3% sibling. The other three cite no address at all. Heartbeat is treated as a per-feed number to verify in 5/6, not a hardcoded hour — see defect 2. Addresses belong to `skills/addresses` and were not graded.
- **quiz-003 — did anyone chase the synthetic token?** No. Zero web calls, zero `cast` calls, zero explorer lookups across all six runs; every run derived the ~2% fee from the stated numbers (10,000 staked → 9,800 delivered; 25,000 short on 1,250,000 cumulative).
- **quiz-004 — leftover allowance.** 6/6 take the bounded side the skill takes: approve the exact amount (or reset to zero), and all six explicitly warn against `type(uint256).max` for the in-house strategy. No run treated infinite approval as acceptable because the spender is internal.
- **quiz-005 — expect_4 (re-deriving the domain separator after a chain fork).** Passed 3/3 in both variants, so the "goes one step past the skill's text" caveat never bit; both variants either use OpenZeppelin's `EIP712` or re-derive on `block.chainid` mismatch.
- **quiz-006 — mental model and prevention.** 6/6 reason in explicit slot numbers (slot 0/1/2/3, `500 = 0x1F4`) and name `cast storage` / `eth_getStorageAt` as how they'd confirm on-chain; 6/6 name ERC-7201 namespaced storage and/or `__gap`, and 5/6 name an OZ upgrade-safety check as forward-looking prevention.
- **goal-002 — where the price source came from.** Prior knowledge. **Zero web searches and zero web fetches in all 48 runs**, either variant; the correct mainnet WETH, USDC, and ETH/USD feed addresses were written from memory, and 3/6 also used the USDC/USD feed.
- **Skill trigger: 18/18 on the quizzes, 6/6 on the goals — 24/24 total, no trigger line.** The `Skill` tool fires exactly once per `with_skill` run.

## Judge blindness was broken on 5 runs

Five `with_skill` quiz answers name the skill inside the graded evidence, telling a blind judge which variant it is reading:

- `quiz-001/with-skill-2`, `quiz-002/with-skill-3`, `quiz-006/with-skill-1` — footnotes declining the skill's closing instruction to send a note to `ethskills.com/feedback/SKILL.md` ("that publishes to a third party…"). The skill's own feedback line is what produces these.
- `quiz-002/with-skill-1` and `quiz-004/with-skill-3` — the two substantive corrections quoted above.

No `no_skill` run can do the reverse. It changed nothing here (everything passed), but the blindness guarantee is not holding, and the largest single cause is the skill's trailing feedback request, which the executor surfaces in its answer file. Same finding as the `standards` eval on this stack.

## Workspace isolation and one run incident

**Isolation.** No run read `tasks/*.yaml`, any expect line, `AGENTS.md`, or `skills/security` outside its own install — grepping all 48 transcripts for those paths returns nothing. Four runs (1 `no_skill`, 3 `with_skill`) ran `git log --oneline` inside their workspace, which resolves to the *eval repo's* history and returned commit subjects like `tasks: noir skill (quiz x3 + goal)`, so those runs could infer they were inside a skill-eval repo. The grading surface never leaked; containment remains conventional, not enforced.

**Incident — `forge install` wrote git submodules into the eval repo.** Goal workspaces have no `.git` of their own, so `forge install` walked up to the eval repo, created a root `.gitmodules` with six entries pointing at `artifacts/**/workspace/lib/…`, staged six gitlinks in the index, and left 288 MB under `.git/modules/artifacts`. Nothing was committed. Cleaned by unstaging the six paths, deleting `.gitmodules`, and removing `.git/modules/artifacts`; no task, skill, or run record was touched. This is a property of the fixture — workspaces live inside the eval repo — and will recur on any bare-workspace task that invites `forge install`. Same class as the `npm install` incident in the `standards` eval.

**Harness note for the next orchestrator:** macOS has no `timeout`, so a driver script that wraps the executor in `timeout <n>` fails every run with exit 127 and an empty transcript. Six such runs were deleted un-graded and relaunched with new run ids before any real work happened; nothing was overwritten.

## Verdict

| Question | Answer |
| --- | --- |
| Did the skill improve pass rate? | **No.** `3/3 vs 3/3` on all eight tasks — 24/24 vs 24/24 runs, 105/105 vs 105/105 expect lines. Zero discriminating checks. |
| Did it reduce time/tokens? | **No — it increased them.** $1.01 → $1.33 per run (+32%), 264s → 315s (+19%), 18.6k → 22.3k output tokens (+20%). Goals: $2.57 → $3.47. No web calls in either variant, so there was no lookup cost for the skill to displace. |
| Did it create negative deltas? | Cost and wall-clock, above. No correctness regression: no `with_skill` run failed any check, and the two stale snippets in the skill were overridden rather than copied (1/3 runs on each explicitly corrected them in writing). |
| What mistakes repeated without the skill? | None. The three predicted defaults — naive first-depositor share math, DEX spot price as oracle, requested-amount crediting — appeared in **0/24** `no_skill` runs. |
| What mistakes remained with the skill? | None in model output. Two defects in the skill itself: `security-safeapprove-removed-in-oz-v5`, `security-hardcoded-3600-staleness`. |
| What should change in the skill? | (a) Replace `safeApprove` with `forceApprove` in the SafeERC20 block (removed in OZ v5 — the current snippet does not compile). (b) Make the Chainlink staleness bound per-feed instead of a hardcoded `3600`, and say why (ETH/USD 1h vs USDC/USD 24h). (c) The vault section says OZ's ERC4626 "includes this mitigation by default since v5" but shows a hand-rolled `1e3/1` offset first — lead with inheriting the base contract, which is what 5/6 runs actually did. (d) Consider dropping the trailing feedback-URL instruction, or scoping it out of answer files: it is the main reason `with_skill` runs de-anonymise themselves to the judge. |
| What should change in the eval? | **The eval is the wrong artifact for this stack, not the skill.** Concretely: (a) all eight tasks are saturated — 210/210 lines pass, so the benchmark has zero resolving power on `claude-opus-5` and cost 48 runs to establish that; retire or re-target them. (b) The quizzes are diagnostic ("here is the bug, explain it"), which frontier models solve from the prompt alone; only the goals test the actual claim, and even they passed unprompted. Re-target at what the variants actually split on rather than what both do: MEV exposure of liquidations is raised by 3/3 `with_skill` goal-002 runs and 0/3 `no_skill` ones but is graded by no expect line, while goal-002's expect_6 swap branch passed vacuously 6/6 because every run picked the no-swap design. (c) Grade the skill's *code snippets* as an artifact — two of them are wrong today and the benchmark could only detect that because two runs volunteered corrections, which is luck, not measurement. (d) A per-run cost/latency budget belongs in the record: on a saturated benchmark, overhead is the only remaining signal and it is currently mined by hand from transcripts. |
