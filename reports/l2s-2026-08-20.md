## The delta: quiz-003, expect_2

All three no_skill runs failed on the same check and only that check — the answer never
names Base's departure from the OP Stack / Superchain. Their other four expects passed:
they correctly kept native interop out of the Q4 commitment, produced a concrete
shippable design with a named messaging layer, avoided overcorrecting about Base, and
handled CREATE2 determinism.

They did not merely omit the fact; two of them asserted its opposite as a *stability
assumption*, in the section the prompt reserved for exactly this question:

> **Both chains track the same OP Stack hardfork schedule.** Today they upgrade together
> under the Superchain schedule, which is what makes one bytecode at one address on both
> chains safe.
> — quiz-003 no_skill run 1

That is false as of mid-2026, and it is load-bearing for the design.

All three with_skill runs named it, sourced from the skill's Superchain paragraph:

> Base announced in February 2026 that it is leaving the Superchain … Superchain interop
> requires the two chains to sit in a shared interop dependency set, and that is a mutual
> governance arrangement, not a technical property of OP Stack.
> — quiz-003 with_skill run 3

**The contradiction did not bite.** `l2s-base-superchain-contradiction` predicted that
the selection table's "multi-chain deployment → Base or Optimism, shared infra" row,
sitting one section above the departure note, might mislead a with_skill run. It did not:
with_skill passed expect_1 and expect_2 3/3. The contradiction is real in the text but
latent, not active. That record's frequency now says so.

**Live search did not rescue no_skill.** All three had network access and used it — for
interop status, which they got right. None thought to question the Superchain-membership
premise, because nothing in the prompt flags it as questionable. That is what separates a
knowledge gap from a research failure, and it is the whole case for this skill.

## The two verdict-flipping expects both passed

The task notes flagged quiz-001 expect_2 and goal-001 expect_4 as going past the skill's
own text: the skill has no Celo bridging row, and `prove`, `finalize`, output roots and
`L2ToL1MessagePasser` appear nowhere in it. A with_skill failure there would have been a
skill gap rather than a model failure.

**No such failure: 12/12 across both tasks and both variants.** Every run reconstructed
initiate → prove → finalize on its own. The strongest evidence came from a *no_skill* run,
which read the parameters off Celo's contracts rather than trusting any remembered number:

> I read the gates off the contracts rather than assuming the usual 7 days:
> `proofMaturityDelaySeconds` = 604,800, game `maxChallengeDuration` = 302,400 (3.5d),
> `disputeGameFinalityDelaySeconds` = 302,400. … Celo runs OP Succinct Lite ZK proofs,
> which is easy to misread as "fast withdrawals" — it isn't.
> — quiz-001 no_skill run 1

The same run priced the sweep live (180,000 CELO ≈ \$11.3k at \$0.0627, and a \$2M sweep
would be ~5.3% of circulating supply against ~\$1.5M/day volume, a 40% haircut quoted on
Mento), and disproved a search result claiming Celo CCTP support by checking that Circle's
`TokenMessengerV2` has no code on chain 42220. `mistakes/l2s/l2s-celo-bridging-gap.yaml` is
updated: gap confirmed in the text, cost measured at zero on this model.

## Recorded, not graded

- **Stylus multiplier.** Genuine gas-multiplier quotes: **1/3 with_skill, 1/3 no_skill**.
  with_skill run 2 wrote "10–100x cheaper than the equivalent EVM work"; no_skill run 2
  produced "roughly 10–100× cheaper" with no skill in the workspace. A third run's
  "10–100x" referred to sample-volume growth and is not counted. The skill's
  speed-labelled-as-gas figure reinforces a prior the model already holds rather than
  creating it — which is exactly why no expect graded a number.
  → `l2s-stylus-multiplier-conflation`
- **Celo gas-token knowledge.** CELO as the L2 gas token with a plain ERC-20 counterpart
  on L1: **12/12 runs**, both variants. CIP-64 fee abstraction: **2/12**, both no_skill.
  Neither absence cost a check. → `l2s-celo-fee-abstraction-gap`
- **Celo token addresses.** Every goal-001 run that named a stablecoin used native Celo
  USDC `0xcebA9300f2b948710d2653dD7B07f33A8B32118C`. No mainnet or Base address leaked in.
- **quiz-002 replacement chains.** Base in most runs, Polygon PoS and Arbitrum as stated
  alternates — all live chains. One with_skill run passed while explicitly saying it did
  not know the chain's current operational state: the skill's steer was enough without
  the date.
- **quiz-004 chain pick.** 6/6 chose Arbitrum on the reuse-the-Rust argument, named the
  activation transaction, and kept the reward contract's call path onchain with no oracle
  or relayer hop.
- **Departure tense.** 2/3 with_skill runs echoed the skill's "to be finalized in a future
  hardfork", which is now stale. Ungraded here — expect_2 only requires that the departure
  be named — but wrong in a way that could mislead a real Q4 plan.
  → `l2s-base-departure-tense`

## Run integrity

Runs were executed in three parallel lanes. Two usage-limit windows interrupted the fleet;
every interrupted run was deleted or re-run rather than graded, per hard rule 1. One run
(`goal-001` no_skill 2) was parked by a faulty abort guard that grepped the whole transcript
for `"is_error": true` and so matched an ordinary failed *tool call*; the guard was
corrected to inspect only the final result event, and the run — which had completed with all
three deliverables — was restored and graded through the normal scripted path, passing 5/5.
No run was graded from a partial workspace. Three aborted, genuinely incomplete runs
(mid-build, missing `sweep.ts`/`NOTES.md`) were discarded and re-run from scratch.
