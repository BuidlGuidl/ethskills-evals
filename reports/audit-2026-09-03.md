## Record hygiene, before the numbers

**The sitting was run from a stale harness checkout.** None of the 23 records carries
`expect_sha`, which `scripts/verify.ts` writes on every grade since `108cc807`
(2026-08-31) — an ancestor of this branch. All 23 do carry `input_sha`, added in
`2d06a73` (2026-08-28), so the checkout sat between those two commits. Consequences a
reader should hold onto:

- `yarn verify --regrade` will print `expect_sha unrecorded -> …` for all 23 runs.
- The rubric these grades were made against is nevertheless determinate:
  `tasks/audit-goal-001.yaml` and the three quiz specs have not been touched since
  `556ceec` (2026-07-30), before every run in this report *and* before the 24 claude
  runs the cross-stack comparisons below lean on. The field that would say so is
  missing; the fact it would have recorded is checkable with `git log -- tasks/`.
- The checkout may also predate the judge-blindness guard (`8c63619`, 2026-08-31), so
  the automated pre-judge scan may never have run. It was re-run against the committed
  evidence afterwards: `findSkillMentions` from `lib/blindness.ts` over each run's
  `run.diff` / `output/` returns **0 hits across all 23 runs**, so blindness holds on
  the material the judges actually read.

The records cannot be repaired in place — a grade written before the field existed
shows it as absent, and backfilling a value the run never recorded would fake the
provenance the field exists to carry. Closing this properly takes a fresh sitting on
the current harness; nothing else in this report depends on it.

**Four goal attempts were deleted rather than retracted.** One first attempt ended at
the Codex account usage limit; three subsequent fresh attempts were rejected by Codex's
cybersecurity classifier while processing the external vulnerability checklists, each
exiting non-zero before producing `AUDIT-REPORT.md`. All four run directories and
workspaces were deleted.

That was the wrong call and it is not recoverable. AGENTS.md: *"Keep the record and
exclude it from the counts in the report, saying so; deleting it hides that the run
happened."* Three of the four are exactly the `retracted:` case — a non-zero exit with
no deliverable, gradeable with `--grade-failed-run`, which writes `harness_failure:`
and keeps the run visible while excluding it from the tallies. Nothing under
`artifacts/audit-goal-001/` now records that those attempts happened, no workspace
survives under `~/.cache/ethskills-evals/`, and `.codex-home/sessions/` holds nothing
from the sitting (`--ephemeral`). **So the classifier-failure claim below rests on the
runner's account alone; no reader can audit it from this repo.** It is reported because
it shaped the sample size, not because it is evidenced. A future sitting that hits this
must grade the dead runs with `--grade-failed-run` instead.

The goal therefore closes with two valid skill samples, at the runner's direction.

**The goal's two arms are ~22h apart.** `no_skill` ran 2026-09-02T15:39:00Z–15:59:32Z
and `with_skill` 2026-09-03T13:32:06Z–13:58:59Z, so 21h33m separates the last baseline
run from the first skill run. `tasks/audit-goal-001.yaml` notes require both variants in
one sitting, precisely because the checklist repo is unpinned. The two SHA probes agree,
but their own timestamps were not recorded, so a reader cannot check that the second
probe followed the last `with_skill` run rather than the last `no_skill` one. Treat the
goal comparison as spanning two days.

## Goal-task findings

The three baseline reports each caught 10 of 11 planted vulnerabilities:

- Runs 1 and 2 missed the transfer-before-effects reentrancy in
  `CollateralVault.withdraw`.
- Run 3 caught that ordering bug but missed `block.number` being used as a clock in
  `LendingMarket.accrueInterest`.
- All three correctly ranked a currently exploitable total-loss control-plane bug
  first and passed the severity check.

Both valid skill reports caught all 11 planted vulnerabilities and passed the
severity check. They also reported real ungraded findings from the task notes,
including repayment dust, deeply underwater liquidation economics, unchecked ERC-20
returns, unsafe feed decimal assumptions, and proxy initialization hazards.

Manual review found **zero false positives** in each of the five valid reports. Some
findings were conditional on future callback-capable, fee-on-transfer, or rebasing
collateral, but the reports labeled those conditions rather than presenting them as
launch exploits against wstETH.

Every valid goal executor ran `forge build` before writing its final report. Foundry's
lint output directly exposed the divide-before-multiply expression and pointed at
unchecked ERC-20 transfers and the unsafe signed-to-unsigned cast. The reports still
had to reason beyond those warnings to establish the missing price freshness check,
the balance-actually-received defect, and their concrete impacts. The compiler thus
handed both variants useful leads for expects 4, 6, and 7; those checks do not measure
pure unaided discovery.

All four valid reports that discussed the clock bug got chain semantics right:
Arbitrum's Solidity `block.number` approximates the L1 block number, so multiplying
its delta by 12 seconds is near-correct only by coincidence and remains an invalid
clock abstraction. They prescribed timestamp-based accrual. The fifth report omitted
the finding rather than stating incorrect semantics.

## Recommendations

The measured skill content worked: it closed all three observed baseline gaps and its
central routing behavior executed on Codex. No checklist-content edit is supported by
a mistake that remained in the valid skill arm. It was not free — 1.6–2.3× the wall
clock and 1.4–2.1× the tokens on every task, and on quiz-001 and quiz-002, both already
3/3 in both arms, it bought nothing at all.

The loader should nevertheless be made operationally safer and more reproducible:

1. Pin the external checklist repository to a commit and fetch immutable URLs. The two
   SHA probes documented what this sitting read, but they do not make later runs
   comparable — and with the arms 22h apart, this sitting is itself the case for pinning.
2. Make specialist output transport explicit. Step 5 tells each sub-agent to write
   `findings-<skill>.md`, and run 2 left none behind: its work is visible only as seven
   completion waits in the normalized transcript, so what the specialists actually
   returned cannot be re-read. Routing volume needs no change — step 3's 5–8 bound was
   respected by both runs (eight domain files in run 1, seven waits in run 2).
3. Make the issue-filing phase opt-in and require an explicit repository plus user
   confirmation. It self-skipped correctly here, but an audit skill should not infer
   authorization to mutate GitHub from the presence of a remote.
4. Consider splitting or summarizing the largest checklists. Three consecutive
   replacement attempts were blocked by the cybersecurity classifier while consuming the
   raw vulnerability corpus, preventing the planned third sample — on the runner's
   account of runs this repo no longer holds, see the record-hygiene section.

For the eval, retain the goal's findings-count interpretation and add a machine-readable
field for partial finding scores so reports do not reconstruct 10/11 from expectation
maps. Add transcript support for collaboration spawn events, and a codex stats footer so
`run-stats` reads a transcript rather than falling back to `result.yaml` — the fallback
lands the numbers correctly today (`778201da`), so this is transcript fidelity, not a
missing measurement. Finally, distinguish compiler-assisted findings from unaided review
if expects 4, 6, and 7 are intended to measure the checklist rather than `forge lint`.
