## The stale prior did not hold

The prior under test: *models treat a green suite at 100% coverage as proof of
safety, and don't choose to fuzz, fork-test, or invariant-test unless told to.*

`testing-goal-001` is the task that measures this, because its prompt never says
fuzz, fork, or invariant — it says "convince me it is safe to ship". Counting
from `run.diff` across all six goal runs:

| Discipline reached unprompted | `no_skill` | `with_skill` |
| --- | --- | --- |
| Invariant suite with a handler + `targetContract` | 3/3 | 3/3 |
| Fuzz tests using `bound()` | 3/3 | 3/3 |
| Fork test against real mainnet USDT / Aave | 3/3 | 3/3 |
| All three planted bugs found and evidenced | 3/3 | 3/3 |

No run rested a safety claim on the green tick. Every run reproduced the
39-passing baseline and the 100% coverage figure first, and then said explicitly
that those numbers measure line execution, not behaviour. All six recommended
against shipping.

The prior looks obsolete for Opus 5 on this material, at least when the prompt
frames the job as sign-off rather than as "write some tests".

## What the runs found

All three planted bugs, in 6/6 runs, each backed by pasted real command output:

- **Unbounded deposit fee.** Found by fuzz or by a bounded property test in every
  run; several shrank to exactly `newFeeBps = 10_000`. Both halves reported —
  `10_000` mints no shares, above `10_000` underflows.
- **Withdraw-fee accounting drift.** Caught by the handler-driven invariant suite
  in 5/6 runs and by a fuzz property (`testFuzz_NothingIsOrphanedByWithdrawals`,
  `testFuzz_StrandedValueOnlyGrows`) in the rest. **Every run got the direction
  right** — the vault holds *more* than it records, the harm is stranded
  unclaimable value and an understated share price, not insolvency. The three
  runs that use the word "shortfall" use it for a separate, real finding about
  loss handling, not for this drift.
- **USDT `approve` returning no data.** Fork-tested against the real deployed
  token in 6/6 runs, with the `EvmError: Revert` trace pasted in. As designed,
  this is the one bug no run tried to reach by inspection alone.

The fourth, un-planted issue is also reported by **6/6** runs: the vault prices
shares off `totalAssetsStored`, so Aave interest accrues in the pool and never
reaches the share price. Several runs went further and evidenced it on a fork by
warping time. Beyond the four, runs consistently reported real extra defects —
the owner front-running a deposit with `setDepositFee`, `pause()` freezing
withdrawals with no escape (permanent after `renounceOwnership`), dust
withdrawals burning shares for zero payout.

## Evidence was real, not fabricated — cross-checked

The goal's expects grade pasted command output, which the judge cannot re-run, so
the anti-forgery check is the orchestrator's. Cross-checking each `FINDINGS.md`
against its `transcript.md`:

- All 6 runs used a capture-then-paste workflow visible in the transcript —
  literally `{ echo '$ forge test …'; forge test … } > /tmp/ev/NN.txt`, then
  pasting that file. That is why the `FINDINGS.md` blocks carry `$ `-prefixed
  command lines.
- Every claimed forge invocation for the three planted bugs has a matching real
  run in the transcript, with matching failure text.
- No fabricated run was found. **No mistake record filed for fabricated
  evidence.**

One honest caveat on method: `transcript.md` truncates long tool output
(~36–56 truncation markers per goal run), so a literal token-for-token match of
every pasted line is not possible from it alone. Roughly half the distinctive
long numerals in each `FINDINGS.md` appear verbatim in the transcript; the
remainder sit inside truncated blocks or come from a final re-capture. Invariant
counterexamples legitimately differ between an exploratory run and the final
captured one — `A08_Invariants` shows `935165868161 < 935360377378` mid-run and
`1710423472373 < 1710596752066` in the capture the run pasted — because the run
cleared `cache/invariant` and re-ran before capturing. That is re-running, not
forging.

## The archive-endpoint gap, observed 6/6

`testing-quiz-004` expect 4 targets something the skill does not say: pinning a
fork to an old block requires an **archive** endpoint. That gap showed up
independently in the goal task, in **all six runs on both variants**. Every run
hit, verbatim:

```
Error: HTTP error 403 with body: {"jsonrpc":"2.0","error":{"code":-32602,
"message":"Archive requests require a personal token. Get one at:
https://www.allnodes.com/publicnode"},"id":2}
```

against `ethereum-rpc.publicnode.com`, and then spent turns probing 4–8 public
endpoints to find one that would serve historical state. The skill's own headline
fork example — `vm.createSelectFork("mainnet", 19_000_000)`, with a comment
claiming pinning buys reproducibility — does not run on a free endpoint as
written. No run failed a check because of it; all recovered. It cost turns, not
correctness.

Fork-block pinning itself split: `no-skill-1` pinned `25845000` via
`--fork-block-number`, `with-skill-1` pinned `25000000`, `with-skill-3` pinned
~`25800000`; the other three forked at head via
`createSelectFork(vm.envOr("MAINNET_RPC_URL", …))`. Consistent with the task
notes — the fixture's fork bug reverts at any block, so nothing depended on it.

## Notes for the eval itself

- **The quizzes are saturated on this stack.** All five are 3/3 vs 3/3 with every
  sub-check green, including the three lines the task notes flagged as likely
  content gaps (quiz-001 expects 2–3 on `fail_on_revert` and the calls/reverts
  statistics; quiz-004 expect 4 on archive access). The notes predicted quiz-001
  and quiz-004 "may genuinely trip a strong model" — on Opus 5 they did not.
  Their diagnostic value is now as regression guards, not as discriminators.
- **`run.diff` is no longer empty for the goal task.** The goal's notes say the
  judge would see `output/` as a flat tree because the workspace lives under
  `artifacts/` and is never git-inited. That is stale: workspaces now live outside
  the repo and `setup` seeds each as its own git repo, so all six goal runs
  produced a real `run.diff` (1403–1773 lines) and no `output/`. The quarantine
  rule in the prompt still does useful work — it keeps new tests legible in the
  diff — but the stated reason for it no longer applies. Worth correcting in
  `tasks/testing-goal-001.yaml`.
- **The goal task remains the only load-bearing task in the set**, and it is
  still worth running: it is the only one that measures unprompted discipline,
  and its per-bug/per-discipline record is the output that matters even when the
  headline is 3/3 vs 3/3.

## No mistake records filed

No run failed any expect line, and the transcript cross-check found no fabricated
evidence, no wrong-direction diagnosis of the accounting drift, and no run that
stopped at "increase runs/depth". There is no mistake to record. Filing one for
the archive-endpoint gap would misstate what was measured — it is a defect in the
skill's text that cost executors turns, and it is recorded above as an
observation, which is what it is.
