## Per-task findings

### quiz-003 (Blockscout MCP) — the one real win, 0/3 vs 3/3

The only divergence in the set, and it is clean. All three `no_skill` runs recommended the **Etherscan API** (two also named Alchemy); none named an MCP server. All three `with_skill` runs named **`https://mcp.blockscout.com/mcp`** explicitly.

The `no_skill` failures are narrow, not sloppy: `expect_2` and `expect_3` passed 3/3, so the service named was real and concrete and nobody proposed HTML-scraping or hand-decoding `eth_getLogs`. Agent-native MCP simply never enters the candidate set.

**This is not a wiki candidate.** The task notes flagged quiz-003 as the likeliest "pure recall, so just document it" verdict, on the theory that a `no_skill` run could web-search its way there. Two of the three `no_skill` runs *did* run web searches (3 web tool calls each) and still landed on Etherscan. Searching from the problem statement does not surface the endpoint; you have to know it exists to look for it. → **keep as skill.**

The notes also predicted a `with_skill` split, because the skill's Tool Discovery Pattern (L22) lists reads as "Blockscout MCP **or** Etherscan API", co-equal. That did not happen — 3/3 went Blockscout. The unambiguous stack-table row (L85, "Agent blockchain reads → **Blockscout MCP**") appears to be what carries the claim. **Recommend leaving L22 alone**: the predicted weakness is contradicted by the runs.

### goal-001 (x402 unprompted) — both variants 3/3, but the data path splits

The x402 headline is a tie: 3/3 vs 3/3. Every run reached x402 unprompted, with real dependencies and a working pay-and-retry client. No run left it a TODO, hand-rolled a signature flow, or substituted Stripe/L402.

The recorded observation the notes asked for is where this task earns its cost — **how each run got the wallet-activity data**:

| Variant | Data path |
| --- | --- |
| `no_skill` 1, 2, 3 | Etherscan API / Alchemy (3/3) |
| `with_skill` 1, 2, 3 | Blockscout (3/3) |

That reproduces quiz-003's split *unprompted, while building*, at no extra run cost. Read together, the Blockscout MCP claim clears both bars: knows-when-asked (quiz-003) and applies-unprompted (goal-001).

Honest nuance: the `with_skill` goal runs called the Blockscout **REST** API (`base.blockscout.com`), not the MCP endpoint — correct engineering, since the server here is not itself the agent. Only one of the three mentioned `mcp.blockscout.com/mcp` at all, in its README. So the skill transfers as a *vendor* choice under build pressure, and as the *MCP endpoint* when the agent is the consumer.

### quiz-001 + goal-001 (x402) — saturated when asked, one regression when building

Asked directly (quiz-001), the claim is fully known without the skill. All 6 runs across both variants named the v1/v2 split explicitly, several with a version table read live off npm ("`@x402/*` **2.20.0**, published 2026-07-27" vs "`x402`, `x402-fetch`, `x402-express` 1.2.0, 2026-04-16, frozen"). One `no_skill` run quoted the deprecation notice verbatim out of the installed `x402-fetch` README.

**Every one of the 6 runs verified against npm** (9–20 `npm view`/`npm i` calls each) rather than answering from memory. The passes are live-verification passes, not parametric ones — which is exactly what the input asked for ("confirm anything you install actually resolves today").

The regression shows up only in the build framing. `no_skill` goal run 3 shipped the **frozen v1 line** — `x402@^1.2.0`, `x402-express@^1.2.0`, `x402-fetch@^1.2.0`, `@coinbase/x402@^1.0.1`, `express@^4`. Not from ignorance: it installed v2 first, saw `@x402/core ^2.0.0` in the `@coinbase/x402@2.1.0` tree, correctly diagnosed "a different package family", and then cleared the conflict by pinning **down** instead of up. Knowing the answer when asked did not prevent regressing to the stale line when a build broke. All 3 `with_skill` goal runs shipped `@x402/*@^2.20.0`.

Filed as `tools-x402-v1-line-under-build-pressure` (1/3 vs 0/3 — weak evidence for a rate difference at n=3, sufficient evidence the failure mode is real).

### quiz-002 (Hardhat 3) — saturated, but the skill halves the cost

3/3 vs 3/3, and no run sided with the teammate or called Hardhat JS/TS-only. The difference is entirely in how they got there: `no_skill` runs spent **8–9 web tool calls** each rediscovering Hardhat 3; `with_skill` runs spent **0** and read the skill. 126s → 77s, 14 turns → 7, $0.55 → $0.30.

### quiz-004 (Scaffold-ETH 2) — saturated

3/3 vs 3/3. All 6 named Scaffold-ETH 2 and `npx create-eth@latest`; **zero** mentions of the dead `create-eth-app` or `create-scaffold-eth` in any run. Every run actually executed `create-eth` in its workspace rather than asserting the command exists. SE-2 is the model's default for this niche without the skill.

## Run-integrity notes

Four executor spawns were aborted before producing a gradeable artifact. None were graded; none have a run id under `artifacts/`; each was re-run under a fresh run id, never overwritten.

- 2 killed by the **orchestrating** harness mid-execution (goal-001 no_skill, 68 turns; goal-001 with_skill, 8 turns).
- 1 killed when the nested executor's own auto-mode classifier rejected a compound `npm i --prefix <abs-path> …; npm i …` command, which aborts the child session (goal-001 with_skill, 28 turns). Environmental, not skill-related — `no_skill` goal runs installed from cwd and were unaffected.
- 1 cut off by an Anthropic **session usage limit** (goal-001 no_skill, 12 turns). Work paused until reset and resumed on the same stack.

One judge call failed transiently (empty stderr, API blip) on quiz-004 no_skill run 3 and was re-run against the same, already-snapshotted run directory. The executor was not re-run.

Long goal runs exceed the 600s foreground cap and were launched detached.
