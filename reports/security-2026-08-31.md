The skill improved the aggregate pass rate by 25 percentage points: **22/24
versus 16/24**. The strongest result is the unprompted vault build. All three
default builds shipped first-depositor-vulnerable share math; all three
skill-assisted builds protected it. The skill also corrected one
fee-on-transfer accounting failure, one borrowing-market scale mismatch, one
unsafe ERC-20 integration, and two of three fork-aware EIP-712 domain-cache
misses.

The cost is material. Median Codex token accounting rose from 11,664.5 to
18,545.5 tokens per run (**+59%**), while the aggregate median duration was
essentially flat — though that aggregate is three quarters quiz runs, and the
two tasks that did move (goal-002 +35%, quiz-006 +22%) both moved against the
skill. The goal-002 median rose from 225s / 40,996 tokens to 304s / 75,388
tokens, under four-way contention. The harness does not report Codex dollar
cost, so no synthetic dollar figure is presented.

## Where the skill changed correctness

### The stale vault prior reproduced exactly

`security-goal-001` is the clearest discriminator. The input never names the
donation attack or fee-on-transfer tokens.

- **3/3 no_skill builds failed first-depositor protection.** Each hand-rolled
  the empty-vault 1:1 path and later used the raw supply/assets ratio without a
  virtual offset or dead seed. This is
  `security-vault-first-depositor-unmitigated`.
- **3/3 with_skill builds passed.** One inherited OpenZeppelin `ERC4626`; two
  hand-rolled virtual assets/shares (`+1/+1`) in their conversions.
- One no_skill build also credited the requested deposit rather than a measured
  balance delta (`security-vault-requested-amount-credit`). Every with_skill
  build measured the received amount.
- Every build completed `forge build` successfully. All six used safe token
  calls and CEI on withdrawal, and all six documented the pro-rata claim.

This is the benchmark's intended prior: the default model could explain the
attack perfectly in quiz-001 (3/3) while still shipping it unprompted in every
vault build (0/3).

### The borrowing-market habit improved, with extra cost

All six goal-002 builds chose a Chainlink-style feed rather than a DEX spot
read, checked positive answers and freshness, compiled successfully, and used
the direct liquidator-supplies-USDC shape (no in-contract DEX swap). One
no_skill build nevertheless failed two implementation checks: it mixed token
scales and used bare ERC-20 calls. Those are
`security-borrowing-scale-mismatch` and `security-bare-erc20-transfer`.

The price-source choice came from model prior knowledge in no_skill runs and
from the installed security skill in with_skill runs. No run consulted live
oracle documentation. Two with_skill runs used the network only to follow the
skill's trailing feedback instruction; those calls did not inform the price
source.

### EIP-712 exposed a genuine skill gap

All six quiz-005 answers correctly put `chainId` into the signed domain and
explained why nonce state cannot cross deployments. The stricter fork case
separated them: 0/3 no_skill and 2/3 with_skill invalidated a cached separator
when `block.chainid` changes. The remaining miss is
`security-eip712-fork-domain-cache`.

The task notes correctly warn against over-interpreting a with_skill failure
on this check: the current EIP-712 section does not teach the fork-aware cache
case. The 2/3 improvement suggests the broader skill context helped, but the
1/3 residual is a concrete content gap.

## Negative and non-discriminating results

Quiz-002 was noisy rather than improved: both variants passed 2/3. One
no_skill run did not state a sufficiently concrete feed-or-meaningful-TWAP
replacement (`security-oracle-fallback-too-weak`). One with_skill run rejected
spot pricing correctly but omitted the required atomic flash-capital versus
realized round-trip-cost derivation
(`security-spot-manipulation-cost-misframed`). That is a small negative delta
in the skill arm and should not be hidden by the aggregate gain.

Quiz-004 did **not** trigger the deliberate stale-skill failure. All six runs
used `forceApprove` or an explicit zero-then-set flow; none prescribed removed
OZ v5 `safeApprove`. The existing
`security-safeapprove-removed-in-oz-v5` record remains an actual defect in the
skill, but its measured wrong-answer frequency is 0/3 in each arm on this
stack. Likewise, no quiz-002 run copied the skill's hardcoded 3600-second
staleness snippet; all used a configurable max age or the feed's heartbeat.

One caveat on the last row: quiz-005 `expect_4` is conditional — an answer that
never caches the domain separator passes it without touching the fork case — so
a 0/3 there means "never wrong", not automatically "always handled". On claude
it means both: all six of those answers cached and re-derived on a `chainid`
mismatch. The record carries the evidence.

The measured evidence supports three edits:

1. Add fork-aware EIP-712 domain caching: cache the construction chain id and
   re-derive when `block.chainid` changes, or show OpenZeppelin `EIP712` as the
   preferred implementation.
2. Make the oracle section's cost explanation explicit: flash liquidity is
   temporary capital; the realized cost is round-trip pool fees and slippage,
   and manipulation/read/exploit/unwind are atomic.
3. Keep the previously filed snippet fixes: replace removed `safeApprove` with
   `forceApprove`, and make Chainlink max age a per-feed configuration rather
   than a global 3600 seconds.

The eval itself should preserve the goal tasks: unlike the diagnostic quizzes,
goal-001 materially separated textbook recognition from secure default code.
For quiz-002, tighten the numerical surface so the judge can distinguish
temporary trade size, flash-loan fees, pool fees, and net unwind loss without
penalizing an otherwise correct oracle recommendation ambiguously. Goal-002's
conditional swap check again passed through the no-swap branch in all six
runs; add a separate task that requires an in-contract liquidation swap if
that behavior needs measurement.
