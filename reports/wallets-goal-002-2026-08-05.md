# wallets-goal-002 — agent custody, decided unprompted (2026-08-05)

**Skill:** `skills/wallets` (vendored @ `9a129f1`, source `ethskills.com/wallets/SKILL.md` @ `191dcc1`)
**Stack:** executor = claude / `claude-opus-5`; judge = **codex** (CLI default model; `~/.codex/config.toml` pins no model)
**Runs:** 3 per variant = 6, all graded. `self_judged: false` on all six — the judge is a different agent and a different model from the executor, unlike the 42-run benchmark of 2026-07-25.
**Trigger:** content-only. No trigger line; **3/3** `with_skill` runs invoked the `Skill` tool on their own.

## Why this task exists

The 2026-07-25 benchmark could not reach issue #1's row 2 — *quiz both pass, goal `no_skill` fails / `with_skill` passes*, the only verdict that says keep this as a skill. `wallets-goal-001` mirrors quiz-001's EIP-7702 claim, which both variants already hold. The live claim, agent custody topology, was tested only by quiz-006, and a quiz can never produce a row-2 result.

goal-002 puts that decision inside a build: ship a rebalancer for a ~$400k treasury that trades unattended. The prompt never says custody, wallet, multisig, Safe, threshold, owner, signer, or key management. The expected failure was not a bad design but no decision at all — `privateKeyToAccount(process.env.PRIVATE_KEY)` on an EOA holding the whole treasury, with the deploy doc discussing RPCs and slippage.

## Result

| Task | no_skill | with_skill |
| --- | --- | --- |
| wallets-goal-002 | **3/3** | **3/3** |

Every expect passed in every run: 24 of 24 checks.

**Not one run took the trap.** All six, unprompted, put the treasury in a 2-of-3 Safe the agent's key cannot reach and gave the agent bounded execution rights — five via a Zodiac Roles Modifier scoped to the router with the recipient forced back to the Safe, all of them with a stated cap or float and an explicit account of what the human must sign for. A `no_skill` run wrote the argument the task's own expect_1 was built to test, without being asked:

> The alternative — one EOA holding $400k, key in a KMS — is the same system with the blast radius set to 100%. Encrypting a key bounds *who can use it*, not *what it can do*.

That is the skill's claim, reached from scratch, by the variant that never saw the skill. One `no_skill` run used WebSearch twice; the other five runs searched nothing.

## What this settles

Issue #1's row 2 is now closed for wallets: the goal task cannot separate the variants, so there is no unprompted-application value for the skill's trigger to add. Combined with the quiz-006 regrade (see the addendum to `reports/wallets-2026-07-25.md`, where property-based expect lines take that task to 3/3 vs 3/3 under both an independent codex judge and the original claude/opus-5 judge), **all eight wallets tasks are now `3/3 vs 3/3` on `claude-opus-5`**, 24/24 per variant.

The verdict is issue #1 row 1, without an exception left in it: **wiki — the skill is dead weight on this model tier**. No mistake record survives against the skill, so no skill edit has evidence behind it. The one edit still worth making stands on other grounds: SKILL.md L34's "use standard EOAs or Safe until tooling matures" measurably steered `opus-4-8` runs off EIP-7702 in the 2026-07-15 benchmark, which is harm removal rather than improvement.

Two caveats worth carrying into the wiki decision. This is one model tier — every result here is `claude-opus-5`, and a skill that is dead weight for opus-5 may not be for a smaller model. And the skill's non-knowledge content was never under test: the secret-handling guardrails are the bulk of SKILL.md and no task in the suite grades them.

## Run hygiene

The first executor escaped its workspace before creating a local `package.json`: an install resolved to the repo-root manifest, added `viem`, bumped three devDependencies, rewrote `yarn.lock` (712 lines) and left a stray root `package-lock.json`. Reverted; not part of this branch, and the remaining five runs installed locally. This is the second benchmark in a row where it happened, and it is a defect in `setup`, not in the executors — a bare workspace should be seeded with its own `package.json` so the nearest manifest up the tree is never the repo's. It was deliberately not fixed mid-benchmark: changing the workspace seed between runs would have made run 1 and runs 2-6 non-identical.

Executor transcripts also still list ~15 user/plugin skills in `system:init` alongside `wallets`, which `--setting-sources project` is supposed to prevent.
